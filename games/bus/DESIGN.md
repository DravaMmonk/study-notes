# 《车在说话》（车载总线与诊断）设计框架

工作名《车在说话》（The Car Talks），专题是车载总线与诊断：从一根谁都能拉低的线，一层层搭到一台能给整车做体检、能刷写软件的诊断仪。所有类图灵完备游戏共同遵守的结构、规则和自动检查见 [`games/DESIGN.md`](../DESIGN.md)；本文档只记录这个专题自己的内容。第 0–2 代写到逐关，后面几代写到系列；第 1 代的前九关已经做成（`games/bus`）。

**学习者：** 不假设任何汽车或电子基础。二进制、十六进制、"一帧"、"协议"都在游戏里从头讲起。

**终点：** 学完以后，学习者把自己搭的诊断仪插进一辆模拟的车：找出哪个控制器报了故障、读出故障发生时的数据、给它刷写修好的软件，再跑一遍检查，确认故障不再回来、别的功能没被改坏。跑的全是自己搭的东西：抓帧器、CAN 控制器、信号解码器、ISO-TP 收发器、诊断请求、刷写器。看一次刷写时，能看见每一层在做什么：哪一位在总线上被谁拉低、哪一帧是一段长消息的第几块、哪个请求被拒绝了又是为什么。

真实标准的出处：CAN 帧和错误处理按 ISO 11898-1（经典 CAN），分段传输按 ISO 15765-2（ISO-TP），诊断服务按 ISO 14229-1（UDS）。写逐关规格时，每个字段宽度、码值和时序参数都对照标准逐条核对，不凭记忆写。

## 1. 映射：把《图灵完备》搬到车上

| 《图灵完备》 / 已有几款 | 车在说话 |
|---|---|
| 原件 NAND | **一根谁都能拉低的线**（显性压过隐性），加上几个极小的元件（选择、比较、算术、异或、拼接与截取）。电平、差分信号、终端电阻交给世界，不教；从"线上每一拍有一位，任何一个节点说 0，大家就都听到 0"这一层起步 |
| 搭好的电路变成元件 | 搭出的板变成元件：去除填充位、CRC、解析帧、发送帧、CAN 控制器、解码信号、ISO-TP、诊断请求、刷写器……后面的关直接用 |
| 测试 | 给定一条总线（上面挂着哪些节点、各自要说什么、什么时候出错）或一辆模拟的车（几个控制器、各自的软件、存着的故障），检查学习者的节点读到、说出、做成了什么；带随机出错的关在多个种子下各跑一遍 |
| 失败给出那一组 | **波形图**：每个节点说的和总线上实际的，一拍一格排开，像逻辑分析仪；标出出错的那一位和原因（"第 37 拍你说隐性，总线是显性：你输了仲裁却还在发"；"这一位是填充位，你把它当成了数据"） |
| 元件数 / 计算量 | **拍数、总线占用、多发的帧**。约束挑战靠它（"每帧不超过 135 拍"；"刷写不超过 N 帧"） |
| 机体 | 学习者插在车上的那个盒子。它先只会听，然后会说，然后会读懂、会问、会写：每一代都是同一个盒子的升级，每一代 `keeps: 'all'` |

**要练出的思维：** 共用一根线的人必须事先约好格式和优先级；没有谁指挥，靠"谁的话更要紧就压过别人"自己排好队；出错是常态，发现错的人要让所有人都知道；一个出毛病的节点不能拖垮整条线；一个量在帧里怎么摆（哪一位起、多长、字节顺序、比例和偏移）必须对照约定，猜是猜不出来的；问一个控制器之前，先弄清它此刻在什么状态、肯不肯回答；改一辆车的软件之后，要证明别的地方没被改坏。

## 2. 核心机制

### 2.1 一台逐拍的机器，一条线性与的总线

整个游戏只有一种跑法：世界按拍推进，一拍就是总线上的一位时间。每一拍分两半：

1. **说**：每个节点跑一遍板，给出这一拍自己要说的（显性、隐性，或者不说，即隐性）。这一半只能读寄存卡，也就是自己前面几拍记下的东西，不能读这一拍的总线。
2. **听**：总线的值是所有节点说的取"线性与"：只要有一个说显性，就是显性。每个节点再跑一遍板，读这一拍总线上的值，写寄存卡。

这正是真实 CAN 控制器的样子：一位时间之内，自己说的和总线上的同时存在，控制器在采样点读回总线，下一位才能据此改变。板上若接成"这一拍说什么取决于这一拍听到什么"，引擎拒绝运行，并在板上指出那条回路（"说"的那一半读到了"听"）。

一拍里所有节点看到同一个总线值，是因为信号走完整条线所需的时间远小于一位的时间。这不是凭空的简化，而是 CAN 能做仲裁的前提：第 2 代仲裁系列末尾的机关台「线多长、跑多快」让学习者自己看到，线一长、速率一高，这个前提就破了。

逐拍机是共享的机制（`kit/engine/ticks.js`，和《从一根线开始》共用，见第 6 节）；线性与是本游戏给它的总线规则。

### 2.2 换代时一层收进世界

第 1–2 代一拍一位，学习者亲手搭出收发一帧的全部电路，最后收成「CAN 控制器」。第 3 代起，一拍送一整帧：线的两头各装着学习者的控制器，世界按控制器的行为直接送帧（谁仲裁赢、谁的帧坏了、谁重发），不再每一帧逐位跑一遍学习者的电路。

- `npm run check` 拿学习者搭控制器那一关的测试，对照逐位运行和整帧运行，结果必须一致（手册第 5 节"黑盒与搭出它的那一关一致"）。
- 波形图上点开一帧，可以切回逐位回放：只把这一帧交给学习者自己的控制器重跑一遍。
- 这是对"封装件跑学习者的电路"的一处例外（手册第 1 节），和《从一根线开始》第 2 代把网卡收进线里是同一个决定，要在原型里看玩家能不能接受。

### 2.3 循环

逐拍跑的时候，跨拍的重复就是时间。第 5 代读故障码时，一个回答里有不定条数的记录，要在一拍之内逐条扫过（逐条看状态位、留下确认过的）；这时引入**重复框**，引言接在"逐拍一位一位地攒"的经验上。元件按游戏隔离，本游戏定义自己的重复框；让区域一圈圈跑的机制若与其他游戏共用，下沉到 `kit/circuit/frames.js` 旁边。

### 2.4 数据的样子

- **位**（显性 / 隐性，记作 0 / 1）、**数**、**是 / 否**、「—」（这一拍没有值）。攒成的数先按十进制显示；有了字节以后（第 1 代的读出数据）按十六进制。
- **帧**：标识符、数据长度、0–8 个字节、时间。按字段拆开它的，是学习者搭出的解析器，不提供"按格式拆"的设置项（手册第 1 节「基础元件保持最少」）。
- **信号定义**（一行 DBC：起始位、长度、字节顺序、有无符号、比例、偏移、单位）、**诊断回答**、**故障码记录**：都是关卡给的数据，作为题目的一部分（`local`，`concept: null`，同《证明完毕》机器板上的公理）。
- 视图：比特串按字段着色（字段名来自学习者自己的解析器；解析器搭出之前只画原始的位），字节一律十六进制，帧日志一行一帧（共用的 `shell/Entries.jsx`）。

### 2.5 世界

- **总线**：挂在上面的节点。世界的节点按脚本说话（周期报文、应答、出错时喊错误帧），学习者的节点跑自己的板。
- **出错**：在指定的拍翻一位、让某个节点总是说错（"一直出错的节点"）；随机出错带种子。关卡可以写"恰好"的出错作为隐藏测试，保证 naive 解一定被抓到（同《从一根线开始》的对抗信道）。
- **模拟的车**（第 5 代起）：几个控制器，各有地址、软件版本、数据标识、故障码存储、会话和安全状态、引导程序。按 ISO 14229 的一个子集回答，由领域模块给出（`kit/domains/can/ecu.js`），每条行为一个单元测试。故障按一个行驶循环的时间线出现和消失。

### 2.6 视图

- **波形图**：每个节点一条泳道（它说的），最下面一条是总线（实际的），一拍一格；字段的分界和名字画在上方，填充位、出错的位、仲裁输掉的那一位单独标出。第 1、2 代最核心的视图。
- **帧日志**：第 3 代起一行一帧；点开一帧看字段和信号的值，再点可切回它的波形。
- **信号曲线**：第 3 代的专题里，几个信号随时间的曲线，标出触发的那一刻。
- **会话图**：第 5 代起，诊断仪和各个控制器之间的一问一答画成时序图（请求、"稍等"、回答、拒绝和它的原因码）。

## 3. 原始元件

尽量少，都问过"能不能用已有的接出来"。和《从一根线开始》意思相同的元件也在本游戏领域里各自定义（手册第 6 节）。

| 元件 | 做什么 | 第一次出现 |
|---|---|---|
| 比较 | 「相等」「小于」两种形状 | 1（和上一拍一样吗） |
| 算术 | 「加一」「相加」两种形状；后来添「相减」「取模」 | 1（数拍） |
| 常数 | 设的一个数 | 1（等够 11 拍） |
| 选择 | 条件为是取一路，否则取另一路 | 1（断了重数） |
| 异或 | 两个数逐位异或 | 1（CRC 的手算长除法之后） |
| 截取 | 取出从第 i 位起的 n 位 | 3（不满一个字节的位段） |
| 表 | 按键查、写 | 3（每个标识符上次什么时候到） |
| 队列 | 有容量的先进先出 | 3（专题「数据采集」的触发前缓存） |

**机体能力**（不是元件，由地基关教）：寄存卡（读、存两个元件，一个概念）、每拍读总线（第 1 代）；每拍驱动总线（第 2 代）；整帧收发、时钟（第 3 代）；重复框（第 5 代）。

**不作为原始元件的**（都由学习者搭出）：非、与、或（选择接出）；计数器；攒成一个数（一个数加上自己就是左移一格）、逐位送出；去除填充位、插入填充位；CRC；解析帧、发送帧；仲裁；错误计数；CAN 控制器；解码信号、编码信号；计时器；报文监视；分段发送、重组消息；诊断请求；会话保持；安全访问；读取故障码；刷写器。

### 第 0 代 · 纸笔

还没有机器，学习者手写。

| 关 | 名称 | 新东西 |
|---|---|---|
| 0-1 | 谁都能拉低 | 一根线，几个人各自按或不按；有一个人按，线就是"按下"（显性，记作 0），没人按才是"松开"（隐性，记作 1）。手填：每人说的 → 线上的 |
| 0-2 | 数怎么写 | 二进制数，固定位宽；每四位合成一个十六进制数字 |
| 0-3 | 线上没话的时候 | 没人说话时线一直是隐性；第一个显性就是有人开口了（帧起始）。手做：在一串位里圈出每一帧从哪开始 |

### 第 1 代 · 监听探针

**能力：** 每拍读到总线上的一位；寄存卡。总线上的其他节点由世界扮演，它们说话、应答；探针只听，从不开口。

**地基与练习**（新机制和它的练习交替；括号里是产出的封装件）

| 关 | 名称 | 新东西 / 变化的维度 |
|---|---|---|
| 1-1 | 跟着总线 | 逐拍：每拍把读到的一位交出去；运行本身就是时间 |
| 1-2 | 晚一拍 | 寄存卡：这一拍存进去，下一拍读出来 |
| 1-3 | 和上一拍一样吗 | 比较：线在哪一拍变了 |
| 1-4 | 数拍 | 算术：读出、加一、存回去 |
| 1-5 | 等够 11 拍 | 常数：计数加一个比较，就是"等到第几拍" |
| 1-6 | 断了重数 | 选择：断的那一拍清零（**计数器**，每一块有自己的寄存卡） |
| 1-7 | 有人开口了 | 组合：隐性连着至少 11 位之后的第一个显性是帧起始 |
| 1-8 | 攒成一个数 | 每拍把一位接到攒下的数后面（**攒成一个数**） |
| 1-9 | 这是哪条消息 | 组合：寄存卡记住"进帧了"，一块计数器数进帧后的拍数，帧起始之后的 11 位就是标识符 |
| 1-10 | 读错了 | 墙：有的帧读出的标识符不对。手做一段（任务）：在位串里找出规律，连着五位一样，后面就多出一位相反的；再搭出逐拍跳过它的电路（**去除填充位**） |
| 1-11 | 填充位也算数 | 练习·辨真伪：填充位本身算进下一段连续的位里；把计数清零的写法在恰好的位串上会错 |
| 1-12 | 一帧里有什么 | 控制段：跳过两位保留位，读 4 位数据长度 |
| 1-13 | 读出数据 | 按数据长度读 0–8 个字节；练习·加层数：0 字节和 8 字节的帧（**解析帧**） |

并行组（两路互不依赖，全部通过才继续）：

- **线会出错**（只需要逐拍的位和寄存卡，不需要解析）

  | 关 | 名称 | 新东西 |
  |---|---|---|
  | 1-14 | 坏了也不知道 | 世界开始翻位；读出的数据错了，解析器照样交出去 |
  | 1-15 | 二进制长除法 | 手算：一串位除以一个生成式，余数就是校验码；不进位的减法就是异或（新原始元件**异或**） |
  | 1-16 | 边收边除 | 逐拍：寄存卡里的 15 位就是除到一半的余数，每拍移一位、按需异或（**CRC**） |
  | 1-17 | 一串错 | 练习·换外观：连续翻掉几位，CRC 查得出 |

- **一帧在哪结束**（需要解析帧）

  | 关 | 名称 | 新东西 |
  |---|---|---|
  | 1-18 | 校验之后 | CRC 段之后填充就停了；界定位、应答位、帧结束的 7 位隐性 |
  | 1-19 | 一帧接一帧 | 练习·加层数：背靠背的几帧，帧间的 3 位间隔 |

**主线收尾：一台抓帧器**（命名系列，同一个问题在长大）

| 关 | 加回的机制 | 产出 |
|---|---|---|
| N1 抓一帧 | 去除填充位 + 解析帧，总线不出错 | — |
| N2 抓一串 | 帧结束、帧间间隔 | — |
| N3 查出坏帧 | CRC 接到解析帧上，标出哪一帧坏了；一段连着六位一样的位直接是填充错误 | **抓帧器** |

**挑战：** 待定。帧以应答界定位、7 位帧结束和 3 位帧间间隔收尾，正好 11 位隐性，所以"两帧紧挨着时等 11 位会漏掉后一帧"不成立，「有人开口了」的点题就讲这一点。

### 第 2 代 · CAN 控制器

**换代：** 探针能听不能说，想问车上任何东西都得先开口。新的外部能力：每拍驱动总线（第 2.1 节的"说"那一半）。引言说上一台为什么不够：只听的盒子什么也问不了。

| 系列 | 关 | 新东西 |
|---|---|---|
| 开口 | 说一位 / 逐位送出 / 插入填充位 / 边发边算校验 / 发一整帧 | 每拍从寄存卡里取下一位说出去（**逐位送出**）；插入填充位是去除填充位倒过来（练习·换方向）；CRC 复用；（**发送帧**） |
| 应答 | 听对了就应一声 | 抓帧器升级：CRC 对时在应答位说显性（同一个元件的升级链，第一次出现"说"也要服从"说只读寄存卡"） |

应答之后分两路并行：

- **仲裁**：同时开口（手做一段：三个节点同时发标识符，逐位圈出谁在哪一位退出；再搭）/ 输了就听（输的一方转成收方，收下赢家的帧）/ 输了再来（总线空闲后重发）/ 前缀很长的两个标识符（练习·加层数）/ 线多长、跑多快（机关台：线的长度、位速率两个旋钮；信号走完全程超过一位的时间，各节点同一拍看到的就不一样，仲裁失效）（**仲裁**）
- **出错**：我说的不是我听到的（仲裁段以外读回的位和说的不同：位错误）/ 大家一起喊（发现错误就连说六位显性，故意破坏填充规则，让所有节点都发现）/ 坏了就重发

两路汇合后：

| 关 | 新东西 |
|---|---|
| 同一个标识符 | 练习·组合与辨真伪：两个节点用同一个标识符，仲裁分不出，到数据段才撞出位错误；看反例明白标识符为什么必须唯一 |
| 记账 | 发送出错加 8、成功减 1；接收出错加 1（**错误计数**） |
| 少说话 | 计数过 127：发现错误只能说隐性的错误标志，不再打断别人 |
| 下线 | 发送计数过 255：自己退出总线；一直出错的节点不能拖垮整条线（**CAN 控制器**） |

**挑战：** 等不到的低优先级（总线很忙时，标识符最大的节点永远仲裁不赢；跳跃：标识符就是优先级，按时限分配标识符。naive 解：随手编号）。

### 第 3 代 · 数据记录仪

**换代：** 控制器收进世界，一拍送一整帧，帧带时间（第 2.2 节）。新的外部能力：整帧收发、时钟；原始元件表、队列。墙：帧收得到，但车速在哪几位、怎么换算成公里每小时，帧里一个字也没写。

| 系列 | 新东西 |
|---|---|
| 一个量 | 一个字节就是一个量：从几帧已知车速的帧里，自己找出比例和偏移（不在引言里给公式）；跨两个字节，低字节在前；字节顺序反过来（墙：照低字节在前读一个高字节在前的信号，读出的数是乱的）；带符号（温度是负的）；不满一个字节的位段（档位 3 位）（**解码信号**） |
| 照表读 | 一张信号定义表（DBC 的几行，题目给的数据）；同一帧里的几个信号；多路复用（一个选择字段决定后面的位是哪个信号） |
| 写回去 | 编码信号（解码倒过来，练习·换方向），按周期发出（**编码信号**） |
| 报文健康 | 一直在吗（该 10 毫秒一帧，超时就标无效，**计时器**；表：每个标识符上次到达的时间）/ 是不是旧的（滚动计数器每帧加一，绕过 15 回到 0）/ 有没有被改坏（报文里的校验和：CRC 换一个生成式，练习·换外观）（**报文监视**） |

「照表读」和「报文健康」都只依赖「一个量」，排成并行组；「写回去」接在「照表读」之后。

**专题：数据采集**（同一个问题在长大：记下来 → 只记要的标识符 → 满足条件时开始记，并留下条件之前的一段（队列）→ 终极：一段几分钟的试车日志，找出轮速和车速第一次持续对不上的时刻，交出那一刻前后的帧）。

**挑战：** 计数器绕回（naive 解：要求滚动计数器严格递增，15 之后的 0 被当成出错）。

### 第 4 代 · 长消息

**墙：** 车辆识别号有 17 个字符，一帧只装得下 8 个字节。

两路并行：

- **发**：一帧装得下（单帧：第一个字节写长度）/ 拆成几帧（首帧写总长，后续帧带 0–15 的序号）/ 等对方点头（收到流控帧才继续，按它给的块大小和间隔发）（**分段发送**）
- **收**：拼回来（按序号接上，凑够总长交出）/ 告诉对方慢一点（收到首帧就回流控帧）/ 等不到（下一块超时就放弃）（**重组消息**）

汇合：一来一回（两边都是自己的电路），填充字节（每帧都补满 8 个字节，练习·换外观）（**ISO-TP 收发器**）。

**挑战：** 序号转一圈（消息长到要发 16 个以上的后续帧；naive 解：序号不绕回）。

### 第 5 代 · 诊断仪

**换代：** 总线上的世界节点换成一辆模拟的车（第 2.5 节）。新的外部能力：重复框。墙：长消息送得过去了，但控制器只回答按约定格式问的问题。

| 系列 | 新东西 |
|---|---|
| 一问一答 | 问一句（读数据标识：识别号）；肯定回答是服务号加 0x40；被拒绝（0x7F、服务号、原因码）；稍等（"还在算"，延长等待时间，再等真正的回答）（**诊断请求**） |
| 会话 | 换个模式（有的数据只在扩展会话里给：墙是"当前会话不支持"）/ 别掉线（几秒不说话就退回默认会话：定期发"我还在"，**会话保持**）/ 解锁（种子换钥匙，钥匙算法是题目给的玩具版；算错了被拒，错太多次被锁一阵，**安全访问**） |
| 故障码 | 有没有毛病（一个回答里有不定条数的记录：重复框第一次出现）/ 状态位（测试失败、待定、已确认……只留已确认的）/ 清掉再看（清除后跑一个行驶循环，看它回不回来：偶发故障）（**读取故障码**） |
| 谁在线 | 功能寻址：一个请求发给所有控制器，收集每一个的回答 |

「会话」和「故障码」都只依赖「一问一答」，排成并行组；「谁在线」接在两路之后。

**专题：一辆车的体检**（六个控制器：一个不说话、一个要扩展会话才给版本号、一个总说"稍等"；终极：一张报告，列出谁在线、各自的软件版本、已确认的故障码）。

**专题：反过来当一回控制器**（可选，挂在「故障码」之后；练习·换方向：自己搭一个控制器的诊断服务端，回答读数据、读故障码，被问到不支持的就给对的原因码）。

**挑战：** 一问多答（功能请求后，两个控制器的多帧回答交错到达；naive 解：只有一个重组消息，把两段拼在了一起；跳跃：按回答者分开重组）。

### 第 6 代 · 刷写器

**墙：** 第 5 代找到了出故障的控制器，修好的软件要送进车里。

| 系列 | 新东西 |
|---|---|
| 进门 | 编程会话（控制器重启进引导程序；顺序不对时"条件不满足"）；安全访问复用 |
| 送软件 | 先擦（例程控制，回答前一直"稍等"）/ 要一块地方（请求下载，控制器说一次最多收多少）/ 一块一块送（传输数据，块计数从 1 开始）/ 收尾（退出传输）/ 对一对（例程：整块的校验和，CRC 第三次换外观） |
| 回到应用 | 重启，读软件版本确认（**刷写器**） |
| 断电 | 练习·去支架：送到一半断电，控制器回来时停在引导程序、应用无效；重新刷一遍 |

**专题：一次空中升级**（全书终点。一辆有偶发故障的车：用记录仪抓到故障出现的时刻，用诊断仪找到报故障的控制器、读出故障时的数据，按依赖顺序给两个控制器刷写新软件，再跑一个行驶循环做回归：故障码不再出现、关卡列出的信号都在范围内、各控制器版本一致。每一步跑的都是学习者自己搭的元件）。

**挑战：** 块计数绕回（软件大到要送 255 块以上；naive 解：块计数超过 0xFF 不回到 0x00）。

## 5. 元件从哪里来

- **原始元件**：第 3 节那张表，八个（寄存卡算在机体能力里）。
- **机体能力**（地基里教）：寄存卡、每拍读总线；每拍驱动总线；整帧收发、时钟；重复框。
- **学习者造的封装件**：计数器、攒成一个数、去除填充位、解析帧、CRC、抓帧器、逐位送出、插入填充位、发送帧、仲裁、错误计数、CAN 控制器、解码信号、编码信号、计时器、报文监视、分段发送、重组消息、ISO-TP 收发器、诊断请求、会话保持、安全访问、读取故障码、刷写器。每个都要在后面的参考解里用到（审计 `unused`）。
- **题目给的数据**：信号定义、钥匙算法、软件镜像，都是 `local`、`concept: null`。

**抽象链要检查的几处**（手册第 7 节第 5 步）：

- CRC 在第 1、3、6 代各出现一次（帧校验、报文校验和、软件镜像校验），后两次换生成式用同一个元件，不从异或重搭。
- 分帧在第 1、4 代各一次（帧起始和帧结束、ISO-TP 的首帧和后续帧），第 4 代的引言接在第 1 代上。
- "稍等"在诊断请求里处理一次，刷写的擦除、对一对直接复用，不重搭。
- 第 6 代专题的参考解几乎只用高层元件（报文监视、诊断请求、读取故障码、刷写器）；还在用原始元件，就说明中间哪一层没进抽象链。

## 6. 引擎：复用什么，补什么

新领域 `games/kit/domains/can/`。游戏文件夹 `games/bus/` 只有规格（`spec.js`、`game.js`），登记在 `games/games.js`。

**能直接复用的：** 电路编辑器、外壳、课程审计（`mechanism` 审计：每台机体写明会什么）、存档和蓝图、`usePlayback` 的步进、`shell/Entries.jsx`、框（`kit/circuit/frames.js`）。

**升级的共享引擎**（都和《从一根线开始》共用，做一次两款都受益）。1–3 已做，第 1 代的关在上面跑；4 跟第 3 代一起做：

1. **逐拍世界**（`kit/engine/ticks.js`，新）。现有的 `engine/machine.js` 的 `walk` 是一块板按固定顺序填一张表，没有"同一拍几个节点共用一根线"。新模块：几个节点各跑自己的板；一拍分"说"和"听"两半，"说"那一半只求值通向驱动口的那部分电路（`evaluate` 的 `targets`），读到这一拍的线就报回路；线的规则由领域给（本游戏：线性与；网络：同一拍重叠就坏、点对点带延迟）；世界节点是领域写的脚本，和玩家节点混在一起；每拍记下各节点说了什么、线上是什么、各自听到后板上的值，一拍是 `usePlayback` 的一步。出错的时间线由领域写进世界节点；跳过没变化的节点、空拍并成快进，等后几代一次运行上千拍时再按量出的需要做。
2. **有状态、多输出的封装件**（`engine/boards.js` 的 `packed`，升级）。现在的封装件只有一个输出、没有状态，每次求值从头算。CAN 控制器里有寄存卡（帧走到哪一段、错误计数），还同时给出"这一拍说什么"和"收到了哪一帧"。现在：封装件里的寄存卡按它所在的元件路径各存一份状态（`ctx.scope`）；一个封装件给出搭建关里的所有结果口，每个结果口只读通向它的那几个输入；`holds` 的封装件多一个引擎自己的结果口 `__state`，"听"那一半经它跑到里面每一张写寄存卡的元件。
3. **波形图**（`kit/shell/Timeline.jsx`）。泳道 × 拍：位画成波形，别的值画成一段段的带子（长的带子隔几拍重写一次值，一拍的值写在它后面的空拍上）；当前一拍居中，出错的拍标红；桌面和手机都横向滚动。要加的：解析器搭出以后，帧的字段名画在泳道上方；网络把帧画成按延迟倾斜的一段。
4. **整帧的线**（换代时一层收进世界，第 2.2 节）：世界按学习者控制器的行为直接送帧；`check` 对照逐位和整帧在搭控制器那一关的测试上一致；点开一帧回到逐位回放。

**本游戏领域里新做的：** 元件（第 3 节）和它们的蓝图拼法；线性与的总线规则和世界节点的脚本；十六进制显示和按字段着色；模拟的车（`ecu.js`：ISO-TP 服务端、UDS 子集、故障码按行驶循环出现、引导程序和刷写状态，每条行为一个单元测试）；`validate`（参考解通过、naive 解失败、隐藏的恰好出错）；`defineBusGame`。

**模拟的分寸：** 目标是把总线和诊断的工作机制讲清楚，不是复现某一款控制器。要守住的是：

- **按真实算法算的就照真的做**：填充规则、CRC-15 的生成式、错误计数的增减和阈值、ISO-TP 的帧格式、UDS 的服务号和原因码。写规格时对照标准核对。
- **简化要说出来。** 每一处和真实不同的地方（没有远程帧、只有 11 位标识符、错误帧的界定段从简、时序参数按拍缩小、安全访问的钥匙算法是玩具），在百科对应的词条里写一句"真实的 X 还会……"。

**诚实的限制：**

- 物理层（差分电压、终端电阻、位定时与同步、采样点）不讲，线从"每拍一位、线性与"开始；只有「线多长、跑多快」这一个机关台碰到它。
- 模拟的车是讲机制用的，各家厂商的私有诊断数据、刷写流程细节都不覆盖。
- 逐拍一位的关里，一帧约 110–130 拍，几个节点、几帧的测试是几千次板的求值；手机上能不能流畅单步和快进，要在原型里量。
