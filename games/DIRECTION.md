# 开发方向决策书：从样板游戏到创作平台

本文记录项目下一阶段的方向和理由。它只定方向、边界和顺序；落到每一条具体规矩时，写进 `games/DESIGN.md`、内核词汇表和 schema，本文不重复。做完的阶段从「实施顺序」里删掉，方向变了就改本文。

---

## 1. 终点

一套面向 agent 的开发套组、平台和 MCP：输入一套课程体系或一个专题，输出一款上手即玩的类图灵完备游戏——从零门槛起步，一路到专业深度和前沿知识，关卡设计符合 `games/DESIGN.md` 的全部规则，关卡有技术含量。

同时，人能轻松参与：任何 AI 生成的实质内容（课程结构、关卡、文案）都能在一个页面上审核、修订、试玩；修订不需要写代码。

## 2. 现状判断

共享内核、内容包、游戏编排、操作集与 Studio 已形成同一条开发路径。内核按模块注册能力，只有一份词汇表和一个课程模型；包可独立检查、逐关试玩，可依赖和覆盖别包；游戏只选包、编排和改文案。Studio 分构建、编排、文案三个工作区。当前结构和命令以 [DESIGN.md 第 6 节](DESIGN.md#6-引擎内核与内容) 为准。

游戏站保留《视觉完备》《状态之图》《证明完毕》，另提供 COMP90086 笔记交互。尚待推进的是各专题的课程设计、笔记交互覆盖，以及不可变发布、远程工具、社区创作和真人数据校准。技术检查不能证明教学质量；盲玩暂停，保留文字试玩工具。

## 3. 决策

### 决策一：内核给能力，包给内容，游戏做编排

内核代码在 `kit/engine/`、`kit/modules/` 和共享编辑、显示层；包在 `packages/<包>/` 声明对象，游戏在 `games/<游戏>/` 选包并排章。内容全是数据，引用内核能力、填参数，不写函数。这样才能被 schema 校验、diff、页面编辑和 agent 读写。

包的对象有命名空间，一对象一文件；标签是集合，关系提供先修和显示顺序，托盘和百科分组各是独立对象。包可依赖和覆盖，库包可跨专题共享。游戏不声明对象，只编排有序章节与路线图，覆盖限文案和关卡关系。具体加载、冲突与来源规则见手册第 6.1 节。

课程蓝图记录教学问题和取舍，关卡规格记录任务与测试，文案和百科解释问题与原理。技术层只验证能检查的正确性；教学引入、复用、负担等由手册第 5.1 节指导评审，不做概念标签或课程硬门禁。

### 决策二：创作层的词汇表是封闭的

模块注册值类型、运算、板、任务、内容资源、显示、语言和内容种类，拼成一份内核词汇表、一条版本线。能力名是 `<模块>:<名>`；包对象名是 `<包>/<名>`。包不属于某个模块，按实际使用的能力加载实现；能否连接看值类型。

创作者只选择和组合已有能力，缺能力就提出内核需求，不能写脚本绕过契约。词汇项按有意义的能力划分，实现细节用参数表达。`describe` 给人、agent 和 Studio 同一份可打印声明。

### 决策三：两级权限

| | 内核 | 创作 |
|---|---|---|
| 谁 | 核心工程师、管理员、高级别 AI | 玩家、普通 AI、课程作者 |
| 产物 | 代码：引擎机制、内核模块（引擎资源、世界、判定）、词汇表 | 数据：元件定义、课程蓝图、关卡规格、文案 |
| 门禁 | 单元测试、契约测试、代码审查、版本号 | schema + 技术检查；教学规范另行评审 |
| 能破坏什么 | 一切 | 只能做出一个不好玩的关 |

**决定**：内核层权限收紧，只接受走完整门禁的代码变更；创作层不设人工门禁，审计清零即可。内核的演进由创作层的需求通道驱动：创作者遇到「词汇表里没有」，产出一条结构化需求（要一种机制、一个元件、一种玩法），内核按队列实现，词汇表随之增长。

**理由**：引擎会一直更新，但更新的权限必须和创作权限分开，否则开放创作就是开放破坏。需求驱动的扩展也比凭空扩展更不容易做出用不上的机制。

### 决策四：修改只有一套操作集

内容修改全经结构化操作，CLI、MCP、Studio 是同一组工具的适配层。变更集校验、预览、写盘、日志和撤销共用实现；包与游戏各有日志，写入只动打开的层，并核对依赖包的并发变化。

id 是对外接口，一经建立不能改，没有改名操作。显示名通过文案修改；要换 id 就明确新建和删除。开发阶段不要求存档兼容，谜题戳失效就重做对应任务。这样操作可以审查，不会把身份变更藏在普通字段编辑里。

### 决策五：Studio 按职责分工作区，按对象编辑

构建打开包，编排打开游戏，文案打开包或游戏。每个工作区左栏选资源、中栏编辑复杂对象、右栏改 schema 字段或 JSON；辅助抽屉放检查、变更集和日志。对象的文案、标签、关系、覆盖虽然按职责分文件，编辑时聚在一起。

Studio 不自带专题逻辑，控件来自内核，能力只读，依赖对象先建覆盖再改。包画面是单关试玩，不借游戏课程。编辑、试玩、审计和应用读同一份待定变更。具体工作区与三栏职责见手册第 6.7 节。

### 决策六：验证闭环

**决定**：三道门，依次是：
1. **审计**：schema、蓝图审计、规格审计、文案 lint，全自动，创作层发布的唯一硬门禁。
2. **解空间信号**（决策十五）：现有变异得分是报告；活变异体的认领门禁属于后续发布工作，短解搜索不再列为门禁。盲玩（手册第 6.6 节）暂停；恢复时只用来校准这组信号，不做门禁。
3. **人评审**：只对官方课程；在 studio 的变更集视图里做。

**理由**：审计抓不到文案好坏和难度；盲玩能抓难度；文案好坏留给人（官方）或游玩数据（社区）。

### 决策七：版本与迁移

**决定**：内容声明它依赖的词汇表版本；词汇表只增不删，删改必须带迁移；kit 独立打包、语义化版本。包声明最低内核词汇表版本；开发阶段不做存档迁移，独立发布与兼容范围另定。删改的那一个版本在词汇表里写明去掉了什么、为什么（`removes: [{ at: 'level.builds', why }]`），`versions.js` 只放过写明的删改，官方游戏的内容在同一个提交里经操作集迁过去并升到这一版。

**理由**：开放给玩家后，一次引擎升级会打坏成千上万个自制关；没有版本，就没有开放。

### 决策八：发布分档

| | 官方课程 | 社区内容 |
|---|---|---|
| 门禁 | 技术检查 + 人评审 | 审计清零 |
| 质量 | 评审保证 | 游玩数据、评分 |
| 可组合 | 可被社区引用、改编 | 可改编官方关、组装成自己的课程 |

### 决策九：模板起步，库包共享

`kit/templates/<模板>/starter/` 提供起步包和建游戏的课程样例，`new-package`、`new-game` 复制数据。模板不是依赖，不会把后续修改传播给已创建的包。需要改一处处处生效的基础件做成库包，由 `uses` 依赖，例如 `arithmetic`。缺能力在内核模块补齐，不再生成模块代码。

### 决策十：基础设施与课程设计分别验收

基础设施用小内容和模板测试机制，用实际游戏检查兼容行为；真实关卡不作为单元测试夹具。课程设计按各游戏设计文档迭代，不再等旧基础设施阶段完成。技术检查通过之后，仍须审读内容、观察桌面和手机实际流程。

### 决策十一：件是内容，运算是内核能力

件在 `packages/<包>/parts/<名>.json` 选择 `op`，端口、参数和值类型来自运算声明，件只收窄设置并补外观；不写 `compute`。设置内联在件里，没有独立设置对象。基础件和后续 `stages` 是同一张卡的线性开放过程，阶段有稳定 id；不同件的替换走 `replaces` 关系。

封装件用 `inside` 保存作品引用和参考版本，任务用 `publishes` 发布实际通过作品，`awards` 开放阶段。默认运行玩家作品，没有才用参考，玩法可明确选择参考。计算实现、特殊值显示与模型都在注册的内核能力里，内容只写数据。具体见手册第 6.8 节。

### 决策十二：笔记版是同一套内核上的另一款游戏，内容各自编排

**决定**：笔记里的交互是一款 `mode: "notes"` 的数据游戏（手册第 12 节），一门课一款（第一款 `games/comp90086/`），和这门课的游戏共用内核能力，内容各自编排：一关对应一个笔记词条，不画关卡树、不设解锁，检查只跑内容正确性，不跑编排审计。每个知识点按核心思想选交互原型，拼电路只是其中一种。笔记里原有的装置插图在对应词条做成笔记关时换掉。

**理由**：游戏的任务按游戏的顺序写，文案和前置都假定玩家刚从上一关过来，直接嵌进笔记会断；另写一份插图又会重复内核已有的运行、判定、显示和 studio。分成两款游戏，笔记版照用操作集、`check`、studio 和存档，编排却只服从笔记的段落。编排审计查的是「一台逐层长大的机器」，笔记版天然不满足，所以不跑，而不是把规则改松。

**边界**：笔记版不教游戏教的东西（逐层搭机器），游戏也不为笔记的段落拆关；两边的同一个知识点用百科词条 id 互相链接。浏览器里跑不动的模型（注意力、CLIP、SAM、扩散）只能用预先算好的数据，交互不接受任意输入。

### 决策十三：运行是确定的，解就是录像

**决定**：一次判定是 `(内容版本, 任务, 板)` 的纯函数。元件求值、世界、参数台模型里不读时钟、不用未播种的随机数；要随机的由求值上下文给种子（测试序号加节点路径）。契约测试查模块的求值代码里没有 `Math.random` 和 `Date.now`。玩家交的解就是蓝图文本（参数台是一组旋钮值，填表是一张表）：任何人、任何机器拿到它，都能无头地重判一遍，得到同一个结论和同一个代价。

**理由**：这是 H5 魔塔的「录像」思路落到本项目上的样子：魔塔记下一串操作，服务器重放它来承认成绩；这里连操作都不用记，板本身就是全部输入。有了它，下面四件事不必各自发明：服务器不信任客户端也能承认成绩和排行（决策十六）；检查按任务缓存（哈希不变就不重跑）；变异审计和解空间搜索（决策十五）能批量跑；每一次尝试都是一条可以重放的数据，真人数据和 agent 数据是同一种东西。

### 决策十四：发布是不可变的包，存档跟着任务走

**决定**：
- 一次发布是一个包：`content.json` 加一张清单（内容哈希、词汇表版本、内核格式版本、来源的变更序号、作者）。包按哈希寻址，发布以后不改；一款游戏的「当前版」只是指向某个包的指针，可以前进，可以退回。
- **内核格式版本**是一个整数，管内核自己定的全部格式：蓝图文本、元件式子、`parts/<名>.json`、`blueprint.json`、修改日志的行。规则和词汇表一样：只增不改，删改带迁移。运行时声明它读得了的范围。
- 引擎不随内容打包：所有游戏跑同一份运行时。这是和魔塔样板最大的不同：每座塔自带一份引擎，引擎修了错，旧塔不受益，平台要永远兼容每一版。只增不改的格式加上兼容语料（决策十七），让旧内容在新运行时上继续成立。
- 存档按任务记，每个任务的板旁边记这个任务的谜题哈希（谜题区和测试区字段，加它用到的元件定义和它依赖的封装件的板）。打开时逐个任务比：哈希没变的板和通过记录留着，变了的只清这一个任务和依赖它的下游。整款游戏一个 stamp 的做法退下。

**理由**：没有不可变的包，就没有「这个成绩是在哪一版上打出来的」，也没有可以退回的发布；没有按任务的哈希，官方每修一关，所有玩家的进度清零一次，开放以后这不可接受。两样的代价都在今天最小：存档本来就不迁移。

### 决策十五：质量信号从解空间里算，接替盲玩

**决定**：审计多一组只看解空间、不看教学意图的信号，对所有模块成立，放在内核：
- **变异得分**：对参考板做机械变异（删一个元件并短接、换一个设置的取值、交换两个输入、换一个同口型的元件），跑这个任务的可见测试和隐藏测试；活下来的变异体是测试没有区分的错解，按 `元件@关卡` 报出。「空板必须不过」「一根线直通必须不过」是它的特例，并进来。纠错关的出题也用同一组变异算子。

原先还列了短解搜索、解的多样性和搜索工作量三项，去掉了：空板、直通和 `drop` 变异已经盖住「比参考解短也能过」里实际出现过的情形；穷举只能用元件的默认设置，而参考解大多靠具体的常数，搜得到的很少，代价却随元件数成倍涨。难度曲线先用已有的数（参考解的元件数、这一关带来几个新想法），有了游玩数据再换成真的。

发布时计划把变异认领接为门禁，现有得分只报告；目标形状是「活下来的每一个都认过」，不是一个比例：等价的变异体机器分不出来（见决策十五的限制）。它也是 agent 选候选的依据（第 4 节）。决策六的第二道门从盲玩换成这一组；盲玩恢复时只做校准，不做门禁。

**理由**：盲玩的基线已经说明，LLM 熟悉要教的东西，它的通过率量不出新手的难度（第 7 节）；而它抓到的真问题（只接一根线就过关）恰恰是解空间的性质，可以不靠模型、确定地算出来。这组信号便宜、可复现、对每个模块一样，是唯一能在没有玩家的时候给出的经验性依据。它量不出文案好坏和「好不好玩」的全部，这一点不变（第 5 节）；真人数据仍然要（决策十八）。

### 决策十六：平台是静态的包加一层薄服务，MCP 就是 API

**决定**：
- **游玩是静态的。** 运行时和包都是静态文件，放在对象存储和 CDN 上；不登录也能玩，进度在本机。这一点照魔塔：每个游戏有自己的地址，打开就玩。
- **服务只做四件事**：账号；目录（游戏、标签、评分、评论）；发布（收一个变更集，跑门禁，产出包）；承认成绩（收一份解，用和页面同一份内核无头重判，记下代价）。内核本来就能在 node 下跑，判定代码只有一份。
- **创作只有一个接口：操作集。** 托管的 studio 和远程 MCP 是它的两层皮，和今天本机的 studio、MCP 是同一组工具，只多了认证。人和 agent 走同一道门，没有只给人或只给 agent 的写入口。
- **存储是接口（开放创作前做）。** 打开一款游戏、原子地写一个变更集、追加日志、取 head：`ops/workspace.js` 收成这四个动作，文件系统是第一个实现，平台上换成数据库或 git 后端。`games/games.js` 里随内容变的字段（关卡数）挪进数据，操作集不再用正则改源码。
- **每个操作声明级别（开放创作前做）**（创作 / 内核，决策三）：关卡、任务、件定义、课程编排、文字和百科是创作级；能力实现与词汇表声明是内核级。`modify` 按调用方的级别拒绝。
- **每个变更集带着是谁**：人或 agent，agent 写明模型和它跑的是流水线的哪一步。署名、改编链、「agent 写的内容被人改掉多少」都从这里来。

存储接口和操作级别都等第二个使用者：现在只有文件系统一个后端、只有本机一种调用方，先抽接口、先标级别，写出来的是没人读的配置。读写盘已经只在 `ops/workspace.js`、`ops/log.js` 和 `content-node.js` 三处，到时是局部改动。「带着是谁」现在就有用，已做（变更集的 `by`，`npm run op -- <游戏> log` 按作者统计，并数出 agent 写的文件有多少后来被人改过）。

**理由**：内容是纯数据、判定是纯函数，所以平台最贵的两样（跑用户的代码、信任用户的成绩）都不存在：不需要沙箱，不需要常驻的游戏服务器。魔塔把塔做成整个项目文件夹，塔里能写任意脚本，换来的是无限的表达力和永久的兼容负担；这里反过来，表达力只经需求通道增长。服务薄，一个人加若干 agent 就运营得动。

### 决策十七：内核是一个有公开面的包，发布前过兼容语料

**决定**：
- （kit 独立发布时再做）`games/kit` 自成一个包（npm workspaces），有自己的依赖、命令和版本号；笔记站是它的一个使用者，不再是它的宿主。
- **公开面写成清单**：模块能导入的内核模块。导入边界进 lint：模块不引用别的模块，内核不静态引用模块，模块不引用公开面之外的内核文件。公开面之内的改动按语义化版本走，之外随便重构。
- **公开面有类型**（和自成一个包一起做）：模块契约、`CircuitScreen` 的适配面、引擎资源的签名写成 JSDoc 类型，对 `engine/` 和 `shell/` 开 `checkJs`；lint 和类型检查进 `test-kit.yml`。
- **值类型与运算签名已统一注册。** 内容端口和件设置按声明检查，跨模块共享仍须匹配类型；一个能力名只登记一个实现，不承诺按值类型选择同名实现。见手册第 6.2 节。
- **兼容语料**：kit 的代码变更，除了单元测试，再对全部已发布的包跑一遍 `check`。它是平台上的一个操作（`npm run check`、MCP 的 `audit`），开发游戏和开发内核的人从平台上跑，不进 GitHub 的 CI：重放一款游戏的耗时随内容增长，推送不该等它，也不该替平台做它。发布运行时的新版本时它是硬门禁，由平台执行。单元测试仍然不认识任何关卡：语料是另一个命令，另一个环节。
- **扩展点都是登记表**：机制、显示方式、设置控件、操作、审计规则各一张，加一项是加一个文件并过它的契约测试。机制先在内核里成形，再有游戏用它（决策二十四）：原先这里写的「只有一个模块用过的机制标成试行，第二个模块接入之前不承诺接口」撤掉，它让机制先在模块里长出来、事后再搬。
- **上限只降不升**：样式字面值和重复代码之外，再给每个模块的行数、适配钩子的个数、单款检查的耗时设上限。

**理由**：「内容检查不进 CI」防的是改关卡牵动测试，对内容编辑成立；kit 的代码变更也不靠 CI 重放游戏，靠的是平台上的兼容语料：内核的一次重构弄坏某款游戏的参考解，要到平台下一次检查这款游戏、或者改内核的人自己跑语料时才发现，运行时发布前的那道硬门禁是兜底。开放以后，运行时的每一次发布面对的是成千上万个别人的包，兼容语料是决策七那句「没有版本就没有开放」的执行办法。早期原型中新模块的实现规模降到了几百行，靠的是电路底座这层公开面；把它写下来、锁住，这个成本才保得住。

### 决策十八：运营靠门禁、数据和 agent，不靠人工审核

**决定**：
- **官方课程**由流水线产出，人在 studio 里评审（决策八不变）。
- **社区内容**过了门禁（schema、审计、变异得分、短解搜索、文案的内容安全检查）就发布，不排队等人。从最小的一环开始：玩家在一关里「改编这一关」，用这款游戏现有的元件做一个变体，得到一个地址。然后是组装成课程，最后才是新游戏。
- **改编保留来路**：一个包记着它改自哪个包；署名和改编链由此生成。
- **成绩和排行**按任务、按代价度量（元件数、步数、计算量），只承认服务器重判过的解（决策十三）。解可以公开，也可以通关后才看得到别人的。
- **游玩数据是第三种信号**：每次尝试一条记录（任务、板的哈希、结论、第一个没过的测试、用时），本机先记，愿意才上传。它校准决策十五的难度估计，也替社区内容排序（通过率、放弃点、评分）。
- **agent 是一等的作者。** 作者带自己的 agent 经远程 MCP 创作，费用在作者那边；平台自己只为官方课程跑流水线、为所有人跑门禁和重判。「跑一步」是接口，`claude -p` 是它的一个实现，换模型不改流水线。
- **需求通道由 agent 分拣**：结构化的需求（要一种机制、一个引擎资源、一种显示方式）去重、归并、按有多少内容在等它排序；实现走内核门禁（单元测试、契约、兼容语料、代码审查），可以由内核级的 agent 写、人审。
- **比赛**：给定一个模块和一套词汇表，限期做关，按游玩数据和评分排名。它同时是内核的压力测试：比赛里集中冒出的需求最能说明词汇表缺什么。

**理由**：魔塔广场的经验是，一个引擎、一个不写代码的编辑器、一套可验证的计分，加上比赛和社区，就能让作者自己长出几千个游戏。它那个年代审核和答疑靠人和群；今天这两样正是 agent 做得了的，前提是门禁是机器能跑的、内容是机器能读的，这两条本项目已经有了。平台的人只做三件事：内核的代码审查、官方课程的评审、裁决门禁判不了的争议。

### 决策十九：形式封闭，内容开放，机制受控

**目标**（2026-11-12 定）：把以前要靠看书反复琢磨的生涩知识，变成一种大体统一、有自己特色、对入门者有吸引力、值得用它学很多门知识的游戏形式。拼电路是核心玩法，但不是唯一的；价值在形式，不在某一种编辑器。

**决定**：在通用引擎（Godot）、单一类型的编辑器（H5 魔塔）和纯关卡编辑器之间，创作体验取魔塔和关卡编辑器（一种形式、只写数据、不写代码），扩展能力取引擎，但只开在一处、带契约。四圈：

| 圈 | 是什么 | 谁能改 | 怎么改 |
|---|---|---|---|
| 形式 | 学习的回路（下面五条）、判定的语义、外壳和交互、存档、地图、操作集、审计 | 内核 | 代码，改一处所有游戏一起变 |
| 机制 | 一种东西怎么造、怎么跑：数据流板、逐拍板、逐步机器、文本程序、词序条、参数台；值的种类、显示方式、引擎资源、世界 | 内核和受信任的贡献者（人或 agent） | 代码，守机制契约，过代码审查 |
| 内容 | 课程、关卡、测试、用资源拼出的元件、文案、百科、译文 | 任何人、任何 agent | 数据，经操作集，过自动门禁 |
| 游玩 | 解、改编、评分 | 玩家 | 蓝图、改编链 |

**形式的五条不变量**（每一款游戏、每一种机制都守，这是玩家认得出它的原因）：
1. **造东西，不答题。** 玩家交出的是一件能运行的东西；选择题、填空只做预测和辨析，不做主体。
2. **规格和测试就是目标。** 目标写成输入输出，失败给出具体的反例和第一处偏离。
3. **造出来的东西成为下一步的零件。** 抽象是奖励：通过的那件东西被收成一个零件，后面的关站在它上面。这条不限于电路：证出的引理是规则，写出的函数是调用。
4. **从很少的原始能力起步**，围绕主要新想法安排任务，负担由作者评审。
5. **多解并存，可以比较。** 有代价度量的关，解可以按代价排。

**机制契约**（一种机制要交什么，交齐了就自动得到 studio、审计、变异报告、重判、排行、流水线）：产物有纯文本形式；有编辑器；有确定的运行（决策十三）；有无头的 `play`；有它自己的变异算子；有接口（下一条）。现在只有电路预设把这些收成了一处（`circuit-preset.js` 和它拼装的基础件），别的机制各写各的；契约写成代码以后，「加一种玩法」才是一件有边界的事。

**一个节奏，几种世界**（2026-11-12 改定，替换原先「几种玩法并列、下一种做文本程序」的写法）。全平台只留一个核心动作：搭一台机器。参数台、分析这些不造东西的玩法不再和拼板并列，降成同一个节奏的前半段：

1. **手做几次**：亲手调一个量、判几个案例、拆一个句子，得到直觉。
2. **搭一台替你做的机器**：用板搭出那条规则。
3. **机器在一大批情形上受检，通过后收成零件**，后面的关站在它上面。

一关的几个任务正好装下这三步。变的不是玩法，是机器所在的世界：

| 世界 | 机器在里面做什么 | 现状 |
|---|---|---|
| 一次流过 | 把输入变成输出 | 已有 |
| 一个结构 | 在每一格上跑一遍 | 已有（逐步机器） |
| 时间 | 每拍跑一遍，带记忆 | 已有（逐拍） |
| 会反应的模拟 | 机器的输出改变世界，世界下一拍喂回来 | 曾验证原型，随演示移除 |
| 一批案例 | 对每个案例下判断，按正确率算 | 没有 |
| 对局 | 和别的机器同场 | 没有 |

需要「写出来」的地方用词序条：带类型的空位、点选填入，没有语法错误，手机上能用；它是板的另一种写法，不另成一种玩法。自由打字的文本程序不做。

**学是解谜，用是优化**（2026-11-12）。要学的知识是现成的、确定的，所以「学」的阶段每个任务都是谜题：几乎只有一个解，条件全摆在面前。策略层面的知识也这样学：规则由题目说出来，玩家把它搭出来。优化（尽量多挣、尽量少用）是学完以后的应用，只做成过关后的成绩或可选的挑战关，目标是挑战而不是学知识。落成三条：
- **过关条件是开始前就能完整读到的规格。** 一个测试要么是一行「这些输入 → 这些输出」，要么是一个写明了的终态；隐藏测试只防止把答案写死，不带来新的条件。
- **总量门槛不当闸门。** 挣到多少、用了几步，只做成绩和直方图。
- **引言和任务说清「搭什么」，谜题是「怎么搭」。** 策略不留给玩家猜。
词汇表可以约束测试必须给出完整的输入和终态。引言有没有说清策略，由 brief 和评审把关。

**先造世界，再造世界里的机器。** 世界的规则对玩家不能是黑箱：让玩家先把世界一块块搭出来（每块一关，逐行规格），再搭在里面活动的机器，最后才把机器放进「会反应的模拟」里跑。模拟是谜题的收尾和回报，不是谜题本身。

**原型经验。** 一组经济学谜题曾让玩家在看不到需求的情况下猜调价策略，并在达到指定收入时过关，测试时只有熟悉策略的玩家能做。后来把需求、供给和调价分别做成输入输出约束，最后才让玩家把调价板放进动态世界，按是否出清判定。世界每拍提供上一次的价格，板表达调价规则。收入留作结果读数。

另一组原型把主线集中在抽象概念，把配套元件的搭法留给支线。通过了自动检查，直觉能不能立住还缺少真人试玩验证。课程仍应说明借来的元件何时提供、何时由玩家的作品接手。

**从别的游戏取什么**（都落在形式这一圈，所有游戏一起得到）：代价的直方图（Zachtronics：过关以后看见自己在所有人里的位置，这是重玩的理由）；一次运行就是一个链接（确定性使它不花钱：内容哈希加蓝图）；改编前必须自己通关（关卡编辑器的规矩，这里就是参考解通过加变异门禁）；蓝图的复制和分享（已有）。

**不做什么**：不给内容开代码口子（魔塔的插件脚本换来的是永久的兼容负担和无法自动验证）；不做没有可判定产物的题型（那不是这个形式，硬塞进来会稀释它）。

**理由**：玩家愿意用同一种形式学很多门知识，前提是换一门课不用重新学怎么玩，而且每一门都保持同样的质量下限。这两条都要求形式封闭。可是知识的形状各不相同，一种编辑器装不下，所以机制必须能长；让它在契约里长，新机制一出生就带着全套工具，也不会长成另一个游戏。内容全开放而且是数据，agent 才能大量地写、机器才能把关。封闭的部分越小越稳，生态才转得起来：内核的人只审机制这一圈。

### 决策二十：文案按字段编辑，按语言独立存放

**切换语言时，平台界面和游戏内容一起更新。** Studio 保留两列语言对照、按章筛选和在画面上点文字编辑。每列可独立选语言，任何语言都可以先写。画面预览即时读取待定变更，切换语言时保留当前关卡、任务和作品。

**配置只引用文案键。** 课程自有文案随课程存放，内容包的关卡、元件和百科文案随内容包存放，各自用 `i18n/<lang>.json` 保存扁平的「键 → 文本」表。键代表字段的文案身份，改写文字、调整顺序和在同一归属内移动字段都可以沿用它。不同字段默认有自己的键，因此同一句话可以按语境分别翻译。Studio 根据配置中的引用找到语言文件，文案编辑通过现有变更集写入该文件。存储格式和编辑规则见[手册第 6.10 节](DESIGN.md#610-多语言文案)。

### 决策二十一：界面由内核按能力装配

共享屏幕、控件、编辑器和结果区由内核维护；模块注册显示声明与加载入口，适配器把内容和运行数据交给它们，通用渲染器不直接引用模块 UI 或 CSS。场景专用的模型与显示可以作为受控能力注册，包只选已有能力。

外观改动先看内容配置，再看共用部件是否缺选项；样式用统一令牌，不在包里写界面代码。场景组合下放到内容时，按实际需求制定 schema，不为假想用法扩展。

### 决策二十二：作品和验证，任意一边都可以交给玩家

各款游戏里拼板之外的玩法（真值表、造反例、填表、找漏洞、参数台……）各写各的屏幕，约 6300 行，新学科还得再写。统一的依据是屏幕上本来就只有两块东西：**作品区**（板、条、表：一样被做出来的东西）和**验证区**（检验它的那些情形和预期）。每一块都可以是给定的，或者交给玩家；任意搭配都是一道题。

| 作品 | 验证 | 是什么 | 现状 |
|---|---|---|---|
| 玩家做 | 给定 | 搭 | 主玩法 |
| 给一样错的，可改 | 给定 | 修 | 任务的 `starter`：板打开时摆着它 |
| 给定，不能改 | 玩家写 | 破（审计） | 任务的 `works`：还是那块标准的板，结果区里填检验（`shell/Checks.jsx`） |
| 玩家做 | 玩家写 | 先写检验再搭 | 没有 |

（两边都给定只能读，不做成任务。）

**一条判定管所有搭配**：一个任务手里有几样作品（标明对错）和几条检验，玩家补上开放的那一边，过关永远是同一句话：**对的作品通过每一条检验，每样错的作品至少被一条检验挡住。** 搭和修是让自己的作品算进「对的」；破是让自己写的检验把对的和错的分开。这就是变异测试，所以出题的原料现成：对的作品是参考解，错的作品是任务已有的错解，不够再从变异体里挑。

**作品不必是机器。** 能确定地跑在一个情形上得出结果、用封闭的几种形态之一写出来，就算作品：**板**（放元件、连线）、**条**（往带类型的空位里填：公式、证明的子句、句子成分）、**表**（一行一条声明）。判定和形态无关，形态只决定作品区用哪个编辑器。

**已有用例。** 《证明完毕》的规则板检验任务给玩家一份只读的声明，由玩家写检验条例。内核的 `BoardChecks` 负责编辑与回放。

**让写检验不退化成调参**，两条都来自证明完毕：一次给几样各错一处的作品，要求用很少几行全部挡住（得先想清每样错在哪）；行数就是限制。只给一样错作品、不限行数，才会是来回试。

**检验的结构。** 单纯给几个数可能碰巧挡住所有错解。原型中一次位串检验要求玩家找出边界输入，因为三样错作品分别对应误读起始位、共享分隔位和误读帧长度。穷举 65536 项输入时，96.9% 挡不住任何错解，两行检验只有四组解。给逐拍作品写检验时，字段形状由模块声明，结果区可显示波形并定位到失败的一拍。

**哪些任务可以出成写检验**：反例是有结构的对象、错作品来自真实误解的知识点才出；算一个数的公式类知识点不出。玩家造的是具体的反例；写「所有情形都该怎样」的性质是另一格（性质本身也得是一块输出真假的板），放在搭过、挑过错之后收束用，还没有做。

检验条例使用 `BoardChecks` 配置和共享判定；曾有的电路 `works` 分支已移除，不作为任务字段保留。新增玩法先注册实际需要的编辑、判定与反馈能力。

还缺少让玩家先写检验、再自己搭作品的完整课程用例。

### 决策二十三：一个模型管理可用件与阶段

默认跟进度，任务再增删；件或阶段是开放的单位，取消设置和取值的派生地址。`adds`、`local`、`opens`、`awards`、`gives`、`withholds`、托盘和发布作品都由同一个课程模型计算。引理形状和设置升级照这条路径，不另设模块标记或修订表。

包不算学习进度：逐关试玩按本关托盘提供能力，没有托盘就提供全部。课程解锁和托盘成员的引入来源只在游戏检查。具体见手册第 2.8 节。

### 决策二十四：底座是一组基础件，玩法是它们的配置

**决定**（2026-11-14）：内核不再按机制各做一个底座（电路底座、以后的规则行底座……），而是照实体组件系统的拆法做：**东西只是数据，逻辑都在只读数据的函数里，一种玩法是一份配置。** 机制的设计不放在内核模块；游戏开发中发现缺一样基础件，停下来回内核做，不在模块里先写一份。

**五个约定**（基础件之间只靠它们对接，不认识彼此）：

| 约定 | 是什么 |
|---|---|
| 作品 | 玩家造出来的东西：放着若干个件的实例，实例之间连着或套着。能存、能比、能写成文字。板和条是同一个作品的两种画法（证明板上的证明带着它的证明项；规则表的几行会转成一块板去判定） |
| 件 | 玩家手头能拿来造的东西。只有名字和若干个可有可无的**面**（下表），没有统一的接口：每个编辑器、每种判定只读它认识的面。「元件」是件在电路上的叫法；词序条上的块和可以独立放进作品的规则也是件。设置内联在件里，由阶段逐步开放。手头可用的件和阶段都由决策二十三的规则管理 |
| 检验 | 一个情形和对它的预期 |
| 失败 | 第一处不对：在作品的哪里、哪条检验、要什么、得到什么、为什么 |
| 过程 | 一次运行留下的步骤，每一步说得出自己在作品的哪个位置，编辑器按位置标出来 |

**件的面**：

| 面 | 内容 | 谁读 |
|---|---|---|
| 空位 | 几个、各要什么、产出什么 | 电路画布画成输入口，词序条画成空格；判定按它求值 |
| 设置 | 哪些设置、什么控件、哪些取值 | 卡片和详情；默认声明来自运算，件写差异 |
| 区域 | 里面还能放件，区域给出局部的值，只在里面能用 | 电路画布画成框，线只往里走；词序条画成一对括号，区域给出的值是括号前绑定的名字（证明项的 `fun a => □` 就是证明板的假设框，块上本来就写着「框」） |
| 内部 | 封装的 variant 和参考作品；任务发布玩家通过的作品，阶段决定何时可用，玩法可明确选择参考 | 求值、回放、元件箱 |
| 画法 | 卡片、块、选项各怎么画 | 各编辑器 |
| 保存 | 跨拍留着什么 | 逐拍的运行 |

**基础件**（内核里各自独立，玩法配置挑着用）：

- **编辑器**：电路画布和手机格位、词序条、规则行、填表。只管画作品和改作品。 Q.E.D. 的固定公式键在 `parts/<名>.json` 登记，公式键由关卡的 `adds` 引入，经内核托盘和课程先修关系进入词序条。翻译和查询共用 `tree + check` 编辑、保存和检查；变量、谓词等随题目和作用域提供。
- **判定**：过关只有一句话（决策二十二）：对的作品通过每一条检验，每样错的作品至少被一条挡住。它下面是「一样作品在一条检验上算不算对」的几种算法，各是一个纯函数，返回同一种失败：**逐例**（跑出结果，和预期比）、**逐拍**（每一拍比，可以有不管的拍）、**性质**（对作品本身的一个断言：写完了没有、递归的参数变小没有、超没超预算）、**等于参考**。再加两个组合：**依次**、**藏起来**（检验不给看，失败时只给第一处不对）。
- **作者侧的检查**：只要「有一个判定」：参考解过、naive 解不过、空作品不过、变异体。不再每种玩法写一遍。
- **运行的节奏**：逐步回放、一次判定、几样作品轮着跑。
- **反馈**：结论行、测试标签、波形、结果区、作品上的标记。
- **件的登记和传递**：这一关手头有什么（决策二十三）；一个任务通过了，它的作品成为一个件。

模块只交三样：这门学科的值怎么比、怎么写出来；一样作品在一个情形上跑出什么；这门学科自己的性质。它不写组件，也不写模板。

**理由**：一个底座里捆着互不相干的事。`circuit-domain.js` 一个文件里有判定、作者侧检查、schema、课程读取，前三样和电路没有必然关系，只是当初写在了一起；`logic` 另写了一遍，再来一种玩法就得第三遍。同一件事「前面造出的东西后面当零件用」在 `logic` 当时有七张互不相通的表（引理、门、机器元件、证出的等式、声明的类型、定义的函数、引入的符号），其中定义没走搭出元件那条路，所以成了「不用玩家自己的定义」的例外。形式的第三条不变量早就写着「这条不限于电路」，这些重复曾说明实现没有跟上。拆开以后，玩法是组合出来的，基础件的数量增长得慢：十来种编辑器、五到八种判定、几种节奏和反馈，配得出远多于一百种玩法，要守住的只有上面五个约定。

**和传统引擎的关系**：拆法取实体组件系统（实体只是编号，组件是数据，系统是函数）；件对应原型，板上的节点对应实例，搭出的件对应预制体，引理的几种形状和元件的升级链对应预制体变体。不取的是「资源里可以写脚本」：内容仍然只能用封闭词汇表里的东西拼（决策二、十九），这是内容能交给不受信任的作者并被机器检查的前提。件也不是对象：它没有藏在里面的可变状态、没有身份、没有继承，更接近带签名的函数，状态明摆在板上，所以运行是确定的（决策十三）。

**运行作品的引用闭包。** 一份解不仅是当前板，还包括它所引用的封装件、引理和定义的具体作品。重判与回放必须一并读取；升级靠阶段与发布的 variant，不把玩家作品和参考实现混用。框在条上是带作用域的括号，在图上是区域，共用同一作用域边界。

## 4. agent 流水线

```
课程资料 → 知识点 → 课程蓝图 → 蓝图审计
        → 关卡规格 → 规格审计 + 参考解运行 + naive 解失败 + 教学 lint
        → 文案 → 文案 lint + 术语链接
        → 变更集进评审队列（官方）或直接发布（社区）
```

每一步的产物都是内容层的数据；每一步失败都定位到一条规则；每一步的修改都是操作集里的操作。

**流水线从知识点出发，不从元件出发**（手册第 1 节「玩的过程就是学的过程」、第 4.1 节）。《视觉实验室》第一版（计算机视觉第 0、1 章，59 关）是按旧蓝图做的：蓝图的「想法」可以是任何东西，审计又要求一关一个新想法、每个想法后面有练习，于是 agent 给每块元件编一个想法（「常数」「取整」「取较大值」各占一关，引言是同一句套话），同一块板、同一段话在几关里重复，判断题看题面的字就能答，参数台拖一个旋钮到变绿就过，文案短到说不清问题。闸门全过，教的东西却很少。改法是改流水线而不是改这款游戏：蓝图先从课程材料列出知识点（术语、出处、撞上的墙、纠正的错误），每个 slot 写出玩家要回答的问题和思维链；审计不再让元件充当知识点；关卡和文案的闸门加上教学 lint（重复的板、重复的话、拖到变绿的实验台）和术语链接。《视觉实验室》后来整款删掉，计算机视觉留下《视觉完备》。

实现见手册第 7.2 节（`kit/pipeline/`，`npm run pipeline`）。在蓝图和关卡规格之间多了一步「模块」：蓝图向模块提的需求（决策三的需求通道）由工程师实现或拒绝并写明理由，内容 agent 不写代码。一步失败时往回走：关卡设计 agent 停在蓝图做不到的地方，它的报告成为课程设计 agent 下一次的输入（`--from`）；评审 agent 的发现按它归属的那一步交回去；人的退回意见也一样（`comment`）。在网络第 1 代上，往回走是常态而不是例外：蓝图改了五次（两次因为模块的回答、一次因为关卡设计停下、两次因为评审），关卡写了四遍，文案三遍。

**流水线接下来的四处改动**（依赖决策十五的信号）：
- **先做竖切片。** 新专题最难的是模块建模：什么是原始能力，机体是什么，哪一种机制承载它。蓝图之前多一步：agent 交出机制选择的论证和三关能玩的切片（从零起步的一关、搭出第一个元件的一关、用上它的一关），过了门禁才铺整门课；切片做不出来的专题在这里拒绝，写明原因（第 5 节的适用范围）。
- **生成几份再选。** 关卡规格这一步，每个 slot 出几个候选，按变异得分、解的多样性、搜索工作量在这一章难度曲线上的位置排序，留下一个；人评审时只看留下的。
- **人的修订是标注。** 修改日志记着每个变更集是谁写的（决策十六）。agent 写的内容被人改掉的比例，按步、按规则统计，是流水线质量的直接读数；被改掉的地方连同改后的样子，回到那一步的 brief 里当反例。它和「闸门漏掉的改成检查」是同一个回路的两半：能机械查的变成检查，不能的变成例子。
- **固定的基准专题。** 选两三个专题反复跑，记闸门通过率、评审发现数、人工修订率、每一步的用量；换模型、改 brief、改闸门，都在这几个数上看得出好坏。

## 5. 承认的边界

- 内容层做不到百分之百无代码：真的只能用代码表达的测试生成和判定留在内核模块，以名字暴露。这是边界，不是失败。
- 词汇表的粒度是本方向唯一真正难的决定，没有办法事先证明对；只能在一个模块上试，按「屏幕上能指着说的概念」校准。
- 审计抓不到的只有文案好坏和难度；前者靠人与社区，后者靠解空间信号（决策十五）估计、靠游玩数据校准，都不是精确的。
- 适用范围：内核承诺的是有组合结构的专题，能从少量原始能力逐层搭起来、每一层的对错可以由测试判定。以记忆、语感、审美判断为主的专题需要另一种玩法，不在承诺之内；竖切片做不出来就是信号。
- studio 的通用控件集是内核的固定开销；每种新的值类型都要内核加一个控件。

## 7. 开放问题

- 词汇表粒度：《状态之图》上定出了第一版（`kit/modules/table/vocabulary.js`），《证明完毕》上成立（`kit/modules/logic/vocabulary.js`）：规则即元件是元件项，框由 kit 给，玩家证出的引理、拼出的门、证出的等式是内容里的数据（陈述、口），不是词汇项；句子是模块记号的文本，存档迁移的几十个一次性函数合成十来个带参数的迁移项。《视觉完备》上同样成立：测试场景、目标图、图像生成器、约束各是一种项，一关按名字选项、填参数（`kit/modules/image/vocabulary.js`）。机关台抽成通用参数台以后也成立：模拟是模块的一个模型项，旋钮、情形、步骤、按钮、目标（对模型算出的量的限制）和版面全是数据，画面是一个封闭的显示项集合（内核给曲线、像素行、读数、目标、步骤……，模块补拼不出来的图和交互）。留下的问题是显示项的粒度：模块的显示项（暗箱侧视图、霍夫累加器、封面配点……）多半一个模型一项，是不是该再拆成更通用的「可拖动的点」「栅格图」，要等第二个有参数台的专题来定。
- 盲玩 agent 的能力与真实学习者的差距：通过率高不等于人学得会；需要少量真人数据校准。基线说明了差多远：五款原型的前 9–12 关，LLM（claude-sonnet-5-5）几乎都一次通过、不要提示，每关十几秒。它熟悉逻辑门、德摩根律、动态规划和图像滤波，新手要学的正是这些；它读得懂一句话的元件说明，新手常常读不懂；它不看图，文字版的画面（图像是一格一格的数）对它反而更好用。所以它的突起是「这一关缺了什么」（`difficulty-spike` 在这上面有用：一关同时要三件事、反馈说不清 0 和「否」、引擎丢了设置），不是「这一关对人难」；平坦的曲线不说明新手也平坦。校准要几个真人走同样的 harness（`--player human`）或页面里的同一种记录，再比两条曲线的形状；另一条路是给 agent 加限制（更小的模型、不许用外部知识、只许按提示走），看它的曲线是不是更像人。
- 社区内容的改编与署名：改编官方关、组装课程时，蓝图审计（抽象链、分支）对拼装出来的课程还能不能成立。
- 内核需求通道的优先级：谁来排序，按什么排。
