# 开发方向决策书：从样板游戏到创作平台

本文记录项目下一阶段的方向和理由。它只定方向、边界和顺序；落到每一条具体规矩时，写进 `games/DESIGN.md`、领域的词汇表和 schema，本文不重复。做完的阶段从「实施顺序」里删掉，方向变了就改本文。

---

## 1. 终点

一套面向 agent 的开发套组、平台和 MCP：输入一套课程体系或一个专题，输出一款上手即玩的类图灵完备游戏——从零门槛起步，一路到专业深度和前沿知识，关卡设计符合 `games/DESIGN.md` 的全部规则，关卡有技术含量。

同时，人能轻松参与：任何 AI 生成的实质内容（课程结构、关卡、文案）都能在一个页面上审核、修订、试玩；修订不需要写代码。

## 2. 现状判断

**已经有的**：一本设计手册（原则、课程结构、关卡规格、审计规则、引擎分层、作者流程）；修改内容的操作集，带修改日志、命令行和 MCP（手册第 7 节）；一个共享 kit（求值、封装件、框、逐步机器、逐拍世界、两套电路编辑器、外壳、地图、存档、蓝图文本）；若干领域模块；七款原型游戏（决策十）。阶段 0+1 已经做完：内核有内容层的契约（schema、词汇表、数据游戏的加载和检查），七款游戏的文件夹里只有数据；封装件跑学习者的电路；`unused`、`bare-intro`、`idle-idea`、`bypass` 在所有游戏打开并清零；课程的形状是数据，`npm run deps` 画出元件依赖图；机关台是一个通用参数台（`kit/shell/bench/`）；电路关是一个内核界面（`kit/shell/CircuitLevel.jsx`）。领域有了写下来、测得出的契约（手册第 6.3 节，`kit/engine/contract.js`，`npm test` 对六个领域、七款数据游戏机械地查）和机制目录（手册第 6.5 节）；`npm run new-domain` 从模板（数据流电路、逐拍总线）生成一个能玩的领域和入门游戏，`npm run new-game` 从领域的入门游戏开新游戏。阶段 6 已经做完：逐拍总线的模板从 `kit/domains/can` 抽出（`kit/scaffold/tick-bus/`），网络专题的 `net` 领域从它生成，契约测试一次通过；路上修了脚手架的三处毛病（游戏文件夹里先有设计文档时拒绝生成、生成失败时留下半个领域、`scaffold.test.js` 嵌在测试运行里跑生成的领域测试时总是退出 0，查不出失败）。阶段 3 已经做完：盲玩 harness 是内核（`kit/engine/play/`，每个领域在 `domain.js` 给一个 `play` 钩子），只给玩家看到的东西、照游戏的规矩判尝试，一局像一份存档，记录是内容里的数据（`playtests/`），`check` 列出审计面板并跑 `difficulty-spike`；五款原型各有一局 LLM 盲玩的基线，harness 指出了两处突起：《状态之图》「走不到的路口」一关同时要三件事（难度曲线，写进了它的设计文档）；《车在说话》1-5 是引擎的毛病（蓝图导入丢了常数的值，已修；量到它的那一局只留在 git 历史里，因为它量的是一个已经修掉的错）。阶段 4 已经做完：studio（手册第 6.7 节，`npm run studio`）是操作集上的一层皮，不认识任何领域——树上拖关就是 `level.move`，表单全部由 schema 和词汇表生成，板在表单里画成无头的 SVG、在游戏自己的电路编辑器里改，试玩的是待定变更集留下的内容，审计栏随每次改动重算（连同盲玩记录），评审里看操作和字段级 diff，再应用或撤销；它和 MCP 用同一组工具（`kit/engine/ops/tools.js`，经开发服务器的 HTTP 桥），MCP 的 `render` 因此也能出 SVG，领域可以给一个无头的 `scene`。在《软件工厂》第 1 章的副本上，读完全部文案、改文案、改测试、挪关、在电路编辑器里改参考板、看审计变红又清零、嵌入试玩、应用、撤销，都在浏览器里走通，不写一行代码。阶段 6.4 已经做完：一关是一串任务（`kit/engine/tasks.js`，手册第 4 节），只有一个任务的关就是普通的关；任务有整款游戏里唯一的 id；存档换成按任务 key 记的新形状（手册第 2 节，旧存档不读），任务在关内插入、换位置、挪进别的关、几关合成一关都不用迁移，`level.merge`、`level.split` 和领域的存档迁移项、`tasks` 钩子都已删掉；两个领域模板和 net 领域是这个形状，《从一根线开始》经操作集换了过去。studio 的主区是游戏自己的页面（手册第 6.7 节）：外壳标出画面上是内容字段的那几块，点一下在右边的侧栏里改（和原来的表单同一套控件），加任务、提示、引言、测试都在它出现的地方点「+」；没有画面位置的字段在「字段」页一项一行，点开也在侧栏改。在《从一根线开始》1-1 的画面上加一个任务、改它的目标、改进线的延迟、加一个测试，经操作集落盘，审计清零。

**缺的**，按对终点的影响排：

1. 领域模块仍是每个专题的真实成本：脚手架有数据流电路和逐拍总线两个模板，逐步机器、参数台的新领域要从例子领域抄起；网络第 1 代的领域从模板生成以后又改写了约一千行（线、格式、取用的队列、要的东西），领域需求通道是流水线里最慢的一环（第 4 节）。
2. 经验性验证只有 LLM 的读数：盲玩 harness 有了，但基线是每款一局 LLM 盲玩，难度规则要 5 局才算数；没有真人数据，LLM 和新手的差距也还没校准（第 7 节）。几种玩法 harness 还不支持（手动玩法、证明板、句法，`games/DESIGN.md` 第 6.6 节）。
3. kit 自身不统一：原型的领域里一关还是「一种玩法（`kind`），可选再拆几段 `tasks`」两种形状，studio 画面上标不出领域自己画的部件（参数台的旋钮、表格的世界）；部分封装件仍是内置实现；电路关界面已在内核（`kit/shell/CircuitLevel.jsx`），《视觉完备》《状态之图》的旧界面等按专题重做时换上（《视觉完备》的电路关因此还没接上最后一次运行）。
4. 设计文档与代码的一致性靠约定。
5. 没有版本与发布形态；studio 的评审页签还没有写驳回意见的入口（流水线那一头已经有了：`npm run pipeline -- <游戏> comment`，意见交给那一步下一次跑的 agent）。

## 3. 决策

### 决策一：三层架构，内容层是纯数据

```
内核层   kit/engine, kit/circuit, kit/shell    机制与界面，所有游戏共用
领域层   kit/domains/<x>                        值、引擎资源（基本运算）、世界、判定、画法；一个专题一份代码
内容层   games/<x>/                             元件定义、课程蓝图、关卡规格、文案、百科；全部是数据，不含代码
```

**决定**：内容层不含任何可执行代码。测试数据、诊断谓词、引言插图、通关后的面板，一律改为**引用**：领域层暴露有名字、带参数 schema 的生成器和谓词，内容层只写 `{ "名字": 参数 }`；无法生成的物化成数据。参考解和 naive 解用已有的 ASCII 蓝图文本。

**理由**：只有纯数据的内容才能被 schema 校验、被 diff、在页面上改、在 git 里审、被 agent 安全地读写；也只有纯数据才能开放给不受信任的创作者。

**内容层分三种产物**，粒度从粗到细，各有审计：

| 产物 | 内容 | 审计 |
|---|---|---|
| 课程蓝图 | 机体阶梯、每代能力、原始元件清单、元件依赖图、每个机制「第一次非它不可」的位置、练习簇、并行组 | 不依赖的就分支、抽象在上升、机制放在被核心用到的地方、基础元件最少 |
| 关卡规格 | 目标、传感器、测试、参考解、naive 解、新带来的元件、托盘、预置、任务段、挂靠 | 现有 `audit` 全部，`idle-idea`、`bypass`、`bare-intro` 全开 |
| 文案与百科 | 中英两面、链接、词条、修订 | 现有 `check` 的文案检查，加禁用词与长度 lint |

设计文档保留，只写理由与取舍；凡是能检查的事实从数据来，不再手抄。

### 决策二：创作层的词汇表是封闭的

**决定**：一关、一款游戏只能由内核和领域**已经提供**的东西组合而成。每个领域给出一份**词汇表**（domain vocabulary）：值类型、原始元件、世界类型、测试生成器、判定谓词、玩法、机体能力，每一项带参数 schema。创作者能写的全部，就是在词汇表里选项、填参数、接线。词汇表里没有的，不由创作者绕路实现，而是提交一条结构化需求进内核队列。

**理由**：这是人机协作和开放创作成立的前提。词汇表封闭，内容才可能无代码；内容无代码，沙箱才是结构上成立的，不靠审查；审计才能覆盖创作者能做的一切。

**词汇项的粒度标准**：一个词汇项对应玩家在屏幕上能指着说「那个东西」的一个概念——一种元件、一种世界、一种玩法、一种测试的形状。满足这条的进词汇表；只有实现细节能区分的，合成一项加参数。太粗创作者表达不出，太细就是变相写代码。先在最成熟的领域（《状态之图》）上定标准，再推到其他领域。

**词汇表 v1 的来源**：从现有样板游戏提炼。规格现在做的每一件事，凡是靠临时 JS 的，都改成词汇表里一个有名字的项。提炼完，v1 自然成形，内容层去代码化也同时完成。

### 决策三：两级权限

| | 内核 | 创作 |
|---|---|---|
| 谁 | 核心工程师、管理员、高级别 AI | 玩家、普通 AI、课程作者 |
| 产物 | 代码：引擎机制、领域模块（引擎资源、世界、判定）、词汇表 | 数据：元件定义、课程蓝图、关卡规格、文案 |
| 门禁 | 单元测试、契约测试、代码审查、版本号 | schema + 审计 + 盲玩，机器自动放行 |
| 能破坏什么 | 一切 | 只能做出一个不好玩的关 |

**决定**：内核层权限收紧，只接受走完整门禁的代码变更；创作层不设人工门禁，审计清零即可。内核的演进由创作层的需求通道驱动：创作者遇到「词汇表里没有」，产出一条结构化需求（要一种机制、一个元件、一种玩法），内核按队列实现，词汇表随之增长。

**理由**：引擎会一直更新，但更新的权限必须和创作权限分开，否则开放创作就是开放破坏。需求驱动的扩展也比凭空扩展更不容易做出用不上的机制。

### 决策四：修改只有一套操作集

**决定**：对内容层的每一种修改都是一个结构化操作：改字段、加关、删关、移动挂靠、拆合任务、改元件的解锁关、重命名 id、拆出引入关、合并几关为一关的任务段……每个操作自带：
- schema 校验和受影响的审计规则；
- 存档迁移的自动生成（重命名、推出新解锁、新插入的前置关标通过、`merge`）——开放之前不做：开发阶段存档不迁移，存档记着谜题的 stamp（`kit/engine/stamp.js`），和内容对不上就清空（手册第 2 节）；
- 一条可回放、可撤销的日志。

MCP 的 `modify`、studio 的每个编辑按钮、CLI 三者只是这套操作集的三层薄皮；人和 agent 改的是同一份数据，走同一条门禁。

**理由**：手写迁移已经是手册里记录的坑；agent 会频繁重排，迁移必须自动。一套操作集也是人机协作不互相踩的唯一办法。

### 决策五：studio 是 schema 驱动的通用编辑器

**决定**：studio 不持有领域知识，不含领域代码，自由度就是词汇表的自由度。它由四块组成：
- **树编辑**：课程树照地图的排法列出（主线、并行组的分支、专题、挑战），拖动一关就是 `level.move`；分支、挂靠的问题由审计栏就地报出；
- **关卡编辑**：字段按 schema 生成表单；值的形状映射到 kit 里一小组**通用控件**（中英文字和链接、可搜索的选项、数值、表格和矩阵、逐拍的波形、列表、电路板），形状说不清的地方词汇表在 schema 上写声明式的提示（「这是矩阵」「这是逐拍的值」「数一次加减多少」「这个字段归哪一段」），不写控件；
- **嵌入式游戏**：改完即玩，运行结果和审计并列；
- **审计面板与变更集评审**：`check` 的结果按关、按规则常驻，改一处立刻重算；agent 的每次产出是一个变更集，附审计结果、盲玩统计和 diff，人可以批准、就地改、或驳回并写意见，意见回到 agent 的下一轮输入。

**边界**：控件是代码，但它们是 kit 的通用控件，由内核维护；领域层不再有「给 studio 的编辑器」这一项。一种新的值形状要内核加一个控件，只在有内容用它时加（现在没有按像素写的图，所以没有图像控件）。

### 决策六：验证闭环

**决定**：三道门，依次是：
1. **审计**：schema、蓝图审计、规格审计、文案 lint，全自动，创作层发布的唯一硬门禁。
2. **盲玩**（暂停中，手册第 6.6 节）：另一个 agent 只凭引言、提示和托盘打每一关，不看参考解；记录通过率、尝试次数、用到的元件。这是难度曲线和「一关一个知识点」的唯一经验性信号。先在现有五款游戏上跑出基线。
3. **人评审**：只对官方课程；在 studio 的变更集视图里做。

**理由**：审计抓不到文案好坏和难度；盲玩能抓难度；文案好坏留给人（官方）或游玩数据（社区）。

### 决策七：版本与迁移

**决定**：内容声明它依赖的词汇表版本；词汇表只增不删，删改必须带迁移；kit 独立打包、语义化版本。官方课程的存档迁移由操作集生成；社区内容只保证在它声明的版本上可玩。

**理由**：开放给玩家后，一次引擎升级会打坏成千上万个自制关；没有版本，就没有开放。

### 决策八：发布分档

| | 官方课程 | 社区内容 |
|---|---|---|
| 门禁 | 审计 + 盲玩 + 人评审 | 审计清零 |
| 质量 | 评审保证 | 游玩数据、评分 |
| 可组合 | 可被社区引用、改编 | 可改编官方关、组装成自己的课程 |

### 决策九：领域层产品化

**决定**：领域仍是代码，但要有：
- **机制目录**：数据流电路、逐步机器、逐拍总线、框、词序条、填表、参数台、纠错/修正玩法——各自适合什么专题，一张表，放在手册第 6 节；
- **domain 脚手架**：按契约生成空壳（值、注册表、世界、`validate`、关卡界面、词汇表、游戏描述），agent 或工程师只填实现；
- **契约测试**：一个 domain 装进去，kit 的通用检查、studio、MCP 自动能用。

### 决策十：现有游戏是原型，基础设施先完整

**决定**：现有七款游戏的关卡是原型，没有打磨过，不再在它们身上重构、打磨或重新编排。它们只做两件事：证明基础设施能承载一个专题，以及给各阶段当测试夹具（操作集、迁移生成、盲玩 harness、studio 都先在它们上面跑通）。基础设施（第 6 节阶段 2–6）全部完整以后，再按专题用流水线从头重做、重新编排这一系列游戏，不抱着原型改。

**理由**：原型的关卡设计本来就要重做；在它上面保持「玩家看到的一模一样」的重构，花的是验证原型的成本，换不来更好的游戏。基础设施做完，重做一款游戏的成本才会降下来，审计、盲玩、studio 也才能在重做时真正约束质量。

### 决策十一：元件是内容，引擎资源是领域

**决定**：一款游戏的原始元件定义在它自己的 `parts.json` 里（手册第 6.9 节）：输入输出的口、设置（六种内核控件：下拉框、数字、拖拉条、小按钮组、开关、自定义）、运算（一行 ASCII 表达式，只调用领域的引擎资源）和三面视图（桌面卡片、手机格位、详情），全部是数据，studio 能直接改，`check` 能查。领域只给引擎资源（词汇表的 `op` 种类）和内核画不出来的自定义控件（`widget` 种类）。

**理由**：元件的口、名字、默认值、哪几个设置、卡片上画什么，都是课程设计的一部分，以前却写在领域代码里，课程设计者改一个默认值或一个按钮的字也要改代码，各领域的设置界面也各写一份。基本运算才是真正要审查的代码：它决定值怎样算、出错怎样说。这样分开以后，元件按游戏隔离也落在文件上：同一个领域的两款游戏各有自己的 `parts.json`。

**边界**：有状态的元件（寄存、跨拍保存）、关卡给的节点、框要等内核给出对应的资源形状再搬进 `parts.json`；在那之前它们仍是领域代码。

## 4. agent 流水线

```
课程资料 → 知识点 → 课程蓝图 → 蓝图审计
        → 关卡规格 → 规格审计 + 参考解运行 + naive 解失败 + 教学 lint
        → 文案 → 文案 lint + 术语链接
        → 变更集进评审队列（官方）或直接发布（社区）
```

每一步的产物都是内容层的数据；每一步失败都定位到一条规则；每一步的修改都是操作集里的操作。

**流水线从知识点出发，不从元件出发**（手册第 1 节「玩的过程就是学的过程」、第 4.1 节）。《视觉实验室》第一版（计算机视觉第 0、1 章，59 关）是按旧蓝图做的：蓝图的「想法」可以是任何东西，审计又要求一关一个新想法、每个想法后面有练习，于是 agent 给每块元件编一个想法（「常数」「取整」「取较大值」各占一关，引言是同一句套话），同一块板、同一段话在几关里重复，判断题看题面的字就能答，参数台拖一个旋钮到变绿就过，文案短到说不清问题。闸门全过，教的东西却很少。改法是改流水线而不是改这款游戏：蓝图先从课程材料列出知识点（术语、出处、撞上的墙、纠正的错误），每个 slot 写出玩家要回答的问题和思维链；审计不再让元件充当知识点；关卡和文案的闸门加上教学 lint（重复的板、重复的话、拖到变绿的实验台）和术语链接；《视觉实验室》按新的流水线从蓝图重做。

实现见手册第 7.2 节（`kit/pipeline/`，`npm run pipeline`）。在蓝图和关卡规格之间多了一步「领域」：蓝图向领域提的需求（决策三的需求通道）由工程师实现或拒绝并写明理由，内容 agent 不写代码。一步失败时往回走：关卡设计 agent 停在蓝图做不到的地方，它的报告成为课程设计 agent 下一次的输入（`--from`）；评审 agent 的发现按它归属的那一步交回去；人的退回意见也一样（`comment`）。在网络第 1 代上，往回走是常态而不是例外：蓝图改了五次（两次因为领域的回答、一次因为关卡设计停下、两次因为评审），关卡写了四遍，文案三遍。

## 5. 承认的边界

- 内容层做不到百分之百无代码：真的只能用代码表达的测试生成和判定留在领域层，以名字暴露。这是边界，不是失败。
- 词汇表的粒度是本方向唯一真正难的决定，没有办法事先证明对；只能在一个领域上试，按「屏幕上能指着说的概念」校准。
- 审计抓不到的只有文案好坏和难度；前者靠人与社区，后者靠盲玩，都不是精确的。
- studio 的通用控件集是内核的固定开销；每种新的值类型都要内核加一个控件。

## 6. 实施顺序

每个阶段写明完成标准；做完就从这里删掉。

**阶段 5 · agent 流水线端到端（余下：人评审；盲玩暂停）**
流水线已经是基础设施（手册第 7.2 节，`kit/pipeline/`）：每一步一份 brief、一道闸门，每一步的产物经操作集写进内容，记录在游戏的 `pipeline.json`。它在全新专题计算机网络上从头走了一遍：《从一根线开始》第 1 代「一根线」的蓝图、关卡、文案、百科全部由 agent 写成，每一处修改都在修改日志里（`games/network/changes.jsonl`），审计清零，评审跑了两轮（发现都已修掉或记下由哪一次修的），盲玩跑了三局（一局量的是改版前的游戏，已退下）。走的过程和闸门抓到的东西见《从一根线开始》的设计文档。按人的要求在这里停下，游戏原样交给人看。还剩：
- 蓝图写在知识点模型之前（「想法」没有术语和出处，slot 没有问题和思维链），按新的 schema 不再合格：补上知识点、问题和思维链，再按教学 lint 和术语链接过一遍关卡和文案（教学 lint 现在在这款游戏上只报出一处重复的提示）。
- 人在 studio 里把这一章审完、改完、玩完（studio 的「变更」页签里是修改日志，可以逐个看、逐个撤销；退回给 agent 的意见用 `npm run pipeline -- network comment`）。这款游戏每一次预览要跑整款检查，约 14 秒。

完成标准：进了评审队列，人在 studio 里修订过这一章，审计清零。

## 7. 开放问题

- 词汇表粒度：《状态之图》上定出了第一版（`kit/domains/table/vocabulary.js`），《证明完毕》上成立（`kit/domains/logic/vocabulary.js`）：规则即元件是元件项，框由 kit 给，玩家证出的引理、拼出的门、证出的等式是内容里的数据（陈述、口），不是词汇项；句子是领域记号的文本，存档迁移的几十个一次性函数合成十来个带参数的迁移项。《视觉完备》上同样成立：测试场景、目标图、图像生成器、约束各是一种项，一关按名字选项、填参数（`kit/domains/image/vocabulary.js`）。机关台抽成通用参数台以后也成立：模拟是领域的一个模型项，旋钮、情形、步骤、按钮、目标（对模型算出的量的限制）和版面全是数据，画面是一个封闭的显示项集合（内核给曲线、像素行、读数、目标、步骤……，领域补拼不出来的图和交互）。留下的问题是显示项的粒度：领域的显示项（暗箱侧视图、霍夫累加器、封面配点……）多半一个模型一项，是不是该再拆成更通用的「可拖动的点」「栅格图」，要等第二个有参数台的专题来定。
- 盲玩 agent 的能力与真实学习者的差距：通过率高不等于人学得会；需要少量真人数据校准。基线说明了差多远：五款原型的前 9–12 关，LLM（claude-sonnet-5-5）几乎都一次通过、不要提示，每关十几秒。它熟悉逻辑门、德摩根律、动态规划和图像滤波，新手要学的正是这些；它读得懂一句话的元件说明，新手常常读不懂；它不看图，文字版的画面（图像是一格一格的数）对它反而更好用。所以它的突起是「这一关缺了什么」（`difficulty-spike` 在这上面有用：一关同时要三件事、反馈说不清 0 和「否」、引擎丢了设置），不是「这一关对人难」；平坦的曲线不说明新手也平坦。校准要几个真人走同样的 harness（`--player human`）或页面里的同一种记录，再比两条曲线的形状；另一条路是给 agent 加限制（更小的模型、不许用外部知识、只许按提示走），看它的曲线是不是更像人。
- 社区内容的改编与署名：改编官方关、组装课程时，蓝图审计（抽象链、分支）对拼装出来的课程还能不能成立。
- 内核需求通道的优先级：谁来排序，按什么排。
