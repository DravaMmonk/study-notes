# 开发方向决策书：从样板游戏到创作平台

本文记录项目下一阶段的方向和理由。它只定方向、边界和顺序；落到每一条具体规矩时，写进 `games/DESIGN.md`、领域的词汇表和 schema，本文不重复。做完的阶段从「实施顺序」里删掉，方向变了就改本文。

---

## 1. 终点

一套面向 agent 的开发套组、平台和 MCP：输入一套课程体系或一个专题，输出一款上手即玩的类图灵完备游戏——从零门槛起步，一路到专业深度和前沿知识，关卡设计符合 `games/DESIGN.md` 的全部规则，关卡有技术含量。

同时，人能轻松参与：任何 AI 生成的实质内容（课程结构、关卡、文案）都能在一个页面上审核、修订、试玩；修订不需要写代码。

## 2. 现状判断

**已经有的**：一本设计手册（原则、课程结构、关卡规格、审计规则、引擎分层、作者流程）；修改内容的操作集，带修改日志、命令行和 MCP（手册第 7 节）；一个共享 kit（求值、封装件、框、逐步机器、逐拍世界、两套电路编辑器、外壳、地图、存档、蓝图文本）；若干领域模块；七款原型游戏（决策十）。阶段 0+1 已经做完：内核有内容层的契约（schema、词汇表、数据游戏的加载和检查），七款游戏的文件夹里只有数据；封装件跑学习者的电路；`unused`、`bare-intro`、`idle-idea`、`bypass` 在所有游戏打开并清零；课程的形状是数据，`npm run deps` 画出元件依赖图；机关台是一个通用参数台（`kit/shell/bench/`）；电路关是一个内核界面（`kit/shell/CircuitLevel.jsx`）。领域有了写下来、测得出的契约（手册第 6.3 节，`kit/engine/contract.js`，`npm test` 对六个领域、七款数据游戏机械地查）和机制目录（手册第 6.5 节）；`npm run new-domain` 从模板（数据流电路、逐拍总线）生成一个能玩的领域和入门游戏，`npm run new-game` 从领域的入门游戏开新游戏。阶段 6 已经做完：逐拍总线的模板从 `kit/domains/can` 抽出（`kit/scaffold/tick-bus/`），网络专题的 `net` 领域从它生成，契约测试一次通过；路上修了脚手架的三处毛病（游戏文件夹里先有设计文档时拒绝生成、生成失败时留下半个领域、`scaffold.test.js` 嵌在测试运行里跑生成的领域测试时总是退出 0，查不出失败）。阶段 3 已经做完：盲玩 harness 是内核（`kit/engine/play/`，每个领域在 `domain.js` 给一个 `play` 钩子），只给玩家看到的东西、照游戏的规矩判尝试，一局像一份存档，记录是内容里的数据（`playtests/`），`check` 列出审计面板并跑 `difficulty-spike`；五款原型各有一局 LLM 盲玩的基线，harness 指出了两处突起：《状态之图》「走不到的路口」一关同时要三件事（难度曲线，写进了它的设计文档）；《车在说话》1-5 是引擎的毛病（蓝图导入丢了常数的值，已修；量到它的那一局只留在 git 历史里，因为它量的是一个已经修掉的错）。阶段 4 已经做完：studio（手册第 6.7 节，`npm run studio`）是操作集上的一层皮，不认识任何领域——树上拖关就是 `level.move`，表单全部由 schema 和词汇表生成，板在表单里画成无头的 SVG、在游戏自己的电路编辑器里改，试玩的是待定变更集留下的内容，审计栏随每次改动重算（连同盲玩记录），评审里看操作和字段级 diff，再应用或撤销；它和 MCP 用同一组工具（`kit/engine/ops/tools.js`，经开发服务器的 HTTP 桥），MCP 的 `render` 因此也能出 SVG，领域可以给一个无头的 `scene`。在《软件工厂》第 1 章的副本上，读完全部文案、改文案、改测试、挪关、在电路编辑器里改参考板、看审计变红又清零、嵌入试玩、应用、撤销，都在浏览器里走通，不写一行代码。阶段 6.4 已经做完：一关是一串任务（`kit/engine/tasks.js`，手册第 4 节），只有一个任务的关就是普通的关；任务有整款游戏里唯一的 id；存档换成按任务 key 记的新形状（手册第 2 节，旧存档不读），任务在关内插入、换位置、挪进别的关、几关合成一关都不用迁移，`level.merge`、`level.split` 和领域的存档迁移项、`tasks` 钩子都已删掉；两个领域模板和 net 领域是这个形状，《从一根线开始》经操作集换了过去。studio 的主区是游戏自己的页面（手册第 6.7 节）：外壳标出画面上是内容字段的那几块，点一下在右边的侧栏里改（和原来的表单同一套控件），加任务、提示、引言、测试都在它出现的地方点「+」；没有画面位置的字段在「字段」页一项一行，点开也在侧栏改。在《从一根线开始》1-1 的画面上加一个任务、改它的目标、改进线的延迟、加一个测试，经操作集落盘，审计清零。

**缺的**，按对终点的影响排：

1. 领域模块仍是每个专题的真实成本：脚手架有数据流电路和逐拍总线两个模板，逐步机器、参数台的新领域要从例子领域抄起；网络第 1 代的领域从模板生成以后又改写了约一千行（线、格式、取用的队列、要的东西），领域需求通道是流水线里最慢的一环（第 4 节）。
2. 经验性验证只有 LLM 的读数：盲玩 harness 有了，但基线是每款一局 LLM 盲玩，难度规则要 5 局才算数；没有真人数据，LLM 和新手的差距也还没校准（第 7 节）。几种玩法 harness 还不支持（手动玩法、证明板、句法，`games/DESIGN.md` 第 6.6 节）。
3. kit 自身不统一：原型的领域里一关还是「一种玩法（`kind`），可选再拆几段 `tasks`」两种形状，studio 画面上标不出领域自己画的部件（参数台的旋钮、表格的世界）；部分封装件仍是内置实现；电路关界面已在内核（`kit/shell/CircuitLevel.jsx`），《视觉完备》《状态之图》的旧界面等按专题重做时换上（《视觉完备》的电路关因此还没接上最后一次运行）。
4. 设计文档与代码的一致性靠约定。
5. 没有版本与发布形态；studio 的评审页签还没有写驳回意见的入口（流水线那一头已经有了：`npm run pipeline -- <游戏> comment`，意见交给那一步下一次跑的 agent）。

## 3. 决策

### 决策一：三层架构，内容层是纯数据

```
内核层   kit/engine, kit/circuit, kit/shell    机制与界面，所有游戏共用
领域层   kit/domains/<x>                        值、引擎资源（基本运算）、世界、判定、画法；一个专题一份代码
内容层   games/<x>/                             元件定义、课程蓝图、关卡规格、文案、百科；全部是数据，不含代码
```

**决定**：内容层不含任何可执行代码。测试数据、诊断谓词、引言插图、通关后的面板，一律改为**引用**：领域层暴露有名字、带参数 schema 的生成器和谓词，内容层只写 `{ "名字": 参数 }`；无法生成的物化成数据。参考解和 naive 解用已有的 ASCII 蓝图文本。

**理由**：只有纯数据的内容才能被 schema 校验、被 diff、在页面上改、在 git 里审、被 agent 安全地读写；也只有纯数据才能开放给不受信任的创作者。

**内容层分三种产物**，粒度从粗到细，各有审计：

| 产物 | 内容 | 审计 |
|---|---|---|
| 课程蓝图 | 机体阶梯、每代能力、原始元件清单、元件依赖图、每个机制「第一次非它不可」的位置、练习簇、并行组 | 不依赖的就分支、抽象在上升、机制放在被核心用到的地方、基础元件最少 |
| 关卡规格 | 目标、传感器、测试、参考解、naive 解、新带来的元件、托盘、预置、任务段、挂靠 | 现有 `audit` 全部，`idle-idea`、`bypass`、`bare-intro` 全开 |
| 文案与百科 | 中英两面、链接、词条、修订 | 现有 `check` 的文案检查，加禁用词与长度 lint |

设计文档保留，只写理由与取舍；凡是能检查的事实从数据来，不再手抄。

### 决策二：创作层的词汇表是封闭的

**决定**：一关、一款游戏只能由内核和领域**已经提供**的东西组合而成。每个领域给出一份**词汇表**（domain vocabulary）：值类型、原始元件、世界类型、测试生成器、判定谓词、玩法、机体能力，每一项带参数 schema。创作者能写的全部，就是在词汇表里选项、填参数、接线。词汇表里没有的，不由创作者绕路实现，而是提交一条结构化需求进内核队列。

**理由**：这是人机协作和开放创作成立的前提。词汇表封闭，内容才可能无代码；内容无代码，沙箱才是结构上成立的，不靠审查；审计才能覆盖创作者能做的一切。

**词汇项的粒度标准**：一个词汇项对应玩家在屏幕上能指着说「那个东西」的一个概念——一种元件、一种世界、一种玩法、一种测试的形状。满足这条的进词汇表；只有实现细节能区分的，合成一项加参数。太粗创作者表达不出，太细就是变相写代码。先在最成熟的领域（《状态之图》）上定标准，再推到其他领域。

**词汇表 v1 的来源**：从现有样板游戏提炼。规格现在做的每一件事，凡是靠临时 JS 的，都改成词汇表里一个有名字的项。提炼完，v1 自然成形，内容层去代码化也同时完成。

### 决策三：两级权限

| | 内核 | 创作 |
|---|---|---|
| 谁 | 核心工程师、管理员、高级别 AI | 玩家、普通 AI、课程作者 |
| 产物 | 代码：引擎机制、领域模块（引擎资源、世界、判定）、词汇表 | 数据：元件定义、课程蓝图、关卡规格、文案 |
| 门禁 | 单元测试、契约测试、代码审查、版本号 | schema + 审计 + 盲玩，机器自动放行 |
| 能破坏什么 | 一切 | 只能做出一个不好玩的关 |

**决定**：内核层权限收紧，只接受走完整门禁的代码变更；创作层不设人工门禁，审计清零即可。内核的演进由创作层的需求通道驱动：创作者遇到「词汇表里没有」，产出一条结构化需求（要一种机制、一个元件、一种玩法），内核按队列实现，词汇表随之增长。

**理由**：引擎会一直更新，但更新的权限必须和创作权限分开，否则开放创作就是开放破坏。需求驱动的扩展也比凭空扩展更不容易做出用不上的机制。

### 决策四：修改只有一套操作集

**决定**：对内容层的每一种修改都是一个结构化操作：改字段、加关、删关、移动挂靠、拆合任务、改元件的解锁关、重命名 id、拆出引入关、合并几关为一关的任务段……每个操作自带：
- schema 校验和受影响的审计规则；
- 存档迁移的自动生成（重命名、推出新解锁、新插入的前置关标通过、`merge`）——开放之前不做：开发阶段存档不迁移，存档记着谜题的 stamp（`kit/engine/stamp.js`），和内容对不上就清空（手册第 2 节）；
- 一条可回放、可撤销的日志。

MCP 的 `modify`、studio 的每个编辑按钮、CLI 三者只是这套操作集的三层薄皮；人和 agent 改的是同一份数据，走同一条门禁。

**理由**：手写迁移已经是手册里记录的坑；agent 会频繁重排，迁移必须自动。一套操作集也是人机协作不互相踩的唯一办法。

### 决策五：studio 是 schema 驱动的通用编辑器

**决定**：studio 不持有领域知识，不含领域代码，自由度就是词汇表的自由度。它由四块组成：
- **树编辑**：课程树照地图的排法列出（主线、并行组的分支、专题、挑战），拖动一关就是 `level.move`；分支、挂靠的问题由审计栏就地报出；
- **关卡编辑**：字段按 schema 生成表单；值的形状映射到 kit 里一小组**通用控件**（中英文字和链接、可搜索的选项、数值、表格和矩阵、逐拍的波形、列表、电路板），形状说不清的地方词汇表在 schema 上写声明式的提示（「这是矩阵」「这是逐拍的值」「数一次加减多少」「这个字段归哪一段」），不写控件；
- **嵌入式游戏**：改完即玩，运行结果和审计并列；
- **审计面板与变更集评审**：`check` 的结果按关、按规则常驻，改一处立刻重算；agent 的每次产出是一个变更集，附审计结果、盲玩统计和 diff，人可以批准、就地改、或驳回并写意见，意见回到 agent 的下一轮输入。

**边界**：控件是代码，但它们是 kit 的通用控件，由内核维护；领域层不再有「给 studio 的编辑器」这一项。一种新的值形状要内核加一个控件，只在有内容用它时加（现在没有按像素写的图，所以没有图像控件）。

### 决策六：验证闭环

**决定**：三道门，依次是：
1. **审计**：schema、蓝图审计、规格审计、文案 lint，全自动，创作层发布的唯一硬门禁。
2. **解空间信号**（决策十五）：变异得分、短解搜索是门禁，解的多样性和搜索工作量是报告。盲玩（手册第 6.6 节）暂停；恢复时只用来校准这组信号，不做门禁。
3. **人评审**：只对官方课程；在 studio 的变更集视图里做。

**理由**：审计抓不到文案好坏和难度；盲玩能抓难度；文案好坏留给人（官方）或游玩数据（社区）。

### 决策七：版本与迁移

**决定**：内容声明它依赖的词汇表版本；词汇表只增不删，删改必须带迁移；kit 独立打包、语义化版本。官方课程的存档迁移由操作集生成；社区内容只保证在它声明的版本上可玩。

**理由**：开放给玩家后，一次引擎升级会打坏成千上万个自制关；没有版本，就没有开放。

### 决策八：发布分档

| | 官方课程 | 社区内容 |
|---|---|---|
| 门禁 | 审计 + 盲玩 + 人评审 | 审计清零 |
| 质量 | 评审保证 | 游玩数据、评分 |
| 可组合 | 可被社区引用、改编 | 可改编官方关、组装成自己的课程 |

### 决策九：领域层产品化

**决定**：领域仍是代码，但要有：
- **机制目录**：数据流电路、逐步机器、逐拍总线、框、词序条、填表、参数台、纠错/修正玩法——各自适合什么专题，一张表，放在手册第 6 节；
- **domain 脚手架**：按契约生成空壳（值、注册表、世界、`validate`、关卡界面、词汇表、游戏描述），agent 或工程师只填实现；
- **契约测试**：一个 domain 装进去，kit 的通用检查、studio、MCP 自动能用。

### 决策十：现有游戏是原型，基础设施先完整

**决定**：现有七款游戏的关卡是原型，没有打磨过，不再在它们身上重构、打磨或重新编排。它们只做两件事：证明基础设施能承载一个专题，以及给各阶段当测试夹具（操作集、迁移生成、盲玩 harness、studio 都先在它们上面跑通）。基础设施（第 6 节阶段 2–6）全部完整以后，再按专题用流水线从头重做、重新编排这一系列游戏，不抱着原型改。

**理由**：原型的关卡设计本来就要重做；在它上面保持「玩家看到的一模一样」的重构，花的是验证原型的成本，换不来更好的游戏。基础设施做完，重做一款游戏的成本才会降下来，审计、盲玩、studio 也才能在重做时真正约束质量。

### 决策十一：元件是内容，引擎资源是领域

**决定**：一款游戏的原始元件定义在它自己的 `parts.json` 里（手册第 6.8 节）：输入输出的口、设置（六种内核控件：下拉框、数字、拖拉条、小按钮组、开关、自定义）、运算（一行 ASCII 表达式，只调用领域的引擎资源）和三面视图（桌面卡片、手机格位、详情），全部是数据，studio 能直接改，`check` 能查。领域只给引擎资源（词汇表的 `op` 种类）和内核画不出来的自定义控件（`widget` 种类）。

**理由**：元件的口、名字、默认值、哪几个设置、卡片上画什么，都是课程设计的一部分，以前却写在领域代码里，课程设计者改一个默认值或一个按钮的字也要改代码，各领域的设置界面也各写一份。基本运算才是真正要审查的代码：它决定值怎样算、出错怎样说。这样分开以后，元件按游戏隔离也落在文件上：同一个领域的两款游戏各有自己的 `parts.json`。

**边界**：有状态的元件（寄存、跨拍保存）、关卡给的节点、框要等内核给出对应的资源形状再搬进 `parts.json`；在那之前它们仍是领域代码。

### 决策十二：笔记版是同一套内核上的另一款游戏，内容各自编排

**决定**：笔记里的交互是一款 `mode: "notes"` 的数据游戏（手册第 12 节），一门课一款（第一款 `games/comp90086/`），和这门课的游戏共用领域与内核，内容各自编排：一关对应一个笔记词条，不画关卡树、不设解锁，检查只跑内容正确性，不跑编排审计。每个知识点按核心思想选交互原型，拼电路只是其中一种。笔记里原有的装置插图在对应词条做成笔记关时换掉。

**理由**：游戏的任务按游戏的顺序写，文案和前置都假定玩家刚从上一关过来，直接嵌进笔记会断；另写一份插图又会重复内核已有的运行、判定、显示和 studio。分成两款游戏，笔记版照用操作集、`check`、studio 和存档，编排却只服从笔记的段落。编排审计查的是「一台逐层长大的机器」，笔记版天然不满足，所以不跑，而不是把规则改松。

**边界**：笔记版不教游戏教的东西（逐层搭机器），游戏也不为笔记的段落拆关；两边的同一个知识点用百科词条 id 互相链接。浏览器里跑不动的模型（注意力、CLIP、SAM、扩散）只能用预先算好的数据，交互不接受任意输入。

### 决策十三：运行是确定的，解就是录像

**决定**：一次判定是 `(内容版本, 任务, 板)` 的纯函数。元件求值、世界、参数台模型里不读时钟、不用未播种的随机数；要随机的由求值上下文给种子（测试序号加节点路径）。契约测试查领域的求值代码里没有 `Math.random` 和 `Date.now`。玩家交的解就是蓝图文本（参数台是一组旋钮值，填表是一张表）：任何人、任何机器拿到它，都能无头地重判一遍，得到同一个结论和同一个代价。

**理由**：这是 H5 魔塔的「录像」思路落到本项目上的样子：魔塔记下一串操作，服务器重放它来承认成绩；这里连操作都不用记，板本身就是全部输入。有了它，下面四件事不必各自发明：服务器不信任客户端也能承认成绩和排行（决策十六）；检查按任务缓存（哈希不变就不重跑）；变异审计和解空间搜索（决策十五）能批量跑；每一次尝试都是一条可以重放的数据，真人数据和 agent 数据是同一种东西。

### 决策十四：发布是不可变的包，存档跟着任务走

**决定**：
- 一次发布是一个包：`content.json` 加一张清单（内容哈希、词汇表版本、内核格式版本、来源的变更序号、作者）。包按哈希寻址，发布以后不改；一款游戏的「当前版」只是指向某个包的指针，可以前进，可以退回。
- **内核格式版本**是一个整数，管内核自己定的全部格式：蓝图文本、元件式子、`parts.json`、`blueprint.json`、修改日志的行。规则和词汇表一样：只增不改，删改带迁移。运行时声明它读得了的范围。
- 引擎不随内容打包：所有游戏跑同一份运行时。这是和魔塔样板最大的不同：每座塔自带一份引擎，引擎修了错，旧塔不受益，平台要永远兼容每一版。只增不改的格式加上兼容语料（决策十七），让旧内容在新运行时上继续成立。
- 存档按任务记，每个任务的板旁边记这个任务的谜题哈希（谜题区和测试区字段，加它用到的元件定义和它依赖的封装件的板）。打开时逐个任务比：哈希没变的板和通过记录留着，变了的只清这一个任务和依赖它的下游。整款游戏一个 stamp 的做法退下。

**理由**：没有不可变的包，就没有「这个成绩是在哪一版上打出来的」，也没有可以退回的发布；没有按任务的哈希，官方每修一关，所有玩家的进度清零一次，开放以后这不可接受。两样的代价都在今天最小：存档本来就不迁移。

### 决策十五：质量信号从解空间里算，接替盲玩

**决定**：审计多一组只看解空间、不看教学意图的信号，对所有领域成立，放在内核：
- **变异得分**：对参考板做机械变异（删一个元件并短接、换一个设置的取值、交换两个输入、换一个同口型的元件），跑这个任务的可见测试和隐藏测试；活下来的变异体是测试没有区分的错解，按 `元件@关卡` 报出。「空板必须不过」「一根线直通必须不过」是它的特例，并进来。纠错关的出题也用同一组变异算子。

原先还列了短解搜索、解的多样性和搜索工作量三项，去掉了：空板、直通和 `drop` 变异已经盖住「比参考解短也能过」里实际出现过的情形；穷举只能用元件的默认设置，而参考解大多靠具体的常数，搜得到的很少，代价却随元件数成倍涨。难度曲线先用已有的数（参考解的元件数、这一关带来几个新想法），有了游玩数据再换成真的。

变异得分是社区内容发布的门禁和官方内容的闸门，形状是「活下来的每一个都认过」，不是一个比例：等价的变异体机器分不出来（见阶段 6.8）。它也是 agent 选候选的依据（第 4 节）。决策六的第二道门从盲玩换成这一组；盲玩恢复时只做校准，不做门禁。

**理由**：盲玩的基线已经说明，LLM 熟悉要教的东西，它的通过率量不出新手的难度（第 7 节）；而它抓到的真问题（只接一根线就过关）恰恰是解空间的性质，可以不靠模型、确定地算出来。这组信号便宜、可复现、对每个领域一样，是唯一能在没有玩家的时候给出的经验性依据。它量不出文案好坏和「好不好玩」的全部，这一点不变（第 5 节）；真人数据仍然要（决策十八）。

### 决策十六：平台是静态的包加一层薄服务，MCP 就是 API

**决定**：
- **游玩是静态的。** 运行时和包都是静态文件，放在对象存储和 CDN 上；不登录也能玩，进度在本机。这一点照魔塔：每个游戏有自己的地址，打开就玩。
- **服务只做四件事**：账号；目录（游戏、标签、评分、评论）；发布（收一个变更集，跑门禁，产出包）；承认成绩（收一份解，用和页面同一份内核无头重判，记下代价）。内核本来就能在 node 下跑，判定代码只有一份。
- **创作只有一个接口：操作集。** 托管的 studio 和远程 MCP 是它的两层皮，和今天本机的 studio、MCP 是同一组工具，只多了认证。人和 agent 走同一道门，没有只给人或只给 agent 的写入口。
- **存储是接口（到阶段 7 再做）。** 打开一款游戏、原子地写一个变更集、追加日志、取 head：`ops/workspace.js` 收成这四个动作，文件系统是第一个实现，平台上换成数据库或 git 后端。`games/games.js` 里随内容变的字段（关卡数）挪进数据，操作集不再用正则改源码。
- **每个操作声明级别（到阶段 7 再做）**（创作 / 内核，决策三）：关卡、任务、文字、百科是创作级；元件定义、课程形状里牵动词汇表的、词汇表版本是内核级。`modify` 按调用方的级别拒绝。
- **每个变更集带着是谁**：人或 agent，agent 写明模型和它跑的是流水线的哪一步。署名、改编链、「agent 写的内容被人改掉多少」都从这里来。

存储接口和操作级别都等第二个使用者：现在只有文件系统一个后端、只有本机一种调用方，先抽接口、先标级别，写出来的是没人读的配置。读写盘已经只在 `ops/workspace.js`、`ops/log.js` 和 `content-node.js` 三处，到时是局部改动。「带着是谁」现在就有用，已做（变更集的 `by`，`npm run op -- <游戏> log` 按作者统计，并数出 agent 写的文件有多少后来被人改过）。

**理由**：内容是纯数据、判定是纯函数，所以平台最贵的两样（跑用户的代码、信任用户的成绩）都不存在：不需要沙箱，不需要常驻的游戏服务器。魔塔把塔做成整个项目文件夹，塔里能写任意脚本，换来的是无限的表达力和永久的兼容负担；这里反过来，表达力只经需求通道增长。服务薄，一个人加若干 agent 就运营得动。

### 决策十七：内核是一个有公开面的包，发布前过兼容语料

**决定**：
- （到阶段 7，kit 离开这个仓库时再做）`games/kit` 自成一个包（npm workspaces），有自己的依赖、命令和版本号；笔记站是它的一个使用者，不再是它的宿主。
- **公开面写成清单**：领域能导入的内核模块。导入边界进 lint：领域不引用别的领域，内核不静态引用领域，领域不引用公开面之外的内核文件。公开面之内的改动按语义化版本走，之外随便重构。
- **公开面有类型**（和自成一个包一起做）：领域契约、`CircuitScreen` 的适配面、引擎资源的签名写成 JSDoc 类型，对 `engine/` 和 `shell/` 开 `checkJs`；lint 和类型检查进 `test-kit.yml`。
- **引擎资源声明值形状**（`scalar`、`grid`、`bits`、`ticks`、`list`）：式子检查、接线拒绝、可用的显示方式都从这一份签名推出。有状态的资源（寄存、跨拍保存）在同一处定形状。签名先有了一项：次序无关的输入（`symmetric`）。值形状还没做，原因写在这里免得被当成遗漏：用引擎资源定义元件的领域现在只有 `linear` 一个，它的资源是多态的（加法收向量也收矩阵），口没有类型，接错了是运行时在卡片上说明原因；改成接线时拒绝，改的是玩法，要有第二个这样的领域、和有状态的资源一起定。
- **兼容语料**：kit 的代码变更，除了单元测试，再对全部已发布的包跑一遍 `check`。它是平台上的一个操作（`npm run check`、MCP 的 `audit`），开发游戏和开发内核的人从平台上跑，不进 GitHub 的 CI：重放一款游戏的耗时随内容增长（《车在说话》到 152 关时，带变异得分的一遍在 CI 上要 47 到 75 分钟），推送不该等它，也不该替平台做它。发布运行时的新版本时它是硬门禁，由平台执行。单元测试仍然不认识任何关卡：语料是另一个命令，另一个环节。
- **扩展点都是登记表**：机制、显示方式、设置控件、操作、审计规则各一张，加一项是加一个文件并过它的契约测试。只有一个领域用过的机制（框、参数台、纠错与修正、词序条）标成试行，第二个领域接入之前不承诺接口。
- **上限只降不升**：样式字面值和重复代码之外，再给每个领域的行数、适配钩子的个数、单款检查的耗时设上限。

**理由**：「内容检查不进 CI」防的是改关卡牵动测试，对内容编辑成立；kit 的代码变更也不靠 CI 重放游戏，靠的是平台上的兼容语料：内核的一次重构弄坏某款游戏的参考解，要到平台下一次检查这款游戏、或者改内核的人自己跑语料时才发现，运行时发布前的那道硬门禁是兜底。开放以后，运行时的每一次发布面对的是成千上万个别人的包，兼容语料是决策七那句「没有版本就没有开放」的执行办法。新领域的成本已经降到几百行（`calculus`、`linear`、`can`、`net`），靠的是电路底座这层公开面；把它写下来、锁住，这个成本才保得住。

### 决策十八：运营靠门禁、数据和 agent，不靠人工审核

**决定**：
- **官方课程**由流水线产出，人在 studio 里评审（决策八不变）。
- **社区内容**过了门禁（schema、审计、变异得分、短解搜索、文案的内容安全检查）就发布，不排队等人。从最小的一环开始：玩家在一关里「改编这一关」，用这款游戏现有的元件做一个变体，得到一个地址。然后是组装成课程，最后才是新游戏。
- **改编保留来路**：一个包记着它改自哪个包；署名和改编链由此生成。
- **成绩和排行**按任务、按代价度量（元件数、步数、计算量），只承认服务器重判过的解（决策十三）。解可以公开，也可以通关后才看得到别人的。
- **游玩数据是第三种信号**：每次尝试一条记录（任务、板的哈希、结论、第一个没过的测试、用时），本机先记，愿意才上传。它校准决策十五的难度估计，也替社区内容排序（通过率、放弃点、评分）。
- **agent 是一等的作者。** 作者带自己的 agent 经远程 MCP 创作，费用在作者那边；平台自己只为官方课程跑流水线、为所有人跑门禁和重判。「跑一步」是接口，`claude -p` 是它的一个实现，换模型不改流水线。
- **需求通道由 agent 分拣**：结构化的需求（要一种机制、一个引擎资源、一种显示方式）去重、归并、按有多少内容在等它排序；实现走内核门禁（单元测试、契约、兼容语料、代码审查），可以由内核级的 agent 写、人审。
- **比赛**：给定一个领域和一套词汇表，限期做关，按游玩数据和评分排名。它同时是内核的压力测试：比赛里集中冒出的需求最能说明词汇表缺什么。

**理由**：魔塔广场的经验是，一个引擎、一个不写代码的编辑器、一套可验证的计分，加上比赛和社区，就能让作者自己长出几千个游戏。它那个年代审核和答疑靠人和群；今天这两样正是 agent 做得了的，前提是门禁是机器能跑的、内容是机器能读的，这两条本项目已经有了。平台的人只做三件事：内核的代码审查、官方课程的评审、裁决门禁判不了的争议。

### 决策十九：形式封闭，内容开放，机制受控

**目标**（2026-11-12 定）：把以前要靠看书反复琢磨的生涩知识，变成一种大体统一、有自己特色、对入门者有吸引力、值得用它学很多门知识的游戏形式。拼电路是核心玩法，但不是唯一的；价值在形式，不在某一种编辑器。

**决定**：在通用引擎（Godot）、单一类型的编辑器（H5 魔塔）和纯关卡编辑器之间，创作体验取魔塔和关卡编辑器（一种形式、只写数据、不写代码），扩展能力取引擎，但只开在一处、带契约。四圈：

| 圈 | 是什么 | 谁能改 | 怎么改 |
|---|---|---|---|
| 形式 | 学习的回路（下面五条）、判定的语义、外壳和交互、存档、地图、操作集、审计 | 内核 | 代码，改一处所有游戏一起变 |
| 机制 | 一种东西怎么造、怎么跑：数据流板、逐拍板、逐步机器、文本程序、词序条、参数台；值的种类、显示方式、引擎资源、世界 | 内核和受信任的贡献者（人或 agent） | 代码，守机制契约，过代码审查 |
| 内容 | 课程、关卡、测试、用资源拼出的元件、文案、百科、译文 | 任何人、任何 agent | 数据，经操作集，过自动门禁 |
| 游玩 | 解、改编、评分 | 玩家 | 蓝图、改编链 |

**形式的五条不变量**（每一款游戏、每一种机制都守，这是玩家认得出它的原因）：
1. **造东西，不答题。** 玩家交出的是一件能运行的东西；选择题、填空只做预测和辨析，不做主体。
2. **规格和测试就是目标。** 目标写成输入输出，失败给出具体的反例和第一处偏离。
3. **造出来的东西成为下一步的零件。** 抽象是奖励：通过的那件东西被收成一个零件，后面的关站在它上面。这条不限于电路：证出的引理是规则，写出的函数是调用。
4. **从很少的原始能力起步**，每关至多带来一个新想法。
5. **多解并存，可以比较。** 有代价度量的关，解可以按代价排。

**机制契约**（一种机制要交什么，交齐了就自动得到 studio、审计、变异报告、重判、排行、流水线）：产物有纯文本形式；有编辑器；有确定的运行（决策十三）；有无头的 `play`；有它自己的变异算子；有接口（下一条）。现在只有电路底座把这些收成了一处（`circuit-domain.js`），别的机制各写各的；契约写成代码以后，「加一种玩法」才是一件有边界的事。

**一个节奏，几种世界**（2026-11-12 改定，替换原先「几种玩法并列、下一种做文本程序」的写法）。全平台只留一个核心动作：搭一台机器。参数台、分析这些不造东西的玩法不再和拼板并列，降成同一个节奏的前半段：

1. **手做几次**：亲手调一个量、判几个案例、拆一个句子，得到直觉。
2. **搭一台替你做的机器**：用板搭出那条规则。
3. **机器在一大批情形上受检，通过后收成零件**，后面的关站在它上面。

一关的几个任务正好装下这三步。变的不是玩法，是机器所在的世界：

| 世界 | 机器在里面做什么 | 现状 |
|---|---|---|
| 一次流过 | 把输入变成输出 | 已有 |
| 一个结构 | 在每一格上跑一遍 | 已有（逐步机器） |
| 时间 | 每拍跑一遍，带记忆 | 已有（逐拍） |
| 会反应的模拟 | 机器的输出改变世界，世界下一拍喂回来 | 已有：`kit/engine/ticks.js` 的 `reacting`，第一个用它的是 `market` 领域 |
| 一批案例 | 对每个案例下判断，按正确率算 | 没有 |
| 对局 | 和别的机器同场 | 没有 |

需要「写出来」的地方用词序条：带类型的空位、点选填入，没有语法错误，手机上能用；它是板的另一种写法，不另成一种玩法。自由打字的文本程序不做。

**学是解谜，用是优化**（2026-11-12）。要学的知识是现成的、确定的，所以「学」的阶段每个任务都是谜题：几乎只有一个解，条件全摆在面前。策略层面的知识也这样学：规则由题目说出来，玩家把它搭出来。优化（尽量多挣、尽量少用）是学完以后的应用，只做成过关后的成绩或可选的挑战关，目标是挑战而不是学知识。落成三条：
- **过关条件是开始前就能完整读到的规格。** 一个测试要么是一行「这些输入 → 这些输出」，要么是一个写明了的终态；隐藏测试只防止把答案写死，不带来新的条件。
- **总量门槛不当闸门。** 挣到多少、用了几步，只做成绩和直方图。
- **引言和任务说清「搭什么」，谜题是「怎么搭」。** 策略不留给玩家猜。
前两条能查的已经在词汇表里：`market` 的测试只有「一行」和「一条街」两种形状，一行必须正好给出任务的每张牌，街没有挣钱门槛这个字段。第三条查不了，靠 brief 和评审。

**先造世界，再造世界里的机器。** 世界的规则对玩家不能是黑箱：让玩家先把世界一块块搭出来（每块一关，逐行规格），再搭在里面活动的机器，最后才把机器放进「会反应的模拟」里跑。模拟是谜题的收尾和回报，不是谜题本身。

**第一次检验：《看不见的手》**（`games/market`，`kit/domains/market`，经济学，五关）。第一版三关（手调价格 → 搭调价板 → 两家店）做错了：需求看不见，过关条件是「挣够一个数」，调价的策略要玩家自己发明，结果只有本来就会的人过得去。上面两段是从这次失败里定下的，重做以后是：

| 关 | 题目给出 | 玩家搭 | 过关 |
|---|---|---|---|
| 想买的人 | 需求的说法 | 想买 = 不要钱时想买 − 每涨一块少 × 价格，收成「需求」 | 逐行 |
| 一天的买卖 | 「需求」，取小 | 卖出、剩下、没买到 | 逐行 |
| 刚好卖完 | 一条街的三个数 | 先手定两条街的价，再搭出出清价格的算式 | 最后一天出清；逐行 |
| 往哪边调 | 规则原文 | 今天 = 昨天 +（没买到 − 剩下）× 0.25，收成「调价器」 | 逐行 |
| 看不见的手 | 读不到需求的街 | 把调价器接上；两家店、行情会变 | 最后一天出清 |

第三关的算式要知道整条街的需求，第四关的规则不需要：这一对比就是这款游戏要教的东西，最后一关让玩家看见它成立。做的过程中得到的：
- 记忆放在世界里，不放在板上：街市把「昨天的价格」当一张牌交给板，板只表达规则，这个领域没有寄存卡。
- 同一个领域里，任务可以活在不同的世界：逐行的任务跑一次，街上的任务逐拍跑（`CircuitScreen` 的 `once`）。
- 收入还显示在街的结果里，但不决定过关。
- 世界有自己的画面（`CircuitScreen` 的 `figure`，跟着当前这一拍；坐标图是内核的 `Chart`，领域只给配置）：每家店一张图，需求线、进货线，板给出的价格是需求线上的一个点，走过的点留在原处；行情一变，线挪开，点再追过去。逐行的任务也画同一张图，五关看的是同一个世界。
- 没解决的：可选的优化挑战关（比如「进多少货挣得最多」）还没有。

**第二次检验：《拆音》**（`games/signal`，`kit/domains/signal`，傅里叶变换，主线四关加一条三关的支线，2026-11-12）。检验的是和手册相反的一种编排：主线只做最抽象一层的概念，要用的复杂元件直接借给玩家（测音），它怎么搭、为什么成立放进挂在旁边的支线。做出来了，现有的闸门也过得了；主线能不能不靠讲解立住直觉，还没有人玩过，没有答案。内核分不清「借来的」和「自己搭的」，这一版用一个原始元件加 `withhold` 顶着，缺的几样（一个元件两个来源、搭出后替换、地图上的「点亮」、按关声明元件集合）记在它的设计文档里。这个问题定下来之前，「基础元件最少」和自底向上的规则不改。

**从别的游戏取什么**（都落在形式这一圈，所有游戏一起得到）：代价的直方图（Zachtronics：过关以后看见自己在所有人里的位置，这是重玩的理由）；一次运行就是一个链接（确定性使它不花钱：内容哈希加蓝图）；改编前必须自己通关（关卡编辑器的规矩，这里就是参考解通过加变异门禁）；蓝图的复制和分享（已有）。

**不做什么**：不给内容开代码口子（魔塔的插件脚本换来的是永久的兼容负担和无法自动验证）；不做没有可判定产物的题型（那不是这个形式，硬塞进来会稀释它）。

**理由**：玩家愿意用同一种形式学很多门知识，前提是换一门课不用重新学怎么玩，而且每一门都保持同样的质量下限。这两条都要求形式封闭。可是知识的形状各不相同，一种编辑器装不下，所以机制必须能长；让它在契约里长，新机制一出生就带着全套工具，也不会长成另一个游戏。内容全开放而且是数据，agent 才能大量地写、机器才能把关。封闭的部分越小越稳，生态才转得起来：内核的人只审机制这一圈。

### 决策二十：译文是独立的工作板块

**决定**：做游戏和做翻译分开。
- 一款游戏声明一种**基准语言**，内容里的文字只写这一种。做关卡、过门禁、评审，都只看基准语言。
- 别的语言是**覆盖层**：`games/<游戏>/i18n/<语言>.json`，按「文件加字段路径」对应一段基准文字，并记下它译自那段文字的哈希。基准文字改了，这一条就算过期，回退到基准语言并列进译文的待办；没有译文的地方同样回退。
- 译文有自己的操作（`i18n.set`）、自己的检查（链接和标记与原文一致、过期的有几条、覆盖率）和自己的流水线步骤，由人或 agent 做，不拦游戏的发布。外壳自己的用词同样分开。
- 现有的 `{ zh, en }` 两面一次性拆开：中文留在内容里，英文搬进覆盖层。硬切换。

**理由**：两面必填让每段文案写两遍、查两遍、评审两遍，改一个词要同时改两处，否则检查不过；agent 的用量翻倍，只会一种语言的作者被挡在外面。翻译的节奏和要求也和做关卡不同：它要整章一起读、要术语表、可以晚到。分开以后，内容的 diff 只有一种语言，加一种语言不碰任何关卡文件。

### 决策二十一：界面也分三层，领域不写组件

界面按内核、领域、内容分成三层，和决策十九的「形式封闭、机制受控、内容开放」是同一种分法：

| 层 | 界面上放什么 | 是哪种设计 | 谁把关 |
|---|---|---|---|
| 内核 | 部件：怎么画、怎么交互（电路屏幕、结果区、`views/plots` 里的场景部件） | 形式：这套游戏长什么样、怎么玩 | 内核的测试 |
| 领域 | 声明：这个世界里有哪些量，一个测试的场景是哪个部件、用哪些数据（纯数据和纯函数） | 机制：一门学科怎么建模成世界 | 契约测试 |
| 内容 | 拼装：每种值默认用哪种视图、每关显示什么、叫什么 | 关卡：教什么、按什么顺序 | schema 和检查 |

落成的：建在电路底座上的领域只交一份声明（`ui/screen.js`，或 `game.jsx` 里的一行），屏幕由内核按声明拼出来（`CircuitScreen.jsx` 的 `circuitScreen`）；场景按名字取内核的部件（`views/plots/scenes.js`）。一款游戏要优化界面时按这个顺序试：改内容里的拼装；给内核部件加一个选项；领域自写一个部件。第三种允许，但被计数（`engine/components.js`），第二款游戏需要时提进内核。颜色、字号、间距不进声明也不进内容，只用令牌。

**现状**（各领域自写组件的行数，`npm test` 只许降）：`market`、`calculus`、`linear`、`net`、`signal`、`unix` 和两个模板是 0；`can` 63（帧回放和纸上作答，内核还没有同类部件）；`syntax` 159，`agent` 324，`logic` 2119，`table` 2413，`image` 2849。

**先于底座写成的五个领域**（2026-11-13 逐文件盘点，共约 9500 行界面代码）：约 1600 行在重做内核已有的东西，约 1000 行是该提进内核的通用部件，约 600 行其实是数据，约 6300 行是没有拼板的学科玩法。所以它们的出路不是「迁到电路屏幕」，而是按玩法给内核补部件。按收益和风险排的顺序：

1. `image` 的六个值视图换成内核的（约 450 行，内核已有同名部件；`ValueView` 被六处引用，要对一遍尺寸和取值范围）。
2. 提进内核的小件：词序条编辑器的外壳（`logic`、`syntax` 共用）、手机数字键盘和滑杆、缓动钩子、地图插画的外壳（七个领域各写了一份）。
3. 格子场景部件：`table` 八种玩法里七种是在格子上直接操作，内核现在只有坐标图一种场景部件。这一步决定 `table` 能不能动。
4. `logic` 的三种拼板（证明、机器、门电路）换到电路屏幕：约 530 行，但它们是这三种玩法唯一的路径，要先给电路屏幕补它们用到而底座没有的东西。
5. `image` 的关卡屏幕自己管判题（隐藏测试、最好成绩、存档），换到电路屏幕会改变怎么判过关，放最后，并且要带存档迁移。

没有去处的约 6300 行（真值表、写定义、造反例世界、证明脚本、十来个参数台……）留在领域里，按上面的规则计数；哪一种被第二门学科用到，再提成内核部件。

**还没做的**：把场景的拼装（用哪个部件、接哪些量）从领域的声明再往下放到内容里、在 studio 里配。现在只有两款游戏用场景图，抽这层 schema 的依据不够，等第三款。

### 决策二十二：作品和验证，任意一边都可以交给玩家

各款游戏里拼板之外的玩法（真值表、造反例、填表、找漏洞、参数台……）各写各的屏幕，约 6300 行，新学科还得再写。统一的依据是屏幕上本来就只有两块东西：**作品区**（板、条、表：一样被做出来的东西）和**验证区**（检验它的那些情形和预期）。每一块都可以是给定的，或者交给玩家；任意搭配都是一道题。

| 作品 | 验证 | 是什么 | 现状 |
|---|---|---|---|
| 玩家做 | 给定 | 搭 | 主玩法 |
| 给一样错的，可改 | 给定 | 修 | 任务的 `starter`：板打开时摆着它 |
| 给定，不能改 | 玩家写 | 破（审计） | 任务的 `works`：还是那块标准的板，结果区里填检验（`shell/Checks.jsx`） |
| 玩家做 | 玩家写 | 先写检验再搭 | 没有 |

（两边都给定只能读，不做成任务。）

**一条判定管所有搭配**：一个任务手里有几样作品（标明对错）和几条检验，玩家补上开放的那一边，过关永远是同一句话：**对的作品通过每一条检验，每样错的作品至少被一条检验挡住。** 搭和修是让自己的作品算进「对的」；破是让自己写的检验把对的和错的分开。这就是变异测试，所以出题的原料现成：对的作品是参考解，错的作品是任务已有的错解，不够再从变异体里挑。

**作品不必是机器。** 能确定地跑在一个情形上得出结果、用封闭的几种形态之一写出来，就算作品：**板**（放元件、连线）、**条**（往带类型的空位里填：公式、证明的子句、句子成分）、**表**（一行一条声明）。判定和形态无关，形态只决定作品区用哪个编辑器。

**这种玩法早就有，只是没被认出来。** 证明完毕的 `decl-*` 十关就是「作品给定、玩家写检验」：别人写的规则声明不能改，玩家写检验条例把毛病测出来（内核的 `useBoardCases`，`audit`；同一处还定义了 `repair`）。2026-11-13 我先在《看不见的手》里把「破」做成了「用三块常数给出一条街」，又一度把它整个撤掉，两次都错：前一次把写检验做成了填三个数再点运行，后一次把做坏了当成不该做。

**让写检验不退化成调参**，两条都来自证明完毕：一次给几样各错一处的作品，要求用很少几行全部挡住（得先想清每样错在哪）；行数就是限制。只给一样错作品、不限行数，才会是来回试。

**在底座上的第一次落地**（《看不见的手》最后一关）：
- 破：三块调价器，一块只会涨、一块接反了、一块步子大了一倍；玩家写两行检验（昨天的价格、剩下、没买到、该给的价格）。一行里既有货剩下又有人没买到会被拒绝（「一天的买卖」教过这不会同时出现），所以一行挡不住三块，至少两行。
- 修：只会涨的那一块摆在板上，只许再添一块元件（`most`，还是 `market` 自己的字段）。

**第二次落地：检验是一个造出来的对象**（2026-11-14，《从一根线开始》「认出旗标」的第二个任务）。玩过调价器那一关后的判断：写检验在调价这类算一个数的任务上不成立，一是「对」只是关卡约定的系数，二是随手填一行互不相等的数就能把线性的小错全挡住，又成了填数字。成立要三条：对错由学科定而不是关卡定；每样错作品对应一个真会有的误解；多数输入分不出对错，要找的是那个边界。再加一条，玩家交出的检验得是一个有结构的对象，造它本身就是在搭。位串是第一种：三块各错一处的认旗标板（线一开头不必先有 0、一个 0 不能给前后两个旗标共用、1 多于六个也算），玩家在两行里各排 16 拍进线上的位；预期不用填，对的作品给出什么由领域的 `want` 算。穷举 65536 种行：96.9% 的行一块也挡不住，没有一行挡得住三块，两行的解一共 4 组。逐拍的领域因此也能用这种玩法：行的每一格是什么由领域说（run.js 的 `cells(task)`，现在有数值和位串两种，`shell/BitsField.jsx`），运行后结果区在检验表下面画出选中那一行上这块板的波形，出错的那一拍标出来，板上的牌停在那一拍。

**哪些任务可以出成写检验**：反例是有结构的对象、错作品来自真实误解的知识点才出；算一个数的公式类知识点不出。玩家造的是具体的反例；写「所有情形都该怎样」的性质是另一格（性质本身也得是一块输出真假的板），放在搭过、挑过错之后收束用，还没有做。

`starter` 和 `works` 现在是底座的任务字段（八个领域的词汇表各升一版）。屏幕还是同一块（`CircuitScreen`）：标签页换成给定的几样作品，板上显示选中的那一样、锁住不能改，牌上是它在选中那一行上算出的值；结果区是玩家填的检验表，运行后每行多出「这一样给出」。判定是纯函数（`engine/caught.js`）。一个领域要用它，只需在 run.js 里说一行检验怎么变成它自己的一个测试（`check(task, row)`）。

没做的、没把握的：
- 检验表会数值和位串两种格；值是格子、句子、带输入和队列的逐拍任务还要各自的填法（net 的写检验任务现在只许有进线）。位串一格一拍地点，不能拖着刷。
- 「认出旗标」那一个任务几乎只有一组解（4 组），甲那块板的毛病还牵着计数器从线一开头数起差一拍，可能偏难；没有人玩过。
- 证明完毕的十关还在它自己的屏幕上，没有迁到这一套；「两边都交给玩家」没有做；条和表两种形态没有在底座上验证。
- 「修」的上限只数元件个数，挡不住推倒重搭。
- 好不好玩没有人玩过。

### 决策二十三：一关手里有什么，是一条规则管三级粒度

照《图灵完备》的元件表：默认跟着进度走，关卡再增删。它整款游戏是一套表；我们一款游戏有几套托盘，关卡之间切换。增删的单位也不是元件而是**配置项**：一个元件、元件的一项设置、设置的一个取值，三级走同一条规则。规则本身写在手册第 2.8 节，实现是 `kit/course.js` 的 `holds`。

做这件事之前，同一个问题有五处各自的写法：底座在自己那一层过滤 `withhold`；外壳在标记集合上加 `grants`、减 `withhold`（只有 `image` 在用）；`image` 的元件表自己按标记裁设置和选项；`logic` 自己拼「托盘之外再给什么、再收什么」，引理的形状另走一个按关卡位置算的函数；底座的界面留了「这里放开哪些选项」的口子，没有人提供。现在都是内核这一条，领域只声明自己的东西怎么对上配置项。

落成的（2026-11-14）：
- 内核：配置项的地址（`itemOf`、`readItem`）；课程的 `opens`、`gives`、`withholds` 三个钩子；`holds(course, 任务, 标记)` 回答任何一级；`usable`、`offer` 建在它上面。一关之内的进度也进了内核：任务拿得到前面的任务搭出的东西，搭它的那个任务自己不拿。
- 底座：任务的 `withhold`、`grants`、`opens` 都是配置项，六个领域和两个模板的词汇表各升一版；`parts.json` 的元件按它裁卡片上的设置和取值；参考解用了手里没有的取值，检查报错。
- `image`、`logic` 换到这条规则上，各自的那套删掉；外壳的 `flagsIn` 只剩「玩家挣到了哪些标记」。

改动前后对过每个任务手里的东西：《视觉完备》318 种情形、底座六款游戏 795 种、《证明完毕》的托盘 796 种，托盘内容和顺序都一样，例外两处，都是规则统一带出来的：
- 《从一根线开始》「认出旗标」的第二个任务现在拿得到第一个任务搭出的认旗标元件（原来写着「后面的任务只是用这个元件」，实际没给）。
- 《证明完毕》里一关证出几种形状的四关（德摩根律、量词的德摩根律、分配律、当且仅当）：后一段任务现在能用前几段刚证出的形状。原来证明板要等到下一关，证明助手板却是同一关就给，两处不一致。

没做的：
- 限量（某种元件最多几个）。没有一关需要。
- `logic` 的字段还叫 `without`：词汇表只许加不许改，改名留给这个领域重做的时候。`image` 的内容里写的还是标记不是配置项，同理。
- 底座上搭出的元件的几种形态（`builds.form`，`assembly-series.js`）还是自己按关卡位置算哪几种可见，没有并进来：它同时决定一种形态跑的是哪块板，拆开要动升级链。
- 元件箱里的说明随进度变（`revisions`）是文案的事，不在这条规则里。
- 界面只在数据检查和单元测试里验过，没有在浏览器里点过。

## 4. agent 流水线

```
课程资料 → 知识点 → 课程蓝图 → 蓝图审计
        → 关卡规格 → 规格审计 + 参考解运行 + naive 解失败 + 教学 lint
        → 文案 → 文案 lint + 术语链接
        → 变更集进评审队列（官方）或直接发布（社区）
```

每一步的产物都是内容层的数据；每一步失败都定位到一条规则；每一步的修改都是操作集里的操作。

**流水线从知识点出发，不从元件出发**（手册第 1 节「玩的过程就是学的过程」、第 4.1 节）。《视觉实验室》第一版（计算机视觉第 0、1 章，59 关）是按旧蓝图做的：蓝图的「想法」可以是任何东西，审计又要求一关一个新想法、每个想法后面有练习，于是 agent 给每块元件编一个想法（「常数」「取整」「取较大值」各占一关，引言是同一句套话），同一块板、同一段话在几关里重复，判断题看题面的字就能答，参数台拖一个旋钮到变绿就过，文案短到说不清问题。闸门全过，教的东西却很少。改法是改流水线而不是改这款游戏：蓝图先从课程材料列出知识点（术语、出处、撞上的墙、纠正的错误），每个 slot 写出玩家要回答的问题和思维链；审计不再让元件充当知识点；关卡和文案的闸门加上教学 lint（重复的板、重复的话、拖到变绿的实验台）和术语链接。《视觉实验室》后来整款删掉，计算机视觉留下《视觉完备》。

实现见手册第 7.2 节（`kit/pipeline/`，`npm run pipeline`）。在蓝图和关卡规格之间多了一步「领域」：蓝图向领域提的需求（决策三的需求通道）由工程师实现或拒绝并写明理由，内容 agent 不写代码。一步失败时往回走：关卡设计 agent 停在蓝图做不到的地方，它的报告成为课程设计 agent 下一次的输入（`--from`）；评审 agent 的发现按它归属的那一步交回去；人的退回意见也一样（`comment`）。在网络第 1 代上，往回走是常态而不是例外：蓝图改了五次（两次因为领域的回答、一次因为关卡设计停下、两次因为评审），关卡写了四遍，文案三遍。

**流水线接下来的四处改动**（阶段 6.8 之后做，依赖决策十五的信号）：
- **先做竖切片。** 新专题最难的是领域建模：什么是原始能力，机体是什么，哪一种机制承载它。蓝图之前多一步：agent 交出机制选择的论证和三关能玩的切片（从零起步的一关、搭出第一个元件的一关、用上它的一关），过了门禁才铺整门课；切片做不出来的专题在这里拒绝，写明原因（第 5 节的适用范围）。
- **生成几份再选。** 关卡规格这一步，每个 slot 出几个候选，按变异得分、解的多样性、搜索工作量在这一章难度曲线上的位置排序，留下一个；人评审时只看留下的。
- **人的修订是标注。** 修改日志记着每个变更集是谁写的（决策十六）。agent 写的内容被人改掉的比例，按步、按规则统计，是流水线质量的直接读数；被改掉的地方连同改后的样子，回到那一步的 brief 里当反例。它和「闸门漏掉的改成检查」是同一个回路的两半：能机械查的变成检查，不能的变成例子。
- **固定的基准专题。** 选两三个专题反复跑，记闸门通过率、评审发现数、人工修订率、每一步的用量；换模型、改 brief、改闸门，都在这几个数上看得出好坏。

## 5. 承认的边界

- 内容层做不到百分之百无代码：真的只能用代码表达的测试生成和判定留在领域层，以名字暴露。这是边界，不是失败。
- 词汇表的粒度是本方向唯一真正难的决定，没有办法事先证明对；只能在一个领域上试，按「屏幕上能指着说的概念」校准。
- 审计抓不到的只有文案好坏和难度；前者靠人与社区，后者靠解空间信号（决策十五）估计、靠游玩数据校准，都不是精确的。
- 适用范围：内核承诺的是有组合结构的专题，能从少量原始能力逐层搭起来、每一层的对错可以由测试判定。以记忆、语感、审美判断为主的专题需要另一种玩法，不在承诺之内；竖切片做不出来就是信号。
- studio 的通用控件集是内核的固定开销；每种新的值类型都要内核加一个控件。

**阶段 6.8 · 平台地基（决策十三、十四、十五、十七）**

- 变异得分（`kit/engine/mutate.js`，`npm run check -- <游戏> --mutants`），接在电路底座上；元件声明次序无关的输入（`symmetric`），由资源的声明推出，声明错了检查会失败。

这一轮的结论改了决策十五的一处：变异得分不能直接当门禁。等价的变异体机器分不出来，占了活下来的大多数；门禁的形状应当是「每个活下来的变异体都有人认过」：认过的记下来，新冒出来的才拦。

- 变更集带着是谁（`by`）：命令行、studio、流水线各自写上；`npm run op -- <游戏> log` 按作者统计。变异报告也能从 MCP 的 `audit` 要（`mutants: true`）。

重审以后推到阶段 7 的（理由在各决策里）：存储接口、操作的级别、kit 自成一个包和公开面的类型、内核格式版本（和不可变的包一起定）。短解搜索去掉了。

- 译文拆成了覆盖层（决策二十，`kit/engine/i18n.js`，手册第 6.10 节）：十款游戏和全部入门内容的英文搬进了各自的 `i18n/en.json`，内容里只剩中文；`text.set` 只改原文，译文用 `i18n.set`；流水线多了不拦发布的 `translate` 一步。和决策的写法有两处不同：覆盖层按原文本身做键（不是「文件加路径」加哈希），所以内容怎么挪都不用动它；基准语言现在是内核里的一个常数，等有了第二种基准语言再让游戏自己声明。迁移时同一句中文原来有两种英文的（共约 190 处，多是一两个词的标签）只留了先出现的那一种；课程蓝图里的英文没有保留。studio 有了「译文」页签；内核和领域的代码自己说的话也拆了（`kit/i18n/en.js`，1949 处调用，`npm run words`），用值拼出来的句子和一词两译的还留在代码里。

还剩（按这个顺序）：
0. 「一批案例」这种世界；机制契约按「怎么造」和「怎么跑」两层写成代码。
1. 认过的变异体记在哪：倾向用游戏 `game.json` 的 `open`（规则 `mutant`，写 `变异@任务`），不给任务加字段；记下以后 `--mutants` 才从报告变成门禁。
2. 变异得分接到电路底座以外的机制上（原型领域随阶段 6.5 重做时接）。
3. 引擎资源的值形状和有状态的资源（并掉阶段 6.6 剩下的那一半），等第二个用资源定义元件的领域。
完成标准：现有游戏活下来的变异体都认过或已修；改一关的谜题只清这一关的存档（已达到）。这一阶段排在阶段 6.5 之前：重做的游戏直接长在新边界里。

## 7. 开放问题

- 词汇表粒度：《状态之图》上定出了第一版（`kit/domains/table/vocabulary.js`），《证明完毕》上成立（`kit/domains/logic/vocabulary.js`）：规则即元件是元件项，框由 kit 给，玩家证出的引理、拼出的门、证出的等式是内容里的数据（陈述、口），不是词汇项；句子是领域记号的文本，存档迁移的几十个一次性函数合成十来个带参数的迁移项。《视觉完备》上同样成立：测试场景、目标图、图像生成器、约束各是一种项，一关按名字选项、填参数（`kit/domains/image/vocabulary.js`）。机关台抽成通用参数台以后也成立：模拟是领域的一个模型项，旋钮、情形、步骤、按钮、目标（对模型算出的量的限制）和版面全是数据，画面是一个封闭的显示项集合（内核给曲线、像素行、读数、目标、步骤……，领域补拼不出来的图和交互）。留下的问题是显示项的粒度：领域的显示项（暗箱侧视图、霍夫累加器、封面配点……）多半一个模型一项，是不是该再拆成更通用的「可拖动的点」「栅格图」，要等第二个有参数台的专题来定。
- 盲玩 agent 的能力与真实学习者的差距：通过率高不等于人学得会；需要少量真人数据校准。基线说明了差多远：五款原型的前 9–12 关，LLM（claude-sonnet-5-5）几乎都一次通过、不要提示，每关十几秒。它熟悉逻辑门、德摩根律、动态规划和图像滤波，新手要学的正是这些；它读得懂一句话的元件说明，新手常常读不懂；它不看图，文字版的画面（图像是一格一格的数）对它反而更好用。所以它的突起是「这一关缺了什么」（`difficulty-spike` 在这上面有用：一关同时要三件事、反馈说不清 0 和「否」、引擎丢了设置），不是「这一关对人难」；平坦的曲线不说明新手也平坦。校准要几个真人走同样的 harness（`--player human`）或页面里的同一种记录，再比两条曲线的形状；另一条路是给 agent 加限制（更小的模型、不许用外部知识、只许按提示走），看它的曲线是不是更像人。
- 社区内容的改编与署名：改编官方关、组装课程时，蓝图审计（抽象链、分支）对拼装出来的课程还能不能成立。
- 内核需求通道的优先级：谁来排序，按什么排。
