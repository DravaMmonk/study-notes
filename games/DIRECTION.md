# 开发方向决策书：从样板游戏到创作平台

本文记录项目下一阶段的方向和理由。它只定方向、边界和顺序；落到每一条具体规矩时，写进 `games/DESIGN.md`、领域的词汇表和 schema，本文不重复。做完的阶段从「实施顺序」里删掉，方向变了就改本文。

---

## 1. 终点

一套面向 agent 的开发套组、平台和 MCP：输入一套课程体系或一个专题，输出一款上手即玩的类图灵完备游戏——从零门槛起步，一路到专业深度和前沿知识，关卡设计符合 `games/DESIGN.md` 的全部规则，关卡有技术含量。

同时，人能轻松参与：任何 AI 生成的实质内容（课程结构、关卡、文案）都能在一个页面上审核、修订、试玩；修订不需要写代码。

## 2. 现状判断

**已经有的**：一本设计手册（原则、课程结构、关卡规格、审计规则、引擎分层、作者流程）；修改内容的操作集，带存档迁移生成、修改日志、命令行和 MCP（手册第 7 节）；一个共享 kit（求值、封装件、框、逐步机器、逐拍世界、两套电路编辑器、外壳、地图、存档迁移、蓝图文本）；若干领域模块；七款原型游戏（决策十）。阶段 0+1 已经做完：内核有内容层的契约（schema、词汇表、数据游戏的加载和检查），七款游戏的文件夹里只有数据；封装件跑学习者的电路；`unused`、`bare-intro`、`idle-idea`、`bypass` 在所有游戏打开并清零；课程的形状是数据，`npm run deps` 画出元件依赖图；机关台是一个通用参数台（`kit/shell/bench/`）；电路关是一个内核界面（`kit/shell/CircuitLevel.jsx`）。领域有了写下来、测得出的契约（手册第 6.3 节，`kit/engine/contract.js`，`npm test` 对六个领域、七款数据游戏机械地查）和机制目录（手册第 6.5 节）；`npm run new-domain` 从电路模板生成一个能玩的领域和入门游戏，`npm run new-game` 从领域的入门游戏开新游戏。阶段 3 已经做完：盲玩 harness 是内核（`kit/engine/play/`，每个领域在 `domain.js` 给一个 `play` 钩子），只给玩家看到的东西、照游戏的规矩判尝试，一局像一份存档，记录是内容里的数据（`playtests/`），`check` 列出审计面板并跑 `difficulty-spike`；五款原型各有一局 LLM 盲玩的基线，harness 指出了两处突起：《状态之图》「走不到的路口」一关同时要三件事（难度曲线，写进了它的设计文档）；《车在说话》1-5 是引擎的毛病（蓝图导入丢了常数的值，已修；量到它的那一局只留在 git 历史里，因为它量的是一个已经修掉的错）。

**缺的**，按对终点的影响排：

1. 领域模块仍是每个专题的真实成本：脚手架只有数据流电路一个模板，逐拍总线、逐步机器、参数台的新领域要从例子领域抄起。
2. 经验性验证只有 LLM 的读数：盲玩 harness 有了，但基线是每款一局 LLM 盲玩，难度规则要 5 局才算数；没有真人数据，LLM 和新手的差距也还没校准（第 7 节）。几种玩法 harness 还不支持（手动玩法、证明板、句法，`games/DESIGN.md` 第 6.6 节）。
3. kit 自身不统一：部分封装件仍是内置实现；电路关界面已在内核（`kit/shell/CircuitLevel.jsx`），《视觉完备》《状态之图》的旧界面等按专题重做时换上（《视觉完备》的电路关因此还没接上最后一次运行）。
4. 设计文档与代码的一致性靠约定。
5. 没有人的编辑入口；没有版本与发布形态。

## 3. 决策

### 决策一：三层架构，内容层是纯数据

```
内核层   kit/engine, kit/circuit, kit/shell    机制与界面，所有游戏共用
领域层   kit/domains/<x>                        值、原始元件、世界、求值、判定、画法；一个专题一份代码
内容层   games/<x>/                             课程蓝图、关卡规格、文案、百科；全部是数据，不含代码
```

**决定**：内容层不含任何可执行代码。测试数据、诊断谓词、引言插图、通关后的面板，一律改为**引用**：领域层暴露有名字、带参数 schema 的生成器和谓词，内容层只写 `{ "名字": 参数 }`；无法生成的物化成数据。参考解和 naive 解用已有的 ASCII 蓝图文本。

**理由**：只有纯数据的内容才能被 schema 校验、被 diff、在页面上改、在 git 里审、被 agent 安全地读写；也只有纯数据才能开放给不受信任的创作者。

**内容层分三种产物**，粒度从粗到细，各有审计：

| 产物 | 内容 | 审计 |
|---|---|---|
| 课程蓝图 | 机体阶梯、每代能力、原始元件清单、元件依赖图、每个机制「第一次非它不可」的位置、练习簇、并行组 | 不依赖的就分支、抽象在上升、机制放在被核心用到的地方、基础元件最少 |
| 关卡规格 | 目标、传感器、测试、参考解、naive 解、新带来的元件、折叠、预置、任务段、挂靠 | 现有 `audit` 全部，`idle-idea`、`bypass`、`bare-intro` 全开 |
| 文案与百科 | 中英两面、链接、词条、修订 | 现有 `check` 的文案检查，加禁用词与长度 lint |

设计文档保留，只写理由与取舍；凡是能检查的事实从数据来，不再手抄。

### 决策二：创作层的词汇表是封闭的

**决定**：一关、一款游戏只能由内核和领域**已经提供**的东西组合而成。每个领域给出一份**词汇表**（domain vocabulary）：值类型、原始元件、世界类型、测试生成器、判定谓词、玩法、机体能力，每一项带参数 schema。创作者能写的全部，就是在词汇表里选项、填参数、接线。词汇表里没有的，不由创作者绕路实现，而是提交一条结构化需求进内核队列。

**理由**：这是人机协作和开放创作成立的前提。词汇表封闭，内容才可能无代码；内容无代码，沙箱才是结构上成立的，不靠审查；审计才能覆盖创作者能做的一切。

**词汇项的粒度标准**：一个词汇项对应玩家在屏幕上能指着说「那个东西」的一个概念——一种元件、一种世界、一种玩法、一种测试的形状。满足这条的进词汇表；只有实现细节能区分的，合成一项加参数。太粗创作者表达不出，太细就是变相写代码。先在最成熟的领域（《状态之图》）上定标准，再推到其他领域。

**词汇表 v1 的来源**：从现有样板游戏提炼。规格现在做的每一件事，凡是靠临时 JS 的，都改成词汇表里一个有名字的项。提炼完，v1 自然成形，内容层去代码化也同时完成。

### 决策三：两级权限

| | 内核 | 创作 |
|---|---|---|
| 谁 | 核心工程师、管理员、高级别 AI | 玩家、普通 AI、课程作者 |
| 产物 | 代码：引擎机制、领域模块、词汇表 | 数据：课程蓝图、关卡规格、文案 |
| 门禁 | 单元测试、契约测试、代码审查、版本号 | schema + 审计 + 盲玩，机器自动放行 |
| 能破坏什么 | 一切 | 只能做出一个不好玩的关 |

**决定**：内核层权限收紧，只接受走完整门禁的代码变更；创作层不设人工门禁，审计清零即可。内核的演进由创作层的需求通道驱动：创作者遇到「词汇表里没有」，产出一条结构化需求（要一种机制、一个元件、一种玩法），内核按队列实现，词汇表随之增长。

**理由**：引擎会一直更新，但更新的权限必须和创作权限分开，否则开放创作就是开放破坏。需求驱动的扩展也比凭空扩展更不容易做出用不上的机制。

### 决策四：修改只有一套操作集

**决定**：对内容层的每一种修改都是一个结构化操作：改字段、加关、删关、移动挂靠、拆合任务、改元件的解锁关、重命名 id、拆出引入关、合并几关为一关的任务段……每个操作自带：
- schema 校验和受影响的审计规则；
- 存档迁移的自动生成（重命名、推出新解锁、新插入的前置关标通过、`merge`），接进 `kit/shell/saves.js` 现有的迁移机制；
- 一条可回放、可撤销的日志。

MCP 的 `modify`、studio 的每个编辑按钮、CLI 三者只是这套操作集的三层薄皮；人和 agent 改的是同一份数据，走同一条门禁。

**理由**：手写迁移已经是手册里记录的坑；agent 会频繁重排，迁移必须自动。一套操作集也是人机协作不互相踩的唯一办法。

### 决策五：studio 是 schema 驱动的通用编辑器

**决定**：studio 不持有领域知识，不含领域代码，自由度就是词汇表的自由度。它由四块组成：
- **树编辑**：现有地图组件（`LevelMap`）可拖动，分支、挂靠、三列规则就地提示；
- **关卡编辑**：字段按 schema 生成表单；值类型映射到 kit 里一小组**通用控件**（网格、序列、电路蓝图、枚举、数值、图像），词汇表只声明「这个类型用哪个控件、参数范围是什么」；
- **嵌入式游戏**：改完即玩，运行结果和审计并列；
- **审计面板与变更集评审**：`check` 的结果按关、按规则常驻，改一处立刻重算；agent 的每次产出是一个变更集，附审计结果、盲玩统计和 diff，人可以批准、就地改、或驳回并写意见，意见回到 agent 的下一轮输入。

**边界**：个别值类型的控件（图像、世界）仍是代码，但它们是 kit 的通用控件，由内核维护；领域层不再有「给 studio 的编辑器」这一项。

### 决策六：验证闭环

**决定**：三道门，依次是：
1. **审计**：schema、蓝图审计、规格审计、文案 lint，全自动，创作层发布的唯一硬门禁。
2. **盲玩**：另一个 agent 只凭引言、提示和托盘打每一关，不看参考解；记录通过率、尝试次数、用到的元件。这是难度曲线和「一关一个知识点」的唯一经验性信号。先在现有五款游戏上跑出基线。
3. **人评审**：只对官方课程；在 studio 的变更集视图里做。

**理由**：审计抓不到文案好坏和难度；盲玩能抓难度；文案好坏留给人（官方）或游玩数据（社区）。

### 决策七：版本与迁移

**决定**：内容声明它依赖的词汇表版本；词汇表只增不删，删改必须带迁移；kit 独立打包、语义化版本。官方课程的存档迁移由操作集生成；社区内容只保证在它声明的版本上可玩。

**理由**：开放给玩家后，一次引擎升级会打坏成千上万个自制关；没有版本，就没有开放。

### 决策八：发布分档

| | 官方课程 | 社区内容 |
|---|---|---|
| 门禁 | 审计 + 盲玩 + 人评审 | 审计清零 |
| 质量 | 评审保证 | 游玩数据、评分 |
| 可组合 | 可被社区引用、改编 | 可改编官方关、组装成自己的课程 |

### 决策九：领域层产品化

**决定**：领域仍是代码，但要有：
- **机制目录**：数据流电路、逐步机器、逐拍总线、框、词序条、填表、参数台、纠错/修正玩法——各自适合什么专题，一张表，放在手册第 6 节；
- **domain 脚手架**：按契约生成空壳（值、注册表、世界、`validate`、关卡界面、词汇表、游戏描述），agent 或工程师只填实现；
- **契约测试**：一个 domain 装进去，kit 的通用检查、studio、MCP 自动能用。

### 决策十：现有游戏是原型，基础设施先完整

**决定**：现有七款游戏的关卡是原型，没有打磨过，不再在它们身上重构、打磨或重新编排。它们只做两件事：证明基础设施能承载一个专题，以及给各阶段当测试夹具（操作集、迁移生成、盲玩 harness、studio 都先在它们上面跑通）。基础设施（第 6 节阶段 2–6）全部完整以后，再按专题用流水线从头重做、重新编排这一系列游戏，不抱着原型改。

**理由**：原型的关卡设计本来就要重做；在它上面保持「玩家看到的一模一样」的重构，花的是验证原型的成本，换不来更好的游戏。基础设施做完，重做一款游戏的成本才会降下来，审计、盲玩、studio 也才能在重做时真正约束质量。

## 4. agent 流水线

```
课程资料 → 课程蓝图 → 蓝图审计
        → 关卡规格 → 规格审计 + 参考解运行 + naive 解失败
        → 文案 → 文案 lint
        → 盲玩 harness
        → 变更集进评审队列（官方）或直接发布（社区）
```

每一步的产物都是内容层的数据；每一步失败都定位到一条规则；每一步的修改都是操作集里的操作。

## 5. 承认的边界

- 内容层做不到百分之百无代码：真的只能用代码表达的测试生成和判定留在领域层，以名字暴露。这是边界，不是失败。
- 词汇表的粒度是本方向唯一真正难的决定，没有办法事先证明对；只能在一个领域上试，按「屏幕上能指着说的概念」校准。
- 审计抓不到的只有文案好坏和难度；前者靠人与社区，后者靠盲玩，都不是精确的。
- studio 的通用控件集是内核的固定开销；每种新的值类型都要内核加一个控件。

## 6. 实施顺序

每个阶段写明完成标准；做完就从这里删掉。

**阶段 2 的余项 · 拆合任务与无头渲染**
操作集、迁移生成、修改日志、CLI 和 MCP 已做（手册第 7 节）；原型上的三次手工修改（c8fc67d 的两处、78e09bf 的一处）和一次跨章改名加挪动由操作重做，内容与提交一致，迁移与手写的等价并通过存档测试（`kit/engine/ops/replay.test.js`）。还剩：
- `level.merge`、`level.split` 要领域给出任务的形状（`domain.js` 的 `tasks`），现在只有逻辑领域给；其余领域等原型重做时再给。
- 谜题改了要去掉存档的规则（`domain.js` 的 `changes`）只有逻辑和句法两个领域给；表格、图像、agent、总线的关改了谜题，变更集照常生成 id 和先修的迁移，但不会去掉旧的板（这些领域的板是程序，多数改动不需要去掉；真需要时，变更集里没有办法表达，要先给领域加 `changes`）。
- MCP 的 `render` 只出文字：板和关卡由浏览器画，无头的 SVG、PNG 要把 kit 的电路画法抽成不依赖 React 的一层，等 studio（阶段 4）一起做。
完成标准：每个领域都给出 `tasks` 和 `changes`，`render` 能出 SVG。

**阶段 4 · studio**
按顺序：树编辑 → 关卡编辑（schema 表单 + 通用控件）→ 嵌入式游戏 → 审计面板 → 变更集评审。
完成标准：一个不写代码的人能把 agent 产出的一章从头到尾审完、改完、玩完。

**阶段 5 · agent 流水线端到端**
用一个全新专题（已有候选：网络、Redis 内部）走完整流水线，产物进 studio 评审。
完成标准：新游戏的全部内容由 agent 产出、人在 studio 里修订、审计与盲玩清零。

**阶段 6 · 领域脚手架（余下的部分）**
契约、契约测试、机制目录、`new-domain`（电路模板）、`new-game` 已经做完（见第 2 节）。余下：阶段 5 的新专题选定机制以后，按它的机制补一个模板（网络多半是逐拍总线：从 `kit/domains/can` 抽出，`can` 已有入门游戏 `starter/`），用它做出真领域；其余领域在用到 `new-game` 时补各自的 `starter/`。只有在一个真专题上从脚手架做出来，才证明脚手架省下了成本。
完成标准：阶段 5 的新领域从 `npm run new-domain` 开始，契约测试一次通过。

**阶段 6.5 · 按专题重做游戏**
基础设施（阶段 2–6）完整以后，按专题用流水线从头重做现有这几款游戏（动态规划、计算机视觉、形式化证明、长难句、编码 agent、车载总线），重新编排课程；原型的关卡、文案、领域代码只当参考，不迁移。
完成标准：每款重做的游戏由流水线产出、在 studio 里评审修订、审计与盲玩清零；原型从仓库里退下。

**阶段 7 · 开放创作**
版本号、kit 打包、社区发布档、需求通道。
完成标准：一个玩家在 studio 里用现有词汇表做出一关并发布，不经人工。

## 7. 开放问题

- 词汇表粒度：《状态之图》上定出了第一版（`kit/domains/table/vocabulary.js`），《证明完毕》上成立（`kit/domains/logic/vocabulary.js`）：规则即元件是元件项，框由 kit 给，玩家证出的引理、拼出的门、证出的等式是内容里的数据（陈述、口），不是词汇项；句子是领域记号的文本，存档迁移的几十个一次性函数合成十来个带参数的迁移项。《视觉完备》上同样成立：测试场景、目标图、图像生成器、约束各是一种项，一关按名字选项、填参数（`kit/domains/image/vocabulary.js`）。机关台抽成通用参数台以后也成立：模拟是领域的一个模型项，旋钮、情形、步骤、按钮、目标（对模型算出的量的限制）和版面全是数据，画面是一个封闭的显示项集合（内核给曲线、像素行、读数、目标、步骤……，领域补拼不出来的图和交互）。留下的问题是显示项的粒度：领域的显示项（暗箱侧视图、霍夫累加器、封面配点……）多半一个模型一项，是不是该再拆成更通用的「可拖动的点」「栅格图」，要等第二个有参数台的专题来定。
- 盲玩 agent 的能力与真实学习者的差距：通过率高不等于人学得会；需要少量真人数据校准。基线说明了差多远：五款原型的前 9–12 关，LLM（claude-sonnet-5-5）几乎都一次通过、不要提示，每关十几秒。它熟悉逻辑门、德摩根律、动态规划和图像滤波，新手要学的正是这些；它读得懂一句话的元件说明，新手常常读不懂；它不看图，文字版的画面（图像是一格一格的数）对它反而更好用。所以它的突起是「这一关缺了什么」（`difficulty-spike` 在这上面有用：一关同时要三件事、反馈说不清 0 和「否」、引擎丢了设置），不是「这一关对人难」；平坦的曲线不说明新手也平坦。校准要几个真人走同样的 harness（`--player human`）或页面里的同一种记录，再比两条曲线的形状；另一条路是给 agent 加限制（更小的模型、不许用外部知识、只许按提示走），看它的曲线是不是更像人。
- 社区内容的改编与署名：改编官方关、组装课程时，蓝图审计（抽象链、分支）对拼装出来的课程还能不能成立。
- 内核需求通道的优先级：谁来排序，按什么排。
