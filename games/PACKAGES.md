# 内容包：模组式的对象、合并与覆盖

**这份文档是这项开发的唯一依据。** `games/DESIGN.md`、`games/DIRECTION.md`、`games/PLAN.md` 里关于内容包、关卡组、课程、托盘、命名的说法，凡是和本文冲突的，以本文为准（第 10 节列出被取代的部分）。全部做完后，再把结果写回 `games/DESIGN.md`，删掉这份文档。

## 1. 目标

内容包做成《我的世界》Java 版、《异星工厂》里「模组」那样的东西：

- 一个包声明一批对象，可以依赖别的包，引用和覆盖它们的对象。
- 可以有只提供基础件的**库包**（比如四则运算），谁都能依赖。
- 一款游戏选用若干个包，在它们之上编排自己的学习路线。

第一个用例：以《证明完毕》（`qed` 包）为起点，新建一个数学分析的包和游戏，依赖 `qed` 和一个库包。本文只管平台；数学分析的内容另外安排。

## 2. 起点（提交 `0fe05d1` 时的状态）

- `packages/<包>/`：`package.json`（`domain`、`vocabulary` 和领域的包级配置，如 `wordSets`、`quotes`）、`trays.json`、`levels/<id>.json`、`groups/<id>.json`（关卡组：`title`、`levels`、`links`）、`pieces.json`（`parts` 和 `settings`）、`glossary.json`（`groups` 和 `entries`）、`i18n/<lang>.json`。
- `games/<游戏>/`：`game.json`（`package` 和标题、引语、导语）、`course.json`（`eras`：章里的 `levels` 是 `{ id }` 或 `{ group }`，`links` 的两端是关或组，`rows` 是路线图布局；还有 `primitives`、`concept`、`replaces`、`local`、`views`、`words`、`open` 等课程设置）、`i18n/<lang>.json`、`overrides/<lang>.json`（游戏对包内文案的覆盖）、`changes.jsonl`。
- 内核里与此相关的：`engine/groups.js`（`expandEras` 把组展开）、`course.js` 的 `mapRows`（路线图排法）、`engine/content.js` 和 `content-node.js`（组装）、`engine/ops/workspace.js` 和 `operations.js`（`opScope` 把操作分成包和游戏两边）、studio 的 `PackageStudio.jsx`、`GameStudio.jsx`、`GroupBoard.jsx`、`ChapterBoard.jsx`。
- 现在四款游戏各用一个同名包，每个包里还没有一个关卡组。

## 3. 对象

### 3.1 种类和名字

每个对象属于一种，每种是一张单独的注册表，名字只要在同种里唯一（关卡和标签同名不冲突）：

| 种类 | 是什么 | 现在在哪 |
|---|---|---|
| 关卡 `level` | 一关 | `levels/<id>.json` |
| 件 `piece` | 玩家手头能用来造的东西 | `pieces.json` 的 `parts` |
| 设置 `setting` | 件可以引用的一项设置的定义 | `pieces.json` 的 `settings` |
| 词条 `entry` | 百科的一条 | `glossary.json` 的 `entries` |
| 标签 `tag` | 同一种对象的集合（3.2） | 关卡组、托盘、百科的分组 |
| 关系 `relation` | 一组有向边（3.3） | 组和章的 `links`、托盘和列表的顺序、`replaces` |
| 布局 `layout` | 一批关卡的路线图排法（3.4） | 章的 `rows` |

- **全名**是 `<命名空间>/<名>`。包的命名空间是包 id；游戏自己声明的对象，命名空间是 `@<游戏 id>`（游戏和包现在同名，加 `@` 区分）。
- 一个文件里写本包（本游戏）的对象用短名，写别的命名空间的对象用全名。标签前加 `#`：`#qed/connectives`、`#connectives`。
- 组装成内容时一律展开成全名。领域代码、存档、检查、页面只看见全名。
- 分隔符 `/` 要进蓝图语法（`circuit/text.js` 的 `WORD`）、件名（`parts/schema.js` 的 `NAME`）和文案键（`engine/i18n.js` 的 `TEXT_KEY`）。短名的写法不变。
- 件和设置之下仍有决策二十三的三级粒度：件 `shift`、它的设置 `shift.border`、设置的一个取值 `shift.border=wrap`，统称**项**。

### 3.2 标签

标签是唯一的容器，主要给开发用：做元件时按标签一次引入一套设置，把一批关卡收在一起开发，把件收成一个托盘，把词条分组。

- 一个标签只装一种东西：关卡标签只装关卡，项的标签只装项，词条标签只装词条。成员是全名或同种标签（`#…`，可以嵌套，不成环）。
- **标签是集合，没有顺序。** 顺序一律由关系（3.3）和布局（3.4）给出。
- 标签可以带呈现字段（名字、说明），用于托盘的菜单、百科的分组。二级菜单就是嵌套的标签。
- 文件：`packages/<包>/tags/<名>.json`，`{ "kind": "level" | "item" | "entry", "title"?, "desc"?, "values": [成员] }`。

用法：
- **凡是引用一种对象的地方，都可以直接写这种对象的标签**，组装和检查时展开成成员。不为标签另设字段。
- 关卡的 `tray` 引用一个项的标签（取代 `trays.json`）。
- 任务的 `gives`、`withholds`、`opens` 和关卡的 `adds`、`local` 写项或项的标签。
- 件引入一套设置：件的 `settings` 里直接写项的标签，标签里的设置都挂到这个件上，键是设置的短名。同一个件上键重复（两个标签之间，或标签和件自己的绑定之间）报错；用来引入设置的标签里有设置以外的项，报错。
- 概念：几个件合起来是一个新概念，就是一个项的标签，标签上标 `"concept": true`（取代课程设置里的 `concept`）。

### 3.3 关系

关系是一份单独声明的有向边，不属于任何标签。

- 文件：`packages/<包>/relations/<名>.json`，`{ "kind": "requires" | "order" | "replaces", "edges": [{ "from", "to", …属性 }] }`。`order` 可以写成 `"sequence": [a, b, c]`，等于相邻两项之间各一条边。
- 一端可以是标签，表示把标签当一个整件：连到标签，就是连到标签里没有这份关系的前置的那几个成员；从标签连出，就是从标签里没有这份关系的后续的那几个成员连出（行为同现在的 `engine/groups.js` `groupEnds`）。

| 种类 | 用在哪 | 含义 |
|---|---|---|
| `requires` | 关卡 | 先修，卡解锁；边上可以带 `required`（来源关可跳过时也要通过）。不成环 |
| `order` | 任意 | 只管显示和编号的先后，不卡解锁。偏序，内核按固定规则展开成全序：先满足边，平局按全名的字典序 |
| `replaces` | 件 | 升级与合并，取代课程设置里的 `replaces` |

**谁生效：** 所有关系一律加载即生效，没有「选用」这一步。
- 项和词条的 `order`、件的 `replaces` 对加载了它的所有游戏生效。
- 关卡的 `requires` 和 `order` 只作用在游戏放进课程的关之间：一条边两端都在课程里才有效，标签端点按放进来的成员展开。
- 游戏不想要包里的某些边，就覆盖那份关系（第 4 节：`remove` 逐条去掉，`replace` 清空重写）。

### 3.4 布局

布局是一批关卡的路线图排法，也是单独声明的对象。

- 文件：`packages/<包>/layouts/<名>.json`，`{ "of": "#关卡标签", "rows": [[关卡 | null]] }`。一行最多三个位置，`null` 是空位。
- 包里的布局是预设，游戏选用了才生效。游戏也可以声明自己的布局。
- 布局没排到的关，照现有的 `mapRows` 规则排在它周围（`course.js`）。

### 3.5 文案

可翻译字段照旧写 `@键`，各语言表按层合并（第 4 节），键展开成全名。任何一层都可以在自己的语言表里写别的命名空间的键，那就是覆盖那段文字。现在游戏的 `overrides/<lang>.json` 并进游戏的 `i18n/<lang>.json`，写全名的键，不再单设文件夹。

## 4. 依赖、加载和覆盖

**依赖**
- `package.json` 加 `"uses": [包]`。只能引用 `uses` 里那些包的对象（直接依赖，不传递）。依赖不成环，只在同一个领域里。
- 游戏的 `game.json` 用 `"packages": [包]` 取代 `"package"`，并且要列全每个包的依赖，少了报错。
- 跨领域的库包（同一个「加法」给图像、表格、逻辑三个领域用）先不做：现在的件调用的是领域资源，要等件能只调内核运算资源才可能。

**加载顺序**：各包按依赖拓扑排序（平局按包名），游戏最后。

**覆盖**：后加载的层用同一个全名再声明一个对象，就覆盖它。不怕被改，放开：

| 对象 | 默认 | 可选 |
|---|---|---|
| 关卡、件、设置、词条、布局 | 整份替换 | `"$merge": true`：按 JSON merge patch 只改写到的字段 |
| 标签、关系 | 追加成员或边 | `"replace": true` 先清空；`"remove": [...]` 逐条去掉 |
| 文案 | 按键合并，后者盖前者 | |

- 覆盖文件放在覆盖者那一层：`packages/<覆盖者>/overrides/<被覆盖的命名空间>/<种类>/<名>.json`，游戏的放在 `games/<游戏>/overrides/<命名空间>/<种类>/<名>.json`。
- **唯一要拦下的情况**：两个互不依赖的包覆盖了同一个对象，先后说不清，检查报错，要求其中一个依赖另一个。其余覆盖都放行。
- 组装后的内容保留每个对象的来源：哪一层声明，被哪几层覆盖过。studio 和检查都读它。
- 有了命名空间，不同的包不会意外重名；全名完全相同就是覆盖，按依赖顺序生效。所有覆盖都可以在 studio 里审计（第 7 节）。

## 5. 游戏层

章、可选、可跳过、路线图布局都是游戏编排的事，和包无关。包里没有这些字段。

游戏是加载顺序上的最后一层，目录结构和包相同，命名空间是 `@<游戏>`；但它**只编排**：只能声明标签、关系、布局和覆盖，外加 `game.json` 与 `course.json`，不能声明自己的关卡、件、设置和词条。新的关、新的件一律放进某个包。

`games/<游戏>/course.json`：

```jsonc
{
  "chapters": [
    {
      "id": "paper",
      "title": "@…", "question": "@…",          // 领域给的章字段照旧
      "levels": ["#qed/paper-basics", "qed/onerow"], // 这一章的关：一个内联的关卡标签
      "layout": "qed/paper-map"                  // 选用一个布局，可以是 @本游戏/… 的
    }
  ],
  "optional": ["#qed/paper-extras"],
  "skippable": ["qed/onerow"],
  // 课程设置：primitives、views、words、open 等，见下
}
```

- 章的编号顺序：已加载的 `order` 关系（限于课程里的关）展开的全序，再用 `requires` 补；同一关只能在一章里。
- 游戏自己声明的标签、关系、布局放在 `games/<游戏>/tags|relations|layouts/`，命名空间 `@<游戏>`。
- **课程设置的归属**按语义分，迁移时逐个核对：
  - 件和关卡的属性在包里声明：`replaces` 是关系；`concept` 是概念标签（3.2）；`local`（只在带来它的关里用、不解锁也不带到后面的件）和 `adds` 写在同一处，是关卡（任务）的字段。
  - 游戏怎么开局归游戏：`primitives`、`views`、`words`、`open`。
  - 游戏要别的做法，就在编排时覆盖包里的对象（第 4 节），不在课程里另设字段。
- 跨游戏前置（`fromGame`）保留，写在游戏的关系里。

## 6. 包独立于游戏

- 包有自己的修改日志 `packages/<包>/changes.jsonl`。操作集可以单独打开一个包，不用借一款游戏。
- **包的试玩课程由内核生成**：
  - 包里每个关卡标签一章；不在任何关卡标签里的关单独一章，放最后。
  - 包里声明的关卡关系照常生效；`of` 指向某个关卡标签的布局，用在那一章上。
  - 件全都在手边。
  - 这样库包和还没有游戏的包也能试玩、检查。
- `npm run check -- <包>` 按这份试玩课程查一个包；不写名字时，查全部游戏，再查没有游戏玩的包。
- `opScope` 的两边改成「这一层的对象」：包的工作区只改这个包里的对象（包括它的覆盖文件），游戏的工作区只改这个游戏的。

## 7. Studio

- **关卡设计工作区按包打开**。左栏按种类列对象：关卡、件、设置、词条、标签、关系、布局。每个对象标出它来自哪一层、被谁覆盖过。别的包的对象可以一键「在本包覆盖」。
- **编辑器**：
  - 标签编辑器：成员的增删和嵌套。
  - 关系板：沿用现在的接线板（`ArrangementBoard.jsx`）；`order` 也能在板上连。
  - 布局编辑器：沿用 `ChapterBoard.jsx` 的路线图视图。
  - 现在的 `GroupBoard.jsx` 由这三样取代。
- **游戏编排工作区**：
  - 章的成员可以是关或标签，章选用布局。
  - 游戏自己的关系、对包里关系的覆盖（去掉不要的边）、可选、可跳过。
  - 游戏自己的标签、关系、布局。
  - 文案覆盖照旧，写进游戏的语言表。
  - 游戏要和包不同的做法（比如某个件的 `local`），在这里覆盖那个对象。
- **覆盖审计**：两个工作区都能列出这一层看得见的全部覆盖：被覆盖的对象、谁覆盖、覆盖前后的差别，可以从这里跳到对象本身。

## 8. 检查

- 引用：未声明依赖的引用、找不到的全名、标签成员种类不符、标签嵌套成环、关系成环（`requires`、`order` 各自）、布局一行超过三个位置或画在前置之上，都报错。
- 覆盖：两个互不依赖的层覆盖同一个对象，报错。
- 部分游戏照现有规则：游戏只查它放进来的关；托盘（现在是项的标签）上的项有没有关带来，只在放进了整个包的游戏上判断。
- 现有四款游戏除名字变成全名外，检查输出不变。这是每一步的验收前提。

## 11. 约定和须知

- **行为不变**：动手前存下基线，`for g in vision-complete state-graph qed comp90086; do npm run -s check -- $g > <基线目录>/$g.txt; done`（在 `trace-viewer/`），改完同样跑一遍对比。
- **测试**：单元测试只用测试里现写的小内容，或领域、模板的 `starter/`，不读任何一款真实游戏。改了内核跑 `npm test`、`npm run lint:kit`、`npm run words -- --check`。
- **词汇表**：词汇表变了，就升各领域的 `version`，再用 `npm run versions` 存下；新版本只能在旧版本上增加，删改要在 `removes` 里写明。
- **改内容只经操作集**：用 `npm run op -- <游戏> --file <变更集.json>`。批量迁移可以用一次性脚本，迁移后对每款游戏跑 `npm run op -- <游戏> adopt --why "…"`。
- **界面**：不加次要标签和说明文字；在浏览器里看桌面和手机（`npx vite --port 5199`；studio 是 `npm run studio`，可以用 `GAMES_ROOT=<副本>` 指向一份内容副本试写）。
- **开发阶段**：不保留玩家存档，存档兼容不是约束。
- **提交和推送**：提交说明照仓库的写法（`kit: …`、`studio: …`），一句话说做成了什么，正文说为什么。main 上同时有别的会话在推，每次推之前先 `git fetch --depth=50 origin main` 再 `git rebase origin/main`，然后 `git -c push.negotiate=true push origin HEAD:main`。
