# 内容包：模组式的对象、合并与覆盖

**这份文档是这项开发的唯一依据。** `games/DESIGN.md`、`games/DIRECTION.md`、`games/PLAN.md` 里关于内容包、关卡组、课程、托盘、命名、领域的说法，凡是和本文冲突的，以本文为准（第 11 节列出被取代的部分）。全部做完后，再把结果写回 `games/DESIGN.md`，删掉这份文档。

## 1. 目标

内容包做成《我的世界》Java 版、《异星工厂》里「模组」那样的东西：

- 一个包声明一批对象，可以依赖别的包，引用和覆盖它们的对象。
- 可以有只提供基础件的**库包**（比如四则运算），谁都能依赖。
- 一款游戏选用若干个包，在它们之上编排自己的学习路线。
- **内核是一张统一的能力表**，没有「领域」这一层。包只有数据：从内核里挑选行为、组合、填参数（第 7 节）。

第一个用例：以《证明完毕》（`qed` 包）为起点，新建一个数学分析的包和游戏，依赖 `qed` 和一个库包。本文只管平台；数学分析的内容另外安排。

## 2. 起点（提交 `0fe05d1` 时的状态）

- `packages/<包>/`：`package.json`（`domain`、`vocabulary` 和领域的包级配置，如 `wordSets`、`quotes`）、`trays.json`、`levels/<id>.json`、`groups/<id>.json`（关卡组：`title`、`levels`、`links`）、`pieces.json`（`parts` 和 `settings`）、`glossary.json`（`groups` 和 `entries`）、`i18n/<lang>.json`。
- `games/<游戏>/`：`game.json`（`package` 和标题、引语、导语）、`course.json`（`eras`：章里的 `levels` 是 `{ id }` 或 `{ group }`，`links` 的两端是关或组，`rows` 是路线图布局；还有 `primitives`、`concept`、`replaces`、`local`、`views`、`words`、`open` 等课程设置）、`i18n/<lang>.json`、`overrides/<lang>.json`（游戏对包内文案的覆盖）、`changes.jsonl`。
- 内核里与此相关的：`engine/groups.js`（`expandEras` 把组展开）、`course.js` 的 `mapRows`（路线图排法）、`engine/content.js` 和 `content-node.js`（组装）、`engine/ops/workspace.js` 和 `operations.js`（`opScope` 把操作分成包和游戏两边）、studio 的 `PackageStudio.jsx`、`GameStudio.jsx`、`GroupBoard.jsx`、`ChapterBoard.jsx`。
- 领域：`kit/domains/<领域>/`（`image`、`logic`、`table`，各从 `kit/scaffold/<机制>/` 的模板生成），每个有自己的词汇表和版本线、课程逻辑 `course.js`、运算、界面 `ui/`、检查、盲玩钩子，经 `engine/contract.js` 的领域契约接进内核。一个包只属于一个领域，件只能调用本领域的运算。
- 现在四款游戏各用一个同名包，每个包里还没有一个关卡组。

## 3. 对象

### 3.1 种类和名字

每个对象属于一种，每种是一张单独的注册表，名字只要在同种里唯一（关卡和标签同名不冲突）：

| 种类 | 是什么 | 文件 |
|---|---|---|
| 关卡 `level` | 一关 | `levels/<名>.json` |
| 件 `piece` | 玩家手头能用来造的东西，设置写在件里（7.4） | `pieces/<名>.json` |
| 词条 `entry` | 百科的一条 | `entries/<名>.json` |
| 标签 `tag` | 同一种对象的集合（3.2） | `tags/<种类>/<名>.json` |
| 关系 `relation` | 一组有向边（3.3） | `relations/<名>.json` |
| 布局 `layout` | 一批关卡的路线图排法（3.4） | `layouts/<名>.json` |

内核还可以声明内容种类（7.1），比如取代包级配置的 `wordset`、`quote`，和上表的种类一样有注册表、全名、合并和覆盖。

- **全名**是 `<命名空间>/<名>`。包的命名空间是包 id；游戏自己的文案键（标题、章名、导语等），命名空间是 `@<游戏 id>`（游戏和包现在同名，加 `@` 区分）。游戏不声明别的对象（第 5 节）。
- 一个文件里写本包（本游戏）的对象用短名，写别的命名空间的对象用全名。标签前加 `#`：`#qed/connectives`、`#connectives`。
- 组装成内容时一律展开成全名。内核模块、存档、检查、页面只看见全名。
- **id 一经建立就不能改。** 关卡、任务、件、词条、标签、关系、布局、章，所有对象的 id 都是包（或游戏）对外的接口，别的包、游戏、存档和覆盖文件都靠全名引用它。没有改名操作；要换 id，就新建一个、删掉旧的。要改的是显示给玩家的名字，那是文案。
- 分隔符 `/` 要进蓝图语法（`circuit/text.js` 的 `WORD`）、件名（`parts/schema.js` 的 `NAME`）和文案键（`engine/i18n.js` 的 `TEXT_KEY`）。短名的写法不变。
- 件之下仍有决策二十三的三级粒度：件 `shift`、它的设置 `shift.border`、设置的一个取值 `shift.border=wrap`，统称**项**。项是从件派生的名字，不是单独的对象。

### 3.2 标签

标签是唯一的容器，主要给开发用：把一批关卡收在一起开发，把件收成一个托盘，把几个件收成一个概念，把词条分组。

- 一个标签只装一种东西：关卡标签只装关卡，项的标签只装项，词条标签只装词条。成员是全名或同种标签（`#…`，可以嵌套，不成环）。
- **标签是集合，没有顺序。** 顺序一律由关系（3.3）和布局（3.4）给出。
- 标签可以带呈现字段（名字、说明），用于托盘的菜单、百科的分组。二级菜单就是嵌套的标签。
- 文件：`tags/<种类>/<名>.json`，种类是 `level`、`item`、`entry`，写在路径里；内容是 `{ "title"?, "desc"?, "concept"?, "values": [成员] }`。

用法：
- **凡是引用一种对象的地方，都可以直接写这种对象的标签**，组装和检查时展开成成员。不为标签另设字段。
- 关卡的 `tray` 引用一个项的标签（取代 `trays.json`）。
- 任务的 `gives`、`withholds`、`opens` 和关卡的 `adds`、`local` 写项或项的标签。
- 概念：几个件合起来是一个新概念，就是一个项的标签，标签上标 `"concept": true`（取代课程设置里的 `concept`）。

### 3.3 关系

关系是一份单独声明的有向边，不属于任何标签。

- 文件：`relations/<名>.json`，`{ "kind": "requires" | "order" | "replaces", "edges": [{ "from", "to", …属性 }] }`。`order` 可以写成 `"sequence": [a, b, c]`，等于相邻两项之间各一条边。
- 一端可以是标签，表示把标签当一个整件：连到标签，就是连到标签里没有这份关系的前置的那几个成员；从标签连出，就是从标签里没有这份关系的后续的那几个成员连出（同原来 `engine/groups.js` 的 `groupEnds`）。

| 种类 | 用在哪 | 含义 |
|---|---|---|
| `requires` | 关卡 | 先修，卡解锁；边上可以带 `required`（来源关可跳过时也要通过）。不成环 |
| `order` | 任意 | 只管显示和编号的先后，不卡解锁。偏序，内核按固定规则展开成全序：先满足边，平局按全名的字典序 |
| `replaces` | 件 | 升级与合并，取代课程设置里的 `replaces` |

**谁生效：** 所有关系一律加载即生效，没有「选用」这一步。
- 项和词条的 `order`、件的 `replaces` 对加载了它的所有游戏生效。
- 关卡的 `requires` 和 `order` 只作用在游戏放进课程的关之间：一条边两端都在课程里才有效，标签端点按放进来的成员展开。
- 游戏不想要包里的某些边，就覆盖那份关系（第 4 节：`remove` 逐条去掉，`replace` 清空重写）。

### 3.4 布局

布局是一批关卡的路线图排法，也是单独声明的对象。

- 文件：`layouts/<名>.json`，`{ "of": "#关卡标签", "rows": [[关卡 | null]] }`。一行最多三个位置，`null` 是空位。
- 布局都在包里声明。章选用一个布局；游戏要换排法，就覆盖（重排）那个布局，不另声明布局。
- 布局没排到的关，照现有的 `mapRows` 规则排在它周围（`course.js`）。

### 3.5 文案

可翻译字段照旧写 `@键`，键展开成全名。每一层自己的文案写在自己的 `i18n/<lang>.json`；覆盖别的命名空间的文案，和覆盖别的对象一样放进 `overrides/`：`overrides/<被覆盖的命名空间>/i18n/<lang>.json`，按键合并（第 4 节）。凡是改别人的东西，都在 `overrides/` 下。

### 3.6 文件按职责放，开发按对象做

```
packages/<包>/
  package.json
  levels/  pieces/  entries/              内容和行为：一个对象一个文件
  tags/<种类>/  relations/  layouts/       编排
  i18n/<lang>.json                         文案
  overrides/<命名空间>/…                    覆盖，结构和上面一样
  changes.jsonl
```

- 文件按职责分目录，好维护；开发者按对象操作，好上手。连接两者的是组装后的注册表（每个对象带来源，第 4 节）和依赖图。
- 一个对象的各部分（件的定义、它的文案、它所在的标签、它参与的关系、谁覆盖过它）散在几个目录里，studio 按对象把它们聚到一页上编辑（第 8 节）。
- 件的行为和外观不拆成两个文件：只改外观的覆盖用 `$merge` 改那几个字段。

## 4. 依赖、加载和覆盖

**依赖**
- `package.json` 加 `"uses": [包]`。只能引用 `uses` 里那些包的对象（直接依赖，不传递）。依赖不成环。依赖不受领域限制（第 7 节之后没有领域）。
- 游戏的 `game.json` 用 `"packages": [包]` 取代 `"package"`，并且要列全每个包的依赖，少了报错。

**加载顺序**：各包按依赖拓扑排序（平局按包名），游戏最后。

**覆盖**：后加载的层用同一个全名再声明一个对象，就覆盖它。不怕被改，放开：

| 对象 | 默认 | 可选 |
|---|---|---|
| 关卡、件、词条、布局、内核声明的内容种类 | 整份替换 | `"$merge": true`：按 JSON merge patch 只改写到的字段 |
| 标签、关系 | 追加成员或边 | `"replace": true` 先清空；`"remove": [...]` 逐条去掉 |
| 文案 | 按键合并，后者盖前者 | |

- 覆盖文件放在覆盖者那一层：`packages/<覆盖者>/overrides/<被覆盖的命名空间>/<种类>/<名>.json`，游戏的放在 `games/<游戏>/overrides/<命名空间>/<种类>/<名>.json`。
- **游戏层能覆盖的只有三样**：文案、关卡的关系（`requires`、`order`）、布局。游戏不能改件（包括件的设置）、关卡内容和项的标签这些决定行为的东西；要改，就做一个依赖原包的新包去覆盖。
- **包之间唯一要拦下的情况**：两个互不依赖的包覆盖了同一个对象，先后说不清，检查报错，要求其中一个依赖另一个。其余覆盖都放行。
- 组装后的内容保留每个对象的来源：哪一层声明，被哪几层覆盖过。studio 和检查都读它。
- 有了命名空间，不同的包不会意外重名；全名完全相同就是覆盖，按依赖顺序生效。所有覆盖都可以在 studio 里审计（第 8 节）。

## 5. 游戏层

章、可选、可跳过、路线图布局都是游戏编排的事，和包无关。包里没有这些字段。

游戏是加载顺序上的最后一层，职责和包不同：包负责内容和行为，游戏只做三件事——面向最终游戏的文案、关卡编排（放进哪些关、分到哪章、依赖关系怎么定）、布局的重排。

- 游戏的文件：`game.json`、`course.json`、自己的文案 `i18n/<lang>.json`、`overrides/`、`changes.jsonl`。
- 游戏不声明任何对象（关卡、件、词条、标签、关系、布局都没有）。依赖关系和布局以包里的为准，游戏要不同，只写覆盖（第 4 节，限文案、关卡关系、布局），不另写一套关卡和依赖图。
- 新的关、新的件一律放进某个包。

`games/<游戏>/course.json`：

```jsonc
{
  "chapters": [
    {
      "id": "paper",
      "title": "@…", "question": "@…",              // 章的字段
      "levels": ["#qed/paper-basics", "qed/onerow"], // 这一章的关：一个内联的关卡标签
      "layout": "qed/paper-map"                      // 选用包里的一个布局
    }
  ],
  "optional": ["#qed/paper-extras"],
  "skippable": ["qed/onerow"],
  // 开局设置：primitives、views、words、open
}
```

- 章的编号顺序：已加载的 `order` 关系（限于课程里的关）展开的全序，再用 `requires` 补；同一关只能在一章里。
- **课程设置的归属**按语义分，迁移时逐个核对：
  - 件和关卡的属性在包里声明：`replaces` 是关系；`concept` 是概念标签（3.2）；`local`（只在带来它的关里用、不解锁也不带到后面的件）和 `adds` 写在同一处，是关卡（任务）的字段。
  - 游戏怎么开局归游戏：`primitives`、`views`、`words`、`open`。
  - 件和关卡的行为游戏不能改；要不同的做法，做一个依赖原包的包去覆盖。
- 跨游戏前置保留：游戏覆盖一份 `requires` 关系，追加一条带 `game` 属性的边 `{ "from": "qed/table", "game": "qed", "to": "…" }`，表示「在游戏 qed 里通过了 qed/table」。

## 6. 包独立于游戏

- 包有自己的修改日志 `packages/<包>/changes.jsonl`。操作集可以单独打开一个包，不用借一款游戏。
- **包的试玩课程由内核生成**：
  - 包里每个关卡标签一章；不在任何关卡标签里的关单独一章，放最后。
  - 包里声明的关卡关系照常生效；`of` 指向某个关卡标签的布局，用在那一章上。
  - 件全都在手边。
  - 这样库包和还没有游戏的包也能试玩、检查。
- `npm run check -- <包>` 按这份试玩课程查一个包；不写名字时，查全部游戏，再查没有游戏玩的包。
- `opScope` 的两边改成「这一层的对象」：包的工作区只改这个包里的对象（包括它的覆盖文件），游戏的工作区只改这个游戏的。

## 7. 内核：领域并入内核

照《异星工厂》：引擎给出原型的种类，原版内容 `base` 本身也只是一个模组，模组只有数据。我们这里，内核给出全部能力（代码，走代码审查，封闭），包只有数据，从内核里挑选、组合、填参数。**「领域」这一层不再存在**：它和内核没有清楚的边界，三个领域里的代码合进内核，按模块组织；领域退化成新建包时的模板。

### 7.1 能力

- 现在三个领域（`image`、`logic`、`table`）和三个机制模板（`circuit`、`rows`、`tick-bus`）的代码拆成内核的**模块**。模块只是代码的组织单位，不是内容的归属：包不声明「属于哪个模块」，用到哪些能力看内容本身。
- 每个模块向内核注册能力。能力按种类分表，名字是 `<模块>:<名>`（冒号和内容的 `/`、项的 `.` `=` 区分开）：

| 种类 | 是什么 | 现在在哪 |
|---|---|---|
| 值类型 | 端口上流的东西：数、图像、公式、表…… | 各领域里隐含 |
| 运算 | 件的 `compute` 能调用的函数，声明输入输出的值类型和参数（类型、范围、选项、默认值） | 各领域词汇表的 `op`，如 `image_gauss` |
| 原始件 | 内核自己实现、包可以直接放进托盘的件 | 各领域词汇表的 `part` |
| 板 | 板子的机制：电路、行、时钟总线…… | `kit/scaffold/<机制>/`、各领域的 board |
| 任务种类 | 一个任务怎么玩、怎么判 | 各领域的 `mode`、`kind`、`want` |
| 内容项 | 内容直接引用的现成东西：场景、图、目标、世界、机体、诊断条件…… | 各领域词汇表其余的种类 |
| 显示 | 卡片块、读数、面板、引言图等界面件 | 各领域的 `ui/`、`widget`、`display`、`view` |
| 语言 | 内容里的小语言（公式、条件……）和它的读法 | 逻辑的 `languages` |
| 内容种类 | 内核声明、由包提供数据的对象种类（3.1），如 `wordset`、`quote`、`power`、`box` | `package.json` 的包级配置 |

- **一份词汇表，一条版本线。** 词汇表由各模块注册的能力拼成，`describe` 打印成一份 JSON。三个领域原来的版本线作废，从新的第 1 版开始；之后照旧只能增加，删改写在 `removes` 里。
- **能不能接看值类型**：件的端口写值类型，运算声明签名，检查按类型查。一款游戏、一个包可以同时用几个模块的能力；放不放得进同一块板由板和值类型决定。
- 同一个运算可以对几种值类型各有实现（比如 `add` 对数、对图像），库包里的件由此能给几种游戏共用。

### 7.2 课程模型

- 现在三个领域各有一个 `course.js`，加上 `engine/board-course.js`，是同一件事的几种实现。合成内核的**一个课程模型**：解锁、托盘、项的三级粒度、概念、`local`、`replaces`、`gives`、`opens`、`withholds`、依赖图都只算一遍。
- 原来某个领域特有的机制（逻辑的引理、修订、证出的等式成为规则，图像的训练模式……）改成内核功能，由件和关卡里写的东西触发（件写 `builds`、任务写种类），不按「哪个领域」开关。
- 检查、试玩、审计、操作集、盲玩只认这一个课程模型。`engine/contract.js` 的领域契约改成模块契约：一个模块注册的能力都能打印、能检查、能被盲玩。

### 7.3 包、模板和库包

- `package.json` 只写 `uses` 和 `vocabulary`（这个包最少需要内核词汇表的第几版，不能高于当前版本），不再写 `domain`。包级配置改成内核声明的内容种类（7.1）。
- **模板**：现在的领域退化成模板 `kit/templates/<名>/`：一份起步包，预设一组件、参数、托盘标签、关卡样例和起步课程。`npm run new-package -- <包> --template <名>` 复制一份起步。模板是复制，不被依赖。
- **库包**：要几个包共用、改一处处处生效的东西，做成库包让大家依赖，不靠复制模板。迁移时至少做一个：四则运算的库包，被原来属于两个不同领域的包依赖。

### 7.4 件和设置

- 「设置」不再是一种对象，也没有设置标签。件的设置直接写在件里：

  ```jsonc
  { "inputs": [{ "name": "in", "type": "image" }], "compute": "image:gauss(in, $sigma, $border)",
    "settings": { "sigma": { "min": 0.5, "max": 2.5 }, "border": {} } }
  ```

- 对应运算参数的设置，控件、选项、范围、默认值来自运算的参数声明，件只写要收窄或改的部分（标签、范围、默认值、去掉的选项）；空对象表示照运算的声明。原来被几个件共用的设置（如 `border`）因此自然共用。
- 不对应运算参数的设置（选公式的 `tree`、选运算符的 `arith_op`）在件里写全。
- 项照旧从件派生：`shift.border`、`shift.border=wrap`。

## 8. Studio

- **关卡设计工作区按包打开**。左栏按种类列对象：关卡、件、词条、标签、关系、布局（和内核声明的内容种类）。每个对象标出它来自哪一层、被谁覆盖过。别的包的对象可以一键「在本包覆盖」。
- **按对象编辑**：打开一个对象，一页上是它的定义、文案、所在的标签、参与的关系、谁覆盖过它（3.6），各部分写回各自的文件。
- **编辑器**：
  - 标签编辑器：成员的增删和嵌套。
  - 关系板：沿用现在的接线板（`ArrangementBoard.jsx`）；`order` 也能在板上连。
  - 布局编辑器：路线图视图，沿用原来 `ChapterBoard.jsx` 的做法。
  - 原来的 `GroupBoard.jsx` 由这三样取代。
- **内核能力**只读浏览：运算、原始件、内容项各自的说明和参数，供写件时查。
- **游戏编排工作区**（和关卡设计工作区分开，对应两种职责）：
  - 章的成员可以是关或标签，章选用布局，可选、可跳过。
  - 关卡关系的覆盖：在接线板上加边、去边，写成对包里关系的覆盖。
  - 布局的覆盖：在路线图上重排，写成对包里布局的覆盖。
  - 文案：游戏自己的文案，和对包里文案的覆盖（写进 `overrides/<命名空间>/i18n/`）。
  - 件、关卡内容在这里只读。
- **覆盖审计**：两个工作区都能列出这一层看得见的全部覆盖：被覆盖的对象、谁覆盖、覆盖前后的差别，可以从这里跳到对象本身。

## 9. 检查

- 引用：未声明依赖的引用、找不到的全名、标签成员种类不符、标签嵌套成环、关系成环（`requires`、`order` 各自）、布局一行超过三个位置或画在前置之上，都报错。
- 类型：件的端口和运算签名的值类型不符、件的设置不在运算参数里又没写全，报错。
- 覆盖：两个互不依赖的层覆盖同一个对象，报错。
- 游戏层：声明了对象，或覆盖了文案、关卡关系、布局以外的东西，报错。
- 部分游戏照现有规则：游戏只查它放进来的关；托盘（现在是项的标签）上的项有没有关带来，只在放进了整个包的游戏上判断。
- 现有四款游戏除名字变成全名外，检查输出不变。这是每一步的验收前提。
