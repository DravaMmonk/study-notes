# 空壳内核：机制全部进包

**这份文档是这项开发的唯一依据。** `games/DESIGN.md` 里关于内核、模块、能力、件和阶段、托盘、Studio 编辑器的说法，凡是和本文冲突的，以本文为准。全部做完后，把结果写回 `games/DESIGN.md`，删掉这份文档。

## 1. 目标

- **内核是空壳**：只有平台（读写内容、操作集、检查的框架、Studio 的外壳）和游戏流程（点进关卡、在主区互动、检验结果、通关解锁新任务）。它不知道任何具体的玩法。
- **一切机制都在包里**：板、件、接线、求值、值的类型、运算、判定、小语言、实验台、主区的界面，都由包里的代码实现。包作者要新机制，就在自己的包里写。
- **加一个学科或一种玩法，只加包，不改内核。** 内核只有在游戏流程或平台本身要变时才改。

这是把 `games/kit/modules/` 拆成「机制归内核」的方向推翻重来：领域代码和通用机制都不留在内核，复杂的原语也整块放在包里，不拆成更细的原语。

## 2. 起点（提交 `3df96b6` 时）

- `games/kit/` 约 6.1 万行代码：`engine/` 1.16 万（平台 + 课程模型 + 电路求值 + 件和阶段）、`modules/` 2.1 万（`circuit`、`rows`、`tick-bus`、`image`、`logic`、`table`）、`circuit/` 5.4 千（蓝图文本、画板编辑器）、`shell/` 7.3 千（游戏外壳，其中大块是电路玩法的界面）、`studio/` 9 千、其余是视图、流水线、界面文案。
- 内核里和具体玩法缠在一起的：`engine/circuit.js`、`boards.js`、`board-works.js`、`parts/`、`pieces.js`、`piece-stages.js`、`trays.js`、课程模型里件、托盘、阶段、工坊的部分，`shell/` 里的电路屏、工作台、件册、训练控件，`circuit/` 整个目录。
- Codex 的盘点（`module-audit`）显示：六个模块里机制、实例、展示混在一起；核心的图求值已经是同一份（`engine/circuit.js`）。

## 3. 三层

| 层 | 是什么 | 装什么 | 谁改 |
|---|---|---|---|
| **内核** | 空壳 | 平台 + 游戏流程 + 插件协议 | 只在流程或平台要变时改 |
| **包** | 数据，可以带代码（`module/`） | 机制（玩法、值、运算、判定、界面）和内容（关卡、件、实例……） | 包作者 |
| **游戏** | 纯数据 | 选用包、章、路线图、文案、只覆盖文案和关卡关系 | 编排者 |

包没有类型之分，不严格区分「玩法包」和「内容包」：
- **大玩法单独成包**：比如拼件接线（`circuit`）、逻辑证明（`logic`）、文字作答（`text`）。相关的几种玩法共用很多代码时放在一个包里（逻辑包里的真值表、证明板、证明机）。
- **任何包都可以带代码**：内容为主的包也可以在自己的 `module/` 里实现一些小玩法和小改动，比如 vision-complete 专用的几个实验台。只有一个包用的东西就放在那个包里；第二个包也要用时，再提到被依赖的包里。
- **被别人依赖的包叫库**，只是一个角色：可以只带玩法（`circuit`），可以只带内容（`arithmetic`），也可以两者都有。
- **包与包之间只有依赖和覆盖，没有继承**：依赖写在 `uses`（只能引用直接依赖的包，不传递），改别人的对象写覆盖文件。要在别的包的基础上做变体，就依赖它再覆盖；要扩展别的包的玩法，就依赖它并调用它导出的接口。「后者在前者之上叠加」只存在于对象内部（关卡和任务、件和阶段）。
- 关卡的每个任务写它用哪种玩法（`<包>:<玩法>`，比如 `circuit:board`、`text:answer`）；同一款游戏里不同关可以用不同包的玩法。

## 4. 内核留什么

### 4.1 平台

- **内容系统**：全名和命名空间，按种类的注册表，一对象一文件的读写，按依赖加载各层、覆盖、冲突检查、来源记录，组装。内核自带少数通用种类（关卡、任务、标签、关系、词条、百科分组、文案），它们的结构由内核定；其余种类由包用数据声明（第 5.3 节）。
- **操作集**：按层打开工作区、变更集、修改日志和撤销、id 不能改；CLI、MCP、Studio 共用。
- **检查的框架**：schema、引用、依赖、覆盖冲突、课程能玩通；关卡对不对，交给提供这种玩法的包去判（参考解通过、naive 失败），内核只负责调用和汇总。
- **兼容性**：每个包的公开面（数据和代码一视同仁）改动前后自动对比，分「只增加 / 破坏 / 行为变了」，列出受影响的包和游戏并跑它们的检查；版本号合并进主线时自动记（第 8 节）。
- **Studio 的外壳**：三个工作区、三栏、底部折叠栏，以及和玩法无关的部分——左栏按种类列资源——可选的种类是内核自带的几种加上所有已加载包声明的种类，默认列哪些由包里的 `studio-left` 种类标签决定，每个人还可以自己调（5.4）；「种类」本身也在左栏列出，右栏用 schema 编辑器改它的字段定义、右栏按 schema 的 JSON 编辑器和原始 JSON（任何有 schema 的种类都能编辑）、文案工作区、编排工作区（章、路线图、关卡顺序、依赖）、覆盖审计、修改日志、对比、检查结果。中栏的关卡预览和专门的编辑器由玩法包提供（第 5 节）；没有专门编辑器的种类只用右栏编辑。
- **文案**：各层语言表的合并；内核只带通用界面用语。

### 4.2 游戏流程

- **地图**：章、路线图（章的 `rows`）、关卡的开关状态。
- **关卡页的框架**：标题、导语、任务列表、**主区的挂载点**、检验按钮、结果面板、通关反馈。
- **进度**：任务和关卡按 `requires` 和章的顺序解锁；通过一个任务就记下来，解锁后面的任务和关卡；存档按关卡、任务的全名记，作品本身的格式由包定。
- **试玩和盲玩的入口**：单关试玩、盲玩驱动；具体怎么操作主区由包的钩子提供。
- **主题、语言、手机布局**。

内核**不**知道：板、件、接线、托盘、阶段、工坊、值的类型、运算、证明、表格、实验台。

## 5. 插件协议：包的代码接到哪里

包的代码放在 `packages/<包>/module/`，入口 `module.js` 导出一个 `register(kernel)`，向内核登记下面几样。每样都有一个名字（`<包>:<名>`），关卡、任务、Studio 通过这个名字找到它。

| 协议 | 包提供什么 | 内核怎么用 |
|---|---|---|
| **玩法** `play` | 主区的界面组件；作品的初始值、读取、保存；运行（把作品跑一遍，产出报告）；判定（这次通过没有，得分，失败在哪）；Studio 里的编辑模式（可选：点画面上的某处告诉内核是哪个字段） | 关卡页把主区交给它；检验按钮调运行和判定；进度按判定结果走；Studio 中栏用它预览关卡 |
| **种类的含义** `kind` | 把行为挂到某个已声明的种类名上（比如 `circuit` 读托盘、件来决定玩家手里有什么）；种类的结构不在这里，在数据里（5.3） | 玩法运行、检查时按种类名调用 |
| **字段扩展** | 给关卡、任务加的字段和它们的 schema（比如 `circuit` 的 `tray`、`gives`、`adds`、`local`），写成数据（5.3） | 内核按 schema 校验和存储，不理解含义 |
| **派生状态** `state` | 根据「已通过的任务」算出的玩法状态（比如手里有哪些件、每个件升到第几个阶段、托盘上摆什么） | 内核的进度只记通过了哪些任务；进关卡时把派生状态交给玩法 |
| **检查** `check` | 这种玩法的关卡怎么检查：参考解、naive 解、玩法自己的一致性检查 | `npm run check` 调用、汇总 |
| **编辑器** `editor` | Studio 中栏的编辑器（比如件的板、托盘编辑器、阶段链） | Studio 按对象种类挂上 |
| **盲玩** `agent` | 盲玩时怎么观察和操作主区 | 盲玩驱动调用 |
| **显示** `display`（可选） | 给别的包复用的展示组件 | 别的包通过 `uses` 使用 |

包的代码可以用的只有两样：内核公开的 API，以及 `uses` 里那些包导出的公开接口。

### 5.1 各种内容的处理逻辑放在哪

标准：和玩法无关、任何游戏都用得上的，在内核；只对某一类玩法有意义的，跟着提供这类玩法的包走。

| 内容 | 放哪 |
|---|---|
| 关卡、任务的基本字段（标题、导语、任务列表、用哪种玩法） | 内核 |
| 标签（任何种类的通用容器：展开、嵌套、成环检查） | 内核 |
| 关系 `requires`（解锁）、`order`（Studio 里的显示顺序） | 内核 |
| 词条、百科分组、百科页 | 内核 |
| 文案、覆盖、依赖；章、路线图（游戏层） | 内核 |
| 件、阶段、托盘、工坊；关系 `replaces`；任务和关卡上关于「手里有哪些件」的字段（`tray`、`gives`、`withholds`、`opens`、`awards`、`adds`、`local`）；从进度算出手里有哪些件 | `circuit` 包 |
| 词组、引语、`power`、`box` 等配置类内容种类 | 用到它们的包（`logic`、`image`） |

别的包要做拼件类玩法，就依赖 `circuit`，用它的件、托盘、阶段这些内容种类。

### 5.2 纯文字的游戏

不碰件、不碰内核：一个提供「文字作答」的包（`text`）——主区显示题目和输入框或选项，作品是答案，判定按关卡里配的规则（完全相同、忽略大小写和空格、正则、数值带容差、几个可接受答案任选其一），检查要求参考答案通过、写在关卡里的错误答案被判错。课程的关卡是数据，游戏选用它和内容包、排好章。Studio 里左栏列关卡，中栏是这个玩法的预览，右栏改题目和答案，文案工作区校对文字。

### 5.3 种类的结构是数据

一个对象种类分两部分：**结构**（字段和类型、能被谁引用、覆盖方式、哪些字段是文案、在 Studio 左栏怎么列）是声明，写成数据；**含义**（这种对象在玩法里起什么作用）才需要代码，由 `kind` 协议挂上去。

- 包里 `kinds/<名>.json` 声明一种对象：字段的 schema（用内核 schema 的 JSON 写法，和 `describe` 打印出来的一样）、可被哪些种类引用、新的关系种类（比如 `replaces` 的端点是件）、覆盖方式（整份替换或追加成员）、文案字段、左栏的名字、图标、分组方式。种类的全名是 `<包>/<名>`，别的包依赖它就能用。
- 这种对象放在包里对应的目录（比如 `scenes/<名>.json`），和关卡、件一样走内容系统：全名、标签、关系、覆盖、来源、文案工作区、兼容性判断全部自动适用。
- **每个种类都能打标签，不用登记**：标签的种类就是所有已声明的种类。包里声明的种类，标签放在以种类全名为路径的目录下——`story` 包的 `scene` 种类，标签写在 `tags/story/scene/<名>.json`；内核自带的种类沿用短路径（`tags/level/`、`tags/entry/`、`tags/kind/`）。件也是这样：它是 `circuit` 包声明的 `circuit/piece`，标签在 `tags/circuit/piece/`，和包作者自己声明的种类没有区别。这和《我的世界》每个注册表（包括模组加的）都自带标签、模组注册表的标签放在 `tags/<模组>/<注册表>/` 下是同一种做法。
- 有些种类不需要任何代码：比如「人物」「例题」「参考资料」，作者自己定义结构，用来组织内容、写文案、被关卡引用。
- 字段扩展也写成数据：`kinds/` 里声明给关卡或任务加哪些字段。
- 种类的定义可以在 Studio 里改，经操作集写回 `kinds/<名>.json`。它影响这个种类已有的全部对象，所以是公开面上的改动（第 8 节）：兼容性判断指出哪些对象因此不合法、哪些依赖方受影响，同一次改动里用操作集把这些对象迁过去。
- 在 Studio 里给一个种类加字段，如果没有代码去读它，它只是存着的值，不起作用；含义永远在代码里。内核自带的几种的结构由内核定，包不能改，只能对关卡、任务做字段扩展。

### 5.4 开发层的标签：左栏和模板

标签只是集合，没有自己的属性。分界看有没有属性，不看玩家看不看得到：

- **只是「属于某一类」的标记，用约定名字的标签**：比如「这个对象是模板」「这个种类默认列在左栏」，也可以是玩法里的标记，比如「这些件不出现在件册里」。代码按约定的名字去读这个标签，看某个对象在不在里面——这和《我的世界》代码查 `climbable`、`beacon_base_blocks` 是同一种用法。
- **有自己属性的分组，单独声明对象，再引用标签**：托盘（名字、说明、工坊、二级菜单）、百科分组（标题、说明）、关系都是。这和《我的世界》的附魔是带属性的对象、它能附在哪些物品上引用一个标签是同一种结构。
- **约定标签名要登记**：按约定名字读标签的代码，登记它读的名字和成员必须是什么种类，由读它的那一方登记，不是内核。Studio 登记 `studio-left`（成员是种类）和 `templates`（每个种类各一个）；`circuit` 包登记它读的件标签；包作者给自己的种类写了读某个标签名的代码，就在自己的协议里登记。检查据此报出没人读的约定名、拼错的名字、种类不对的成员；Studio 在左栏标出这些有作用的标签。《我的世界》没有这一层，标签名拼错只会悄悄不起作用，这里补上。「能不能打标签」不用登记（5.3），只有「谁按名字读它」要登记。

开发工具用到的两个约定标签：

- **种类可以进标签**：标签的种类多一种 `kind`，成员是种类的全名。
- **左栏默认列哪些种类**：Studio 读包里名为 `studio-left` 的种类标签（`tags/kind/studio-left.json`），按它和它的 `order` 关系决定构建工作区左栏默认列出哪些种类、什么顺序；一款游戏依赖的几个包的设置合并起来。每个人还可以在 Studio 里改自己这一份（存在浏览器里），不写进包。没有任何设置时列出全部种类。
- **模板**：模板是开发工具，不是关卡专属的东西。任何对象都可以存成模板：把它放进这个种类名为 `templates` 的标签（比如 `tags/level/templates.json`、`tags/circuit/piece/templates.json`）。新建对象时，「从模板新建」列出当前包和它依赖的包里这个种类的模板，选一个，复制成一个新 id 的对象再改。
  - 模板本身是完整、合法的对象，照常走检查，所以种类的结构变了，模板也会跟着被检查、被迁移，不会悄悄过期。
  - 模板不放进任何课程，玩家看不到；一个关卡模板没有被任何章放进来，就只是一份可以复制的起点。
  - Studio 里任何对象都有「存为模板」（加进 `templates` 标签）和「从模板新建」两个动作。
- **新建一个包**：从一个现有的包复制一份起步（`npm run new-package -- <新包> --from <包>`）。原来 `kit/templates/` 里各玩法的起步内容，改成各玩法包里的模板对象，或者一个专门用来复制的起步包。

## 6. 包的代码要守的边界

1. **只实现协议**：登记玩法、内容种类、检查、编辑器、盲玩、显示；不改内核行为，不绕开进度和检查。
2. **只能 import 内核公开的 API 和 `uses` 里的包导出的接口**，不能伸进别的包的内部文件；检查要拦。
3. **判定必须确定**：运行和判定不访问时钟、网络、文件；随机只能来自传入的种子；同样的作品同样的结果。界面代码不受这条限制，但不能影响判定。
4. **契约测试**：每个带代码的包都要通过——能登记、能检查自己的关卡、能盲玩、能和别的包一起组装。
5. **代码和数据分两条路改**：数据经操作集和 Studio；`module/` 只经代码提交和审查，操作集和 Studio 不能写它。
6. **内核零内容能跑**：`packages/` 和 `games/` 清空、只留模板时，内核的测试全过，Studio 和游戏外壳能打开，`check` 能跑。

包名是建议，开发时按代码定，答复里列出。

| 去向 | 搬进来的 |

复杂的原语（卷积、频域、证明核、训练、逐格递推……）整块随包走，不拆。

## 8. 兼容性与版本

- 包的**公开面**：一切能被别的包、游戏、覆盖文件用全名引用的东西——关卡、任务、件和阶段、词条、标签、关系、托盘、百科分组、各种内容种类的对象、种类本身的结构定义（`kinds/`）、文案键，以及代码登记的玩法、内容种类、检查、编辑器、显示的名字和接口。
- 改动后自动判断三级：**只增加**（新对象、可选字段、新登记项）；**破坏**（删掉有人引用或覆盖的东西，改了接口或 schema 让别人不再合法）；**行为变了**（结构没变，依赖方的检查结果变了）。前两级看结构，第三级跑依赖方的检查。
- 有破坏或行为变了，同一个提交里受影响的一方也要通过。
- 版本号不手编：合并进主线时由工具按这次的最高级别自动记一笔；内核接口（插件协议）同样如此，并行分支不再撞号。
- 包还都在这个仓库里，所以不需要依赖范围；包要分开发布时，再用这份记录生成正式版本。

## 9. 检查

- 内核：schema、引用（只引用 `uses` 里的包）、约定标签名（有人登记、成员种类对）、标签和关系的成环、覆盖冲突、游戏层越界、课程能玩通（解锁可达）、id 不变、包代码的 import 边界。
- 包：自己那类玩法的关卡检查（参考解、naive 解、玩法内的一致性），通过 `check` 协议接入。
- 技术层和规范层照旧分开：教学节奏等规范不进检查。
- 现有四款游戏的检查输出，除了提示来自哪个包的写法外，不变。这是每一步的验收前提。

## 10. 实施步骤

每一步一个或几个提交，直接合入 main；步内硬切换，不留旧路径、兼容层、死代码。

1. **锁住行为。** 存四款游戏和四个包的检查基线、逐步报告、参考解和 naive 解的结果；给 state-graph 的手工玩法补上纯判定，让它能进对照。
2. **定插件协议，内核开放包的代码。** `module/` 的加载、`register` 协议（玩法、内容种类、字段扩展、派生状态、检查、编辑器、盲玩、显示）、import 边界检查、契约测试；用新写的 `text`（文字作答）作为第一个插件验证——它和电路毫无关系，证明协议不依赖件体系，做完就是一个模板，也是零内容验收时的最小玩法。
3. **`circuit` 出内核。** 电路求值、件、托盘、阶段、工坊、蓝图文本、画板编辑器、电路屏，连同课程模型里对应的部分，搬进 `packages/circuit`；内核的进度只剩任务和关卡的解锁。验收：四款游戏不变。
4. **`rows`、`tick-bus` 出内核。**
5. **`image` 出内核**，专用实验台、场景进 vision-complete / comp90086。
6. **`table` 出内核**，专用世界、机器人进 state-graph。
7. **`logic` 出内核**，专用部分进 qed。
8. **Studio 的编辑器改成由包提供**；内核的 Studio 只剩外壳。
9. **兼容性自动判断和自动版本**（第 8 节）。
10. **零内容验收和写回手册**：清空内容后内核能跑；改写 `DESIGN.md`，删掉这份文档。

## 11. 已定

- 只有一个包用的东西放在那个包里，第二个包要用时再提到被依赖的包里（第 3 节）。
- `circuit` 先作为一个包，件、托盘、阶段、工坊、蓝图文本、画板编辑器都在里面，以后有需要再拆。
- 百科页留在内核。
- 不做内核里的 AST 或受限脚本语言；复杂原语整块随包走，不拆。

## 12. 约定

- 行为不变：每一步前后对比基线（`npm run -s check -- <游戏>`、`npm run -s check -- --package <包>`）。
- 测试：内核测试只用测试里现写的小内容或模板；每个带代码的包有自己的测试。
- 改内容只经操作集；包的代码只经代码提交。
- 界面：桌面和手机都看；不加次要标签和说明文字。
- 提交和推送照仓库的写法；main 上同时有别的会话在推，推之前先拉取再变基。
