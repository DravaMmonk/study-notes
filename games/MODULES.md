# 空壳内核：机制全部进包

**这份文档是这项开发的唯一依据。** `games/DESIGN.md` 里关于内核、模块、能力、元件和阶段、托盘、Studio 编辑器的说法，凡是和本文冲突的，以本文为准。全部做完后，把结果写回 `games/DESIGN.md`，删掉这份文档。

## 1. 目标

- **内核是空壳**：只有平台（读写内容、操作集、检查的框架、Studio 的外壳）和游戏流程（点进关卡、在主区互动、检验结果、通关解锁新任务）。它不知道任何具体的玩法。
- **一切机制都在包里**：板、元件、接线、求值、值的类型、运算、判定、小语言、实验台、主区的界面，都由包里的代码实现。包作者要新机制，就在自己的包里写。
- **加一个学科或一种玩法，只加包，不改内核。** 内核只有在游戏流程或平台本身要变时才改。

这是把 `games/kit/modules/` 拆成「机制归内核」的方向推翻重来：领域代码和通用机制都不留在内核，复杂的原语也整块放在包里，不拆成更细的原语。

## 2. 起点（提交 `3df96b6` 时）

- `games/kit/` 约 6.1 万行代码：`engine/` 1.16 万（平台 + 课程模型 + 电路求值 + 元件和阶段）、`modules/` 2.1 万（`circuit`、`rows`、`tick-bus`、`image`、`logic`、`table`）、`circuit/` 5.4 千（蓝图文本、画板编辑器）、`shell/` 7.3 千（游戏外壳，其中大块是电路玩法的界面）、`studio/` 9 千、其余是视图、流水线、界面文案。
- 内核里和具体玩法缠在一起的：`engine/circuit.js`、`boards.js`、`board-works.js`、`parts/`、`pieces.js`、`piece-stages.js`、`trays.js`、课程模型里元件、托盘、阶段、工坊的部分，`shell/` 里的电路屏、工作台、元件册、训练控件，`circuit/` 整个目录。
- Codex 的盘点（`module-audit`）显示：六个模块里机制、实例、展示混在一起；核心的图求值已经是同一份（`engine/circuit.js`）。

## 3. 三层

| 层 | 是什么 | 装什么 | 谁改 |
|---|---|---|---|
| **内核** | 空壳 | 平台 + 游戏流程 + 插件协议 | 只在流程或平台要变时改 |
| **包** | 数据，可以带代码（`core/`、`view/`） | 机制（玩法、值、运算、判定、界面）和内容（关卡、元件、实例……） | 包作者 |
| **游戏** | 纯数据 | 选用包、章、路线图、文案、只覆盖文案和关卡关系 | 编排者 |

包没有类型之分，不严格区分「玩法包」和「内容包」：
- **大玩法单独成包**：比如元件接线（`circuit`）、逻辑证明（`logic`）、文字作答（`text`）。相关的几种玩法共用很多代码时放在一个包里（逻辑包里的真值表、证明板、证明机）。
- **任何包都可以带代码**：内容为主的包也可以在自己的 `core/`、`view/` 里实现一些小玩法和小改动，比如 vision-complete 专用的几个实验台。只有一个包用的东西就放在那个包里；第二个包也要用时，再提到被依赖的包里。
- **被别人依赖的包叫库**，只是一个角色：可以只带玩法（`circuit`），可以只带内容（`arithmetic`），也可以两者都有。
- **包与包之间只有依赖和覆盖，没有继承**：依赖写在 `uses`（只能引用直接依赖的包，不传递），改别人的对象写覆盖文件。要在别的包的基础上做变体，就依赖它再覆盖；要扩展别的包的玩法，就依赖它并调用它导出的接口。「后者在前者之上叠加」只存在于对象内部（关卡和任务、元件和阶段）。
- 关卡的每个任务写它用哪种玩法（`<包>:<玩法>`，比如 `circuit:board`、`text:answer`）；同一款游戏里不同关可以用不同包的玩法。

## 4. 内核留什么

### 4.1 平台

- **内容系统**：全名和命名空间，按对象类型的注册表，一对象一文件的读写，按依赖加载各层、覆盖、冲突检查、来源记录，组装。内核自带少数通用对象类型（关卡、任务、标签、关系、词条、百科分组、文案），它们的结构由内核定；其余对象类型由包用数据声明（第 5.3 节）。
- **操作集**：按层打开工作区、变更集、修改日志和撤销、id 不能改；CLI、MCP、Studio 共用。
- **检查的框架**：schema、引用、依赖、覆盖冲突、课程能玩通；关卡对不对，交给提供这种玩法的包去判（参考解通过、naive 失败），内核只负责调用和汇总。
- **兼容性**：每个包的公开面（数据和代码一视同仁）改动前后自动对比，分「只增加 / 破坏 / 行为变了」，列出受影响的包和游戏并跑它们的检查；版本号合并进主线时自动记（第 8 节）。
- **Studio 的外壳**：三个工作区、三栏、底部折叠栏，以及和玩法无关的部分——左栏按对象类型列资源——可选的对象类型是内核自带的几种加上所有已加载包声明的对象类型，默认列哪些由标签 `kernel/studio-left` 决定，每个人还可以自己调（5.4）；任何对象都能复制成新对象（5.5）；「对象类型」本身也在左栏列出，右栏用 schema 编辑器改它的字段定义、右栏按 schema 的 JSON 编辑器和原始 JSON（任何有 schema 的对象类型都能编辑）、文案工作区、编排工作区（章、路线图、关卡顺序、依赖）、覆盖审计、修改日志、对比、检查结果。中栏的关卡预览和专门的编辑器由玩法包提供（第 5 节）；没有专门编辑器的对象类型，中栏列出它的字段，在右栏编辑。
- **文案**：各层语言表的合并；内核只带通用界面用语。

### 4.2 游戏流程

- **地图**：章、路线图（章的 `rows`）、关卡的开关状态。
- **关卡页的框架**：标题、导语、任务列表、**主区的挂载点**、检验按钮、结果面板、通关反馈。
- **进度**：任务和关卡按 `requires` 和章的顺序解锁；通过一个任务就记下来，解锁后面的任务和关卡；存档按关卡、任务的全名记，作品本身的格式由包定。
- **试玩和盲玩的入口**：单关试玩、盲玩驱动；具体怎么操作主区由包的钩子提供。
- **主题、语言、手机布局**。

内核**不**知道：板、元件、接线、托盘、阶段、工坊、值的类型、运算、证明、表格、实验台。

## 5. 插件协议：包的代码接到哪里

包的代码按运行环境分两个目录，各有一个入口，都导出 `register(kernel)`，向内核登记下面几样。每样都有一个名字（`<包>:<名>`），关卡、任务、Studio 通过这个名字找到它。

```
packages/<包>/
  core/   无界面，入口 core/index.js：玩法的核心、对象类型的含义、派生状态、检查、盲玩、无界面导出
  view/   界面，入口 view/index.jsx：玩法的视图、编辑器、显示、样式和图标、界面导出
  kinds/ parts/ levels/ tags/ i18n/ …   数据，两边都不属于
```

- **按目录分，不拆成两个包**：核心和视图共用玩法名、公开面、`uses`、覆盖和 Studio 里的包列表，登记要配对；没有「只要核心不要视图」的用法，单独加载核心靠目录就够了。
- **谁加载什么**：检查、基线、盲玩只加载 `core/index.js`，在 Node 里跑；游戏和 Studio 两个都加载。
- **玩法两边各登记一半**，用同一个玩法名：`core/` 登记作品的初始值、读写、规范化、运行、判定；`view/` 登记主区界面和 Studio 编辑模式、预览。只有视图没有核心算错；只有核心没有视图，在游戏用到它时报错。其余协议只在一边登记（下表「入口」一列）。
- **导出也分两份**：别的包 import `<包>` 拿到 `core/` 的导出（比如 `circuit` 的 `grants.register`、板的求值和接线），import `<包>/view` 拿到 `view/` 的导出（电路板组件、读数、托盘卡片）。内核同样分两份：无界面 API（内容系统、进度、检查框架）和界面工具（外壳、表格、表单字段这些共用组件）。
- 这和《我的世界》的 Fabric 模组把客户端代码放进单独的 `src/client/`、编译时拦住公共代码引用客户端类，《异星工厂》模组把原型数据和运行时逻辑分成 `data.lua`、`control.lua` 是同一个思路：一个模组里分目录，不拆模组。

| 协议 | 入口 | 包提供什么 | 内核怎么用 |
|---|---|---|---|
| **玩法** `play` | 两边 | `core/`：作品的初始值、读取、保存；运行（把作品跑一遍，产出报告）；判定（这次通过没有，得分，失败在哪）。`view/`：主区的界面组件；Studio 里的编辑模式（可选：点画面上的某处告诉内核是哪个字段） | 关卡页把主区交给它；检验按钮调运行和判定；进度按判定结果走；Studio 中栏用它预览关卡 |
| **对象类型的含义** `kind` | `core/` | 把行为挂到某个已声明的对象类型名上（比如 `circuit` 读托盘、元件来决定玩家手里有什么）；对象类型的结构不在这里，在数据里（5.3） | 玩法运行、检查时按对象类型名调用 |
| **字段扩展** | 数据 | 给关卡、任务加的字段和它们的 schema（比如 `circuit` 的 `tray`、`gives`、`adds`、`local`），写成数据（5.3） | 内核按 schema 校验和存储，不理解含义 |
| **派生状态** `state` | `core/` | 根据「已通过的任务」算出的玩法状态（比如手里有哪些元件、每个元件升到第几个阶段、托盘上摆什么） | 内核的进度只记通过了哪些任务；进关卡时把派生状态交给玩法 |
| **检查** `check` | `core/` | 这种玩法的关卡怎么检查：参考解、naive 解、玩法自己的一致性检查 | `npm run check` 调用、汇总 |
| **编辑器** `editor` | `view/` | Studio 中栏的编辑器（比如元件的板、托盘编辑器、阶段链） | Studio 按对象类型挂上 |
| **盲玩** `agent` | `core/` | 盲玩时怎么观察和操作主区 | 盲玩驱动调用 |
| **显示** `display`（可选） | `view/` | 给别的包复用的展示组件 | 别的包通过 `uses` 使用 |

包的代码可以用的只有两样：内核公开的 API，以及 `uses` 里那些包导出的公开接口。

### 5.1 各种内容的处理逻辑放在哪

标准：和玩法无关、任何游戏都用得上的，在内核；只对某一类玩法有意义的，跟着提供这类玩法的包走。

| 内容 | 放哪 |
|---|---|
| 关卡、任务的基本字段（标题、导语、任务列表、用哪种玩法） | 内核 |
| 标签（任何对象类型的通用容器：展开、嵌套、成环检查） | 内核 |
| 关系 `requires`（解锁）、`order`（Studio 里的显示顺序） | 内核 |
| 词条、百科分组、百科页 | 内核 |
| 文案、覆盖、依赖；章、路线图（游戏层） | 内核 |
| 元件、工坊；关系 `replaces`；发放机制：阶段、托盘、任务和关卡上关于「手里有什么」的字段（`tray`、`gives`、`withholds`、`opens`、`awards`、`adds`、`local`）、从进度算出手里有什么 | `circuit` 包 |
| 词组、引语、`power`、`box` 等配置类对象类型 | 用到它们的包（`logic`、`image`） |

别的包要做元件接线类玩法，就依赖 `circuit`，用它的元件、托盘、阶段这些对象类型。

**不再有「件」这个统称。** 「件」原本是想给各种玩法一个共用的「玩家手里的东西」，好让内核统一管理；对象类型成了可以声明的对象以后，每种玩法声明自己的对象类型就够了，内核不需要这个统称。
- 元件是 `circuit` 包声明的对象类型 `circuit/part`：对象在 `parts/<名>.json`，文案键 `@part.<名>.…`，阶段是元件内部的 `stages`。《证明完毕》的规则、《视觉完备》的运算、《状态之图》的封装元件都是元件。
- 词条是内核的对象类型 `entry`，在 `entries/`。
- 《证明完毕》填句子条用的公式连接词（∧ ∨ ¬ → ↔ ∀ ∃ ⊥）不上板、没有运算，不是元件：它们是 `logic` 包声明的对象类型「符号」`logic/symbol`，在 `symbols/<名>.json`，文案键 `@symbol.<名>.…`。
- 别的玩法要发给玩家什么，就声明自己的对象类型、用自己的目录，不借元件的壳。
- **发放机制对登记过的对象类型通用**：`circuit` 包提供的发放机制不只管元件，任何登记为「可发放」的对象类型都能用（下面 5.1.1）。元件和符号都这样登记。

#### 5.1.1 发放机制

「手里有什么」（`adds`、`gives`、`withholds`、`opens`、`awards`、`local`、托盘、阶段）不是新的内核协议，是 `circuit` 包用现有协议拼出来、再作为导出接口给别的包用的能力。内核只存字段、记通过了哪些任务，不知道「发放」。

| 部分 | 协议 | 提供者 |
|---|---|---|
| 关卡、任务上的 `tray`、`adds`、`gives`、`withholds`、`opens`、`awards`、`local` | 字段扩展（数据） | `circuit` |
| 被发放对象上的 `stages` | 字段扩展，加到每个登记过的对象类型上 | `circuit` |
| 托盘 `trays/` | 对象类型声明（数据） | `circuit` |
| 从已通过的任务算出手里有什么、每个对象升到第几个阶段 | 派生状态 `state` | `circuit` |
| 参考解只用可用的对象、托盘成员有关卡带来 | 检查 `check` | `circuit` |
| 托盘编辑器、阶段链 | 编辑器 `editor` | `circuit` |
| 主区按手里有什么显示、拒收不可用的对象 | 玩法 `play` | 用它的包（比如 `logic`） |

- **登记用代码**，经 `circuit` 导出的接口：登记时要给出「这份作品用到了哪些对象」，因为作品的形状只有用它的玩法知道，`circuit` 检查参考解时要靠它。所以不用约定标签。

  ```js
  // packages/logic/core/index.js
  import { grants } from 'circuit'
  export function register(kernel) {
    grants.register({ type: 'logic/symbol', used: (work) => symbolsIn(work) })
  }
  ```

  元件由 `circuit` 自己用同一个接口登记。
- **引用**：发放字段直接写对象全名，元件和符号可以混写（`"adds": ["qed/formulaAnd", "qed/andI"]`）；`circuit` 在登记过的对象类型里找。同一个名字同时是两种可发放对象类型的对象，检查报歧义（和标签名不能跨成员对象类型重名同理）；名字带包的命名空间，只在同一个包里可能撞。
- **字段的类型**：引用字段的 schema 类型是「任一可发放对象」，由 `circuit` 提供，内核照 schema 校验。
- **阶段**：任何登记过的对象都可以写 `stages`，引用方式和元件一样。
- **托盘**：成员可以是任何可发放对象，一个托盘里能同时有元件和符号。
- **派生状态**按对象类型分开交给玩法（`{ "circuit/part": {…}, "logic/symbol": {…} }`）：证明板读元件，填句子条读符号。
- **Studio**：每个可发放对象类型在左栏单独列；托盘编辑器、阶段链对所有登记过的对象类型都能用。
- **不跟着泛化的**：`replaces`（一个元件被另一个取代）和工坊（把搭出的电路做成元件）只对元件有意义，留在元件上；以后真有别的对象类型需要，再照这个办法开放。
- 参考解用到不可用的对象、托盘成员或发放字段引用了没登记的对象类型、名字歧义，检查都报错。
- **每个对象类型走自己的路径**：对象 `<目录>/<名>.json`；覆盖就是在覆盖者的 `overrides/<命名空间>/` 下放同一路径（`overrides/<命名空间>/parts/<名>.json`、`overrides/<命名空间>/tags/<对象类型>/<名>.json`），不再另有一套单复数混用的覆盖目录名；标签在 `tags/<对象类型>/`。

### 5.2 纯文字的游戏

不碰元件、不碰内核：一个提供「文字作答」的包（`text`）——主区显示题目和输入框或选项，作品是答案，判定按关卡里配的规则（完全相同、忽略大小写和空格、正则、数值带容差、几个可接受答案任选其一），检查要求参考答案通过、写在关卡里的错误答案被判错。课程的关卡是数据，游戏选用它和内容包、排好章。Studio 里左栏列关卡，中栏是这个玩法的预览，右栏改题目和答案，文案工作区校对文字。

### 5.3 对象类型的结构是数据

一个对象类型分两部分：**结构**（字段和字段类型、能被谁引用、覆盖方式、哪些字段是文案、在 Studio 左栏怎么列）是声明，写成数据；**含义**（这种对象在玩法里起什么作用）才需要代码，由 `kind` 协议挂上去。

- 包里 `kinds/<名>.json` 声明一种对象：字段的 schema（用内核 schema 的 JSON 写法，和 `describe` 打印出来的一样）、可被哪些对象类型引用、新的关系（比如 `replaces`，端点是元件）、覆盖方式（整份替换或追加成员）、文案字段、左栏的名字、图标、分组方式。对象类型的全名是 `<包>/<名>`，别的包依赖它就能用。
- 这种对象放在包里对应的目录（比如 `scenes/<名>.json`），和关卡、元件一样走内容系统：全名、标签、关系、覆盖、来源、文案工作区、兼容性判断全部自动适用。
- **每个对象类型都能打标签，不用登记**：标签的成员可以是任何已声明对象类型的对象，规则见 5.4。
- 有些对象类型不需要任何代码：比如「人物」「例题」「参考资料」，作者自己定义结构，用来组织内容、写文案、被关卡引用。
- 字段扩展也写成数据：`kinds/` 里声明给关卡或任务加哪些字段。
- 对象类型的定义可以在 Studio 里改，经操作集写回 `kinds/<名>.json`。它影响这个对象类型已有的全部对象，所以是公开面上的改动（第 8 节）：兼容性判断指出哪些对象因此不合法、哪些依赖方受影响，同一次改动里用操作集把这些对象迁过去。
- 在 Studio 里给一个对象类型加字段，如果没有代码去读它，它只是存着的值，不起作用；含义永远在代码里。内核自带的几种的结构由内核定，包不能改，只能对关卡、任务做字段扩展。

### 5.4 标签

只有一种标签，规则照《我的世界》的标签。

- **身份是全名** `<命名空间>/<名>`：成员类型由文件所在的目录决定（`tags/<成员类型>/`），不进身份；同一个命名空间里标签名唯一，不同成员类型也不能同名。引用写 `#<命名空间>/<名>`，永远不会有歧义。这是和《我的世界》唯一的差别：它允许方块标签和物品标签同名，我们没有这个需要。
- **标签只是集合**：成员是对象或别的标签（`#…`），没有别的属性。有自己属性的分组单独声明对象、再引用标签：托盘（名字、说明、工坊、二级菜单）、百科分组（标题、说明）、关系都是。这和《我的世界》的附魔是带属性的对象、它能附在哪些物品上引用一个标签是同一种结构。
- **一种写法，两个位置**：自己命名空间的标签写在自己包的 `tags/<成员类型>/<名>.json`；往别的命名空间的标签里加成员，写在自己包的 `overrides/<命名空间>/tags/<成员类型>/<名>.json`（相当于《我的世界》在自己的数据包里写 `data/minecraft/tags/...`）。内容相同：`values` 追加成员，`replace: true` 整份替换，`remove` 去掉成员。包里声明的对象类型的成员类型目录用对象类型全名（`tags/story/scene/`、`tags/circuit/part/`），内核自带的用短名（`tags/level/`、`tags/kind/`）。
- **合并**：所有包对同一个标签的贡献按依赖顺序合成一个，默认取并集；读标签的代码只看到合成后的集合。
- **比《我的世界》多的两条**：
  - 标签要先存在：拥有这个命名空间的包写了它，或者读它的代码登记了它。往一个没人写、没人登记的标签里加成员，检查报错——《我的世界》里拼错名字只会悄悄多出一个没人用的标签。
  - 记下每个成员是谁加的，Studio 的覆盖审计能看到。
- **代码按名字读的标签，归读它的一方**：读的一方登记全名和成员类型，各包照上面的写法往里加成员。内核和 Studio 读的标签在保留命名空间 `kernel` 下（`kernel` 不能用作包名，它本来就是包代码 import 内核 API 的名字）；`circuit` 读的是 `circuit/…`（比如「不出现在元件册里」的元件标签）；包作者自己的代码读的是 `<自己的包>/…`。这和《我的世界》代码查 `minecraft:climbable`、各模组往里加成员是同一种用法。检查报出没登记的名字、成员类型不对的成员；Studio 在左栏标出被代码读的标签。
- **左栏默认列哪些对象类型**：`kernel/studio-left`，成员类型是 `kind`（对象类型的全名）。各包往里加，合成后的成员和它的 `order` 关系决定构建工作区左栏默认列出哪些对象类型、什么顺序。每个人还可以在 Studio 里改自己这一份（存在浏览器里），不写进包。没有任何包加过成员时，列出有对象的全部类型。
- **跨对象类型的顺序**：顺序关系的端点可以是不同对象类型的对象（比如托盘里元件和符号混排），这时不写 `of`，端点直接写对象全名。

### 5.5 新建对象

不设模板。《异星工厂》的模组复制一个现成的原型再改（`table.deepcopy(data.raw[...])`），《我的世界》的数据包复制原版的文件再改，任何已有对象都是起点。

- **复制为新对象**：Studio 里任何对象都能复制成一个新 id 的对象，来源可以是本包的，也可以是依赖的包里的。
- **空白对象**：结构由对象类型的 schema 给出；关卡和任务的初始内容由玩法的 `core/` 给出一个最小合法的版本。
- 想要一份精选的起点，建一个普通标签就行，左栏按标签分组时它就是一组。
- **新建一个包**：从一个现有的包复制一份起步（`npm run new-package -- <新包> --from <包>`）。原来 `kit/templates/` 里各玩法的起步内容，改成一个专门用来复制的起步包。

## 6. 包的代码要守的边界

1. **只实现协议**：登记玩法、对象类型、检查、编辑器、盲玩、显示；不改内核行为，不绕开进度和检查。
2. **只能 import 内核公开的 API 和 `uses` 里的包导出的接口**，不能伸进别的包的内部文件；检查要拦。
3. **核心和视图单向依赖，按路径检查**：`core/` 下的文件只能 import 内核的无界面 API、别的包的无界面导出和自己的 `core/`，不能碰 `view/`、界面库、JSX、CSS；`view/` 可以 import 自己的 `core/`（比如用核心的作品读写来画）、内核的界面工具和别的包的 `/view` 导出，反过来不行。作品格式只在 `core/` 里定义一次。
4. **判定必须确定**：运行和判定不访问时钟、网络、文件；随机只能来自传入的种子；同样的作品同样的结果。`view/` 不受这条限制，但不能影响判定。
5. **契约测试**：每个带代码的包都要通过——`core/` 单独在 Node 里能登记、能检查自己的关卡、能盲玩，两个入口一起能和别的包组装；`core/` 的测试在 Node 里跑，`view/` 的测试另跑。
6. **代码和数据分两条路改**：数据经操作集和 Studio；`core/`、`view/` 只经代码提交和审查，操作集和 Studio 不能写它。
7. **内核零内容能跑**：`packages/` 和 `games/` 清空时，内核的测试全过，Studio 和游戏外壳能打开，`check` 能跑。

## 8. 兼容性与版本

- 包的**公开面**：一切能被别的包、游戏、覆盖文件用全名引用的东西——关卡、任务、元件和阶段、词条、标签、关系、托盘、百科分组、各种对象类型的对象、对象类型本身的结构定义（`kinds/`）、文案键，以及代码登记的玩法、对象类型、检查、编辑器、显示的名字和接口。
- 改动后自动判断三级：**只增加**（新对象、可选字段、新登记项）；**破坏**（删掉有人引用或覆盖的东西，改了接口或 schema 让别人不再合法）；**行为变了**（结构没变，依赖方的检查结果变了）。前两级看结构，第三级跑依赖方的检查。
- 有破坏或行为变了，同一个提交里受影响的一方也要通过。
- 版本号不手编：合并进主线时由工具按这次的最高级别自动记一笔；内核接口（插件协议）同样如此，并行分支不再撞号。
- 包还都在这个仓库里，所以不需要依赖范围；包要分开发布时，再用这份记录生成正式版本。

## 9. 检查

- 内核：schema、引用（只引用 `uses` 里的包）、标签（写进的标签有人写或登记、成员类型对、名字唯一）、标签和关系的成环、覆盖冲突、游戏层越界、课程能玩通（解锁可达）、id 不变、包代码的 import 边界。
- 包：自己那类玩法的关卡检查（参考解、naive 解、玩法内的一致性），通过 `check` 协议接入。
- 技术层和规范层照旧分开：教学节奏等规范不进检查。
- 现有四款游戏的检查输出，除了提示来自哪个包的写法外，不变。这是每一步的验收前提。

## 10. 实施步骤

每一步一个或几个提交，直接合入 main；步内硬切换，不留旧路径、兼容层、死代码。

1. **锁住行为。** 存四款游戏和四个包的检查基线、逐步报告、参考解和 naive 解的结果；给 state-graph 的手工玩法补上纯判定，让它能进对照。
2. **定插件协议，内核开放包的代码。** `core/`、`view/` 两个入口的加载、`register` 协议（玩法、对象类型、字段扩展、派生状态、检查、编辑器、盲玩、显示）、import 边界检查（含核心和视图的单向依赖）、内核的两份导出、契约测试；用新写的 `text`（文字作答）作为第一个插件验证——它和电路毫无关系，证明协议不依赖元件体系，做完就是一个模板，也是零内容验收时的最小玩法。
3. **`circuit` 出内核。** 电路求值、元件、托盘、阶段、工坊、蓝图文本、画板编辑器、电路屏，连同课程模型里对应的部分，搬进 `packages/circuit`；内核的进度只剩任务和关卡的解锁。元件的对象类型 `part` 变成 `circuit/part`，发放机制按「可发放」登记工作（5.1）。（`piece` 改名 `part`、覆盖路径统一、公式连接词拆成 `logic/symbol`，在第 1 步之后已单独做完。）验收：四款游戏不变。
4. **`rows`、`tick-bus` 出内核。**
5. **`image` 出内核**，专用实验台、场景进 vision-complete / comp90086。
6. **`table` 出内核**，专用世界、机器人进 state-graph。
7. **`logic` 出内核**，专用部分进 qed。
8. **Studio 的编辑器改成由包提供**；内核的 Studio 只剩外壳。
9. **兼容性自动判断和自动版本**（第 8 节）。
10. **零内容验收和写回手册**：清空内容后内核能跑；改写 `DESIGN.md`，删掉这份文档。

## 11. 已定

- 只有一个包用的东西放在那个包里，第二个包要用时再提到被依赖的包里（第 3 节）。
- `circuit` 先作为一个包，元件、托盘、阶段、工坊、蓝图文本、画板编辑器都在里面，以后有需要再拆。
- 百科页留在内核。
- 不做内核里的 AST 或受限脚本语言；复杂原语整块随包走，不拆。

## 12. 约定

- 行为不变：每一步前后对比基线（`npm run -s check -- <游戏>`、`npm run -s check -- --package <包>`）。
- 测试：内核测试只用测试里现写的小内容；每个带代码的包有自己的测试。
- 改内容只经操作集；包的代码只经代码提交。
- 界面：桌面和手机都看；不加次要标签和说明文字。
- 提交和推送照仓库的写法；main 上同时有别的会话在推，推之前先拉取再变基。
