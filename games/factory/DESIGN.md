# 《软件工厂》（编码 agent）设计框架

工作名《软件工厂》（Software Factory），专题是 AI 原生的软件开发：从一次模型调用，到一个能自己接 issue、写代码、跑测试、互相审查、按预算并行运转的流水线。题材取自斯坦福 CS146S（The Modern Software Developer，2026 秋季）的主线，但只教它背后的机制，不教任何具体产品。所有类图灵完备游戏共同遵守的结构、规则和自动检查见 [`games/DESIGN.md`](../DESIGN.md)；本文档只记录这个专题自己的内容。现在是框架阶段：逐关的规格等模拟模型的原型做出来再写。

**终点：** 学完以后，学习者用自己从一次模型调用搭起来的 agent，组装出一座软件工厂：一个 issue 队列进去，审过、测试全绿的修改出来，不越权，不被仓库里的文字劫持，花的 token 不超预算。看一个真实的编码 agent 时，能看见它的骨架：一个循环、一个上下文窗口、一组工具描述、几道闸门。

## 1. 映射：把《图灵完备》搬到编码 agent 上

| 《图灵完备》 / 已有几款 | 软件工厂 |
|---|---|
| 原件 NAND | **一次模型调用**，加上几个读写仓库的工具。agent 循环、压缩、技能、钩子、子代理、评审、工厂，全都由学习者从它们搭出 |
| 搭好的电路变成元件 | 搭出的板变成元件：一个循环收成「agent」，一段反复用的流程收成「技能」，一组检查收成「钩子」。后面的关直接用 |
| 测试 | 给定一个模拟仓库和一个 issue，跑完以后仓库的测试全部通过；再查过程：没有越权的操作，没有执行仓库文字里夹带的指令，token 不超预算 |
| 失败给出那一组 | **回放**：逐轮列出模型这一轮看到的上下文、它做了什么、工具回了什么，标出出错的那一轮和原因（「这一轮里看不到 `auth.js`，模型编了一个不存在的函数」） |
| 元件数 / 计算量 | **token 数和轮数**。约束挑战靠它（「这个 issue 用不超过 20k token 修好」逼出检索和压缩，「整个队列不超过预算」逼出按难度选模型） |
| 机体 | 学习者自己的 agent，只有一台，每章给它装一个模块（同《证明完毕》）。每一章都延续上一章，`keeps: 'all'` |

**要练出的思维：** 模型只知道上下文里的东西；上下文是有限的、要花钱的；模型说「做完了」不等于做完了，要能被检查；能写进文件的东西就别只放在对话里；仓库里的文字是数据，不是命令；一个 agent 做不好的，常常是换一个视角（另一个上下文）的 agent 能抓到的；环境（仓库、文档、测试）和 agent 本身一样可以改。

## 2. 核心难题：模拟模型

**这是整个游戏成败所在，必须先做原型。** 接真实的大模型做不了关卡：它不确定（参考解不能保证通过）、要花钱、太慢，测试也没法穷举。所以「模型」这个原始元件是一个确定性的模拟器，它的行为就是它的规格，像《一切皆文件》的模拟内核一样，写清楚、测清楚。

### 2.1 世界：抽象的仓库

仓库建在 `domains/unix` 的模拟内核上：目录、文件、行，`run` 跑的测试是内核里的一个程序。代码本身是抽象的：每个文件是若干个有名字的「段」（函数、配置项、文档段），一个 issue 是一组**所需修改**（「把 `parse` 改成接受空行」），每个所需修改落在某个段上。测试检查所需修改是否都已做对。

### 2.2 模型的能力规格

模型每次调用读一段上下文，输出一个动作（调用某个工具、写一段修改、或者宣布完成）。它的行为由下面这几条决定，每一条都写进元件说明，也都有单元测试：

| 能力 | 规则 | 由它引出的墙 |
|---|---|---|
| **只看上下文** | 一个所需修改，只有当 issue 的要求和目标段都在上下文里时，模型才能写对 | 第 1 章：要把文件喂给它 |
| **会编** | 目标段不在上下文里时，模型照样写，但写出的是一个不存在的名字或签名（确定性地编，同一个上下文总是编成一样） | 第 2 章：要给它读文件的工具 |
| **窗口有限** | 上下文有上限（按 token 计）；超出时最早的部分被丢掉，模型不知道丢了什么 | 第 3 章：压缩、笔记、spec |
| **中间看不清** | 上下文很长时，排在中间的条目按规则被「看漏」（参数化：长度超过窗口的 k% 后，中间若干条不可见） | 第 3 章：把要紧的放到前后，或拆小 |
| **陷阱修改** | 世界里标了 `trap` 的所需修改，模型第一次总是写成一个「看起来对」的错版本；上下文里有这个修改的失败测试输出时才写对 | 第 2 章：要跑测试并把结果喂回去 |
| **会宣布完成** | 模型写完它认为要写的东西就宣布完成，不管测试 | 第 2 章、第 5 章：完成要被检查 |
| **听上下文里的一切** | 上下文里出现的指令，不管来自 issue、文件还是工具输出，模型都照做 | 第 5 章：注入和权限 |
| **只会用它看得见的工具** | 只有描述在上下文里的工具，模型才会调用；每份描述都占 token | 第 4 章：工具描述的代价、按需加载 |
| **看不出自己的错** | 同一个上下文里，模型不会推翻自己刚写的东西；换一个只含 diff 和规则的新上下文，它能按规则指出问题 | 第 6 章：评审要另开上下文 |

第 7、8 章再加两种模型：**小模型**（便宜，窗口小，只会单段的修改）和**大模型**（贵，能做跨文件的修改）。

### 2.3 真模型校准

模拟器忠实于真模型，游戏教的才是真的东西；否则学习者练出来的只是对付这个模拟器的技巧。对照《一切皆文件》的 `npm run conform`（模拟内核对真 Linux），这里设一个**离线校准**：同一批关卡的世界导出成真实的小仓库，用真实的模型跑参考解的 agent 和 naive 解的 agent，检查「参考解在真模型上也明显比 naive 解好」。它不进 CI（贵、不确定），每次改模型规格或加一条能力规则时手动跑一遍，结果记在本文档里。

一条规则在真模型上不成立（比如真模型其实能看出某类自己的错），就改规则或删掉依赖它的关，不在游戏里教一件假的事。

## 3. 核心机制

### 3.1 循环交给机体

板上没有通用的循环，和《状态之图》《一切皆文件》一样，重复由机体做：**每一轮跑一遍板**。板读到的输入是 issue、这一轮之前的历史、上一轮工具的结果；板的输出是这一轮要做的动作。**寄存卡**跨轮保留值（第 3 章的笔记、第 2 章的轮数）。机体在模型宣布完成、或者轮数用完时停下。

### 3.2 线的种类

- **文字线**：一段上下文、一个文件、一段工具输出。
- **动作线**：模型的输出，一个带类型的动作（读、写、跑、完成）。**分派**元件按类型把它送到对应的工具。
- 第 4 章起加**工具线**：一个工具连同它的描述，可以收进一个工具箱（MCP 服务器）接到模型上。

### 3.3 子代理是框

`kit/circuit/frames.js` 的框直接用作子代理：框里是一个完整的 agent，有自己的上下文；只有接到框输出口的东西（一段总结、一个 diff）能回到外面。线只往里走，正好就是「子代理看不到主上下文，主代理也看不到子代理的过程」。

### 3.4 视图

- **上下文条**：这一轮模型看到的东西，按条目画成一条带刻度的条（token 为单位），超出窗口和「中间看不清」的部分画成灰的。
- **回放**：逐轮的时间线，每轮一行：上下文条、动作、工具结果。失败时停在出错的那一轮。
- **仓库**：文件和段，改过的段高亮，测试的结果标在旁边。
- 第 7 章起：**看板**，issue 在队列、进行中、评审、合并几列之间移动。

### 3.5 通关点题附真实写法

过关后，点题旁边给出这块板在真实工具里对应的写法（一段循环的伪代码、一个 SKILL.md、一个钩子配置、一份 AGENTS.md），说明「真机上同样的事长这样」，不要求学习者写。

## 4. 课程

| 章 | 给机器装上的模块 | 新的外部能力 | 专题（终极谜题） | 挑战（例） |
|---|---|---|---|---|
| 0 | 纸笔 | 学习者自己当循环 | — | — |
| 1 | 一问一答 | 一次调用、拼上下文 | — | 一次就修好 |
| 2 | 循环 | 每轮跑板、工具、分派 | 两百行的 agent | 不读完也能修 |
| 3 | 上下文 | 窗口上限、寄存卡、笔记文件 | 长任务 | 二十轮以内 |
| 4 | 工具与技能 | 工具描述、工具箱、按需加载 | 自己的技能库 | 五十个工具 |
| 5 | 护栏 | 钩子、权限、仓库规则文件 | 让仓库准备好 | 藏在 README 里的话 |
| 6 | 分工 | 子代理（框）、评审 | 三人小组 | 看起来对的 PR |
| 7 | 后台 | 多个 agent 同时跑、队列、隔离的工作区 | 夜班 | 两个人改同一个文件 |
| 8 | 工厂 | 两种模型、预算、路由 | 软件工厂 | 一半的预算 |

关数先不估：每一章写逐关规格时，按手册 2.3 给每个机制配足练习。CS146S 各周和本课程的对应：第 1 周 → 第 1–2 章；第 2 周 → 第 3–4 章（spec、MCP）；第 3–4 周 → 第 4–5 章（技能、规则文件、钩子、子代理）；第 5 周 → 第 5 章专题；第 6 周 → 第 6 章；第 7 周 → 第 5 章（安全）；第 8 周 → 第 7 章；第 9–10 周 → 第 8 章。

### 第 0 章 · 纸笔

还没有机器。学习者自己扮演循环：模型说「我要看 `parse.js`」，学习者点开文件、把它拖进上下文，再按一次「调用」。

| 关 | 名称 | 新东西 |
|---|---|---|
| 0-1 | 它只知道你给它的 | 不给文件，模型编了一个函数；给了，它写对了 |
| 0-2 | 它要什么你给什么 | 照着模型的请求，手动读文件、跑测试、把结果贴回去，直到测试全绿 |
| 0-3 | 窗口满了 | 手动喂到上下文满，看最早的条目被丢掉 |

### 第 1 章 · 一问一答

**能力：** 一次模型调用（这一章没有循环，板只跑一遍）。

**原始元件**（一关出现一个）：模型、拼接（几段文字按顺序拼成上下文）、读文件（按名字读出一个文件）、写回（把模型的修改写进仓库）。

**地基：** 1-1 第一次调用（模型 + 写回，issue 里已经贴好了代码）、1-2 把文件拼进去（拼接 + 读文件）、1-3 顺序有讲究（同样的几段，拼的顺序不同，模型看漏的不同）。

**练习：** 两个文件的修改（两次读、一次拼）、issue 没写清是哪个文件（naive 解：全拼进去，超出窗口；要先想清楚 issue 指向哪里）、辨真伪：一个只拼对文件、却仍然改不对的 issue（它是陷阱修改，墙留给第 2 章）。

**挑战：** 一次就修好（一个跨三个文件的 issue，只许一次调用，窗口刚好装下必要的三段：要读段而不是读整个文件）。

### 第 2 章 · 循环

**能力：** 机体每轮跑一遍板；模型的输出是动作；寄存卡。第一关的引言接着第 1 章的墙：issue 指向哪个文件，写板的人事先不知道，只有模型读了以后才知道，所以要让它自己去读。

**原始元件：** 分派（按动作类型分路）、列目录、跑测试。读文件、写回在这一章变成工具：由分派接到模型的动作上。

**地基：** 2-1 让它自己读（循环 + 分派 + 读文件）、2-2 让它自己找（列目录）、2-3 它说做完了（模型宣布完成，测试是红的）、2-4 让它跑测试（跑测试，把失败输出接回上下文；陷阱修改第二轮写对）、2-5 完成要过闸（宣布完成时先跑测试，红的就不许停：板上用已有元件搭出这道闸）。

**练习：** 两个陷阱（要跑两次测试）、测试很慢（每跑一次测试花很多 token：先读再改再跑，不要每改一行就跑）、去支架：issue 只说「登录坏了」、组合：找 + 改 + 测、辨真伪：一个测试本身写错了的 issue（agent 永远跑不绿，正确的结局是报告「测试和 issue 矛盾」而不是一直改）。

**专题：两百行的 agent。** 对应 CS146S 第一讲。终极谜题：一个只给 issue 的仓库，agent 自己找、读、改、测、停。

| 关 | 加回的机制 | 产出 |
|---|---|---|
| A1 只会读 | 循环 + 读文件 | — |
| A2 会改 | 写回作为工具 | — |
| A3 会测 | 跑测试 + 完成闸 | — |
| A4 一个完整的 agent（终极） | 有上限的轮数，到上限时报告做到哪了 | **agent**（整块板收成一个元件，后面的章直接用） |

**挑战：** 不读完也能修（一个大仓库，按轮数限预算：要先用跑测试的输出定位，而不是挨个读文件）。

### 第 3 章 · 上下文

**能力：** 窗口上限在这一章真的起作用（任务变长，历史会撑满窗口）；笔记文件（agent 能写一个只给自己看的文件）。第一关的引言：第 2 章的 agent 在长任务里会「忘掉」issue 本身，因为 issue 是最早进上下文的那一条。

**原始元件：** 截断（只留最后 n 个 token）。其余全由已有元件搭：

**地基：** 3-1 把 issue 钉住（每轮重新把 issue 拼到最前，不随历史滚走）、3-2 只留最近的（截断：丢掉旧的工具输出）、3-3 压缩（另调一次模型，把旧历史写成一段总结，换掉原文：搭出**压缩器**）、3-4 写下来（笔记文件：计划和进度写进仓库，每轮读回来）、3-5 先写 spec（第一轮只写 spec 文件，后面每轮按 spec 一项一项做：RePPIT 里「研究、提议、计划」三步收成一段）。

**练习：** 压缩丢了关键的一句（总结里没写进错误信息，下一轮重犯：要让压缩保留失败的测试输出）、中间看不清（同样长的上下文，把要紧的放到前后）、换方向：读一份别人写的 spec 照着做、组合：钉住 + 压缩 + 笔记、辨真伪：一个根本装不进窗口的单步修改（一个段比窗口还大；正确的结局是拆 issue，第 6 章再给拆的手段）。

**专题：长任务。** 一个要改十几处的 issue，跑几十轮。

| 关 | 加回的机制 |
|---|---|
| L1 十处修改 | 钉住 issue |
| L2 三十轮 | 压缩器 |
| L3 中途换了要求 | issue 第 15 轮追加一条评论：笔记要能被改写 |
| L4 长任务（终极） | spec + 笔记 + 压缩，五十轮内做完 |

**挑战：** 二十轮以内（同一个长任务，轮数减半：要一轮里读多个文件、把多处修改合进一次写）。

### 第 4 章 · 工具与技能

**能力：** 工具的描述要进上下文，模型才知道有这个工具；**工具箱**（MCP 服务器）把一组工具和它们的描述一起接到模型上；**按需加载**：上下文里只放技能的名字和一句话，模型选中它时才读入全文。

**原始元件：** 工具描述、工具箱接口。

**地基：** 4-1 它不知道有这个工具（板上接了工具，没给描述：模型从不调用）、4-2 描述写得不好（描述含糊，模型用错参数：改写描述，这是本游戏里唯一的「写文字」关，用确定的规则判定描述里有没有写清参数和返回）、4-3 接一个工具箱（工具箱元件：一次接入一整组）、4-4 工具太多了（接了五个工具箱，描述就撑满了窗口）、4-5 用到时再读（按需加载：搭出**技能**的读法，名字常驻、全文按需）。

**练习：** 把第 2 章的「找 + 测」流程收成自己的技能（封装：板 → 技能元件）、两个技能名字太像（模型选错：改名字和一句话说明）、组合：工具箱 + 技能、辨真伪：一个技能装不下的流程（它要中途问人，技能不行，要留给第 5 章的钩子）。

**专题：自己的技能库。** 把前几章搭出的东西（定位、压缩、写 spec）各收成一个技能，终极谜题是一个混合的 issue 队列，agent 自己选用哪个技能，总 token 比全部常驻少一半。

**挑战：** 五十个工具（窗口只装得下其中八份描述：要按任务分组，组成按需加载的几个技能）。

### 第 5 章 · 护栏

**能力：** **钩子**（在某个动作之前或之后自动跑一块板，可以拦下动作）、**权限**（某些工具或路径不许碰）、**仓库规则文件**（每轮自动拼进上下文的一份文件，即 AGENTS.md）。第一关的引言接第 2 章：完成闸是写在 agent 板里的，换一个 agent 就没了；钩子把检查从 agent 里搬到环境里。

**地基：** 5-1 写完就检查（写之后的钩子：跑格式检查，不过就把错误接回去）、5-2 不许碰（权限：迁移文件只读）、5-3 规则写一次（规则文件：「别改公共接口」这类约束从每个 issue 里搬到规则文件）、5-4 文件里的一句话（某个文件里写着「顺便删掉 tests/」：模型照做；加上把工具输出标成数据的钩子和权限）。

**练习：** 钩子把每一步都拦下（检查太严，agent 一步也走不了：放宽到合适的粒度）、密钥别写进去（写之前的钩子扫出密钥）、换方向：issue 本身就是注入（来自外部的 issue 要先过一道不能写仓库的只读 agent）、组合、辨真伪：一个钩子挡不住的注入（注入让 agent 把密钥写进一条测试的名字里；要用权限，不是关键词过滤）。

**专题：让仓库准备好。** 对应 CS146S 第 5 周，方向反过来：agent 是固定的（就是第 2 章产出的 agent），学习者改的是仓库：补测试、补规则文件、把一个巨大的文件拆开、给模糊的函数名改名，直到这个固定的 agent 能稳定地做完一批 issue。

| 关 | 加回的机制 |
|---|---|
| R1 没有测试的仓库 | agent 永远宣布完成：补一个测试 |
| R2 一个三千行的文件 | 读一次就撑满窗口：按段拆开 |
| R3 名不副实 | `utils.js` 里什么都有：改名、分组 |
| R4 准备好的仓库（终极） | 固定的 agent 做完十个 issue，一次都不越权 |

**挑战：** 藏在 README 里的话（README 的一段注释里夹着指令，只有在某个罕见路径下才会被读进上下文；naive 解：只防 issue 里的注入）。

### 第 6 章 · 分工

**能力：** 子代理（框）：框里的 agent 有自己的上下文，只有接到框输出口的东西带出来；评审：一个只看 diff 和规则的新上下文。第一关的引言接第 3 章的墙：有的 issue 一个上下文装不下，拆开以后每块要在干净的上下文里做。

**地基：** 6-1 派出去（子代理：主 agent 把「找出所有用到 `parse` 的地方」派给一个框，只拿回一份列表）、6-2 回来的只是总结（子代理的总结漏了一处：规定输出的格式）、6-3 换一双眼睛（评审：实现者看不出的错，只看 diff 的新上下文按规则指出来）、6-4 改到评审通过（评审意见接回实现者，循环到通过或到上限）。

**练习：** 评审太宽（什么都过）、评审太严（永远不过：规则要能被满足）、计划 → 实现 → 评审三段、并行的两个子代理改了同一个段（合并冲突第一次出现，留给第 7 章正式处理）、辨真伪：一个评审规则抓不到的错（只有跑起来才看得出：评审替代不了测试）。

**专题：三人小组。** 规划、实现、评审三个子代理，终极谜题是第 3 章里装不进窗口的那个 issue。

**挑战：** 看起来对的 PR（一个 diff 通过了全部测试，但删掉了一个没有测试覆盖的行为；naive 解：只跑测试的评审；跳跃：评审规则里加「每个删除的分支都要有理由」，让评审回到 issue 去对照）。

### 第 7 章 · 后台

**能力：** 机体升级成一组 agent：一个 issue 队列，几个 agent 同时各领一个；每个 agent 有隔离的工作区（worktree），做完的修改排队合并。

**地基：** 7-1 两个一起做（两个 agent，两个不相干的 issue）、7-2 撞车（两个 issue 改同一个段：合并冲突）、7-3 各自的工作区（隔离，合并时由一个合并 agent 解决冲突）、7-4 从 issue 到 PR（触发：issue 打上标签就自动派一个 agent，做完开 PR 等评审）。

**练习：** 队列里有依赖（B 要等 A 合并）、一个 agent 卡住了（超时就收回 issue 重派）、组合：队列 + 评审 + 合并、辨真伪：一批无法并行的 issue（都改同一个核心文件，并行反而更慢）。

**专题：夜班。** 下班前把二十个 issue 放进队列，第二天早上看结果：全部合并或明确地报告失败，没有一个半成品留在主分支。

**挑战：** 两个人改同一个文件（naive 解：先到先合，后到的覆盖；跳跃：合并前先 rebase 并重跑测试）。

### 第 8 章 · 工厂

**能力：** 两种模型（小模型便宜、窗口小、只会单段修改；大模型贵、会跨文件）；**预算**（整个队列的 token 上限）；**网关**（所有调用经过的一个元件，可以计数、路由、拦截）。

**地基：** 8-1 都用大模型（做得完，超预算）、8-2 都用小模型（便宜，一半做不了）、8-3 按难度分（路由：先让小模型试，失败或判断为跨文件时升级）、8-4 网关（把路由、计数、权限收到一处）。

**练习：** 路由判断错了（小模型看起来做完了：评审要按模型分级）、预算用完了（剩下的 issue 排序：先做最值的）、组合。

**专题：软件工厂。** 终极谜题：一个真实规模的队列（五十个 issue，含陷阱修改、注入、冲突、装不进窗口的大任务），在预算内跑完，主分支始终是绿的。用到前面每一章搭出的东西。

**挑战：** 一半的预算（同一座工厂，预算减半：要靠技能和压缩省 token，而不是降低通过率）。

## 5. 元件从哪里来

- **原始元件**：模型（第 1 章；第 8 章加小模型、大模型两个型号）、拼接、读文件、写回、分派、列目录、跑测试、截断、工具描述、工具箱接口。每个都在它那一章的地基里出现一次。
- **机体能力**（地基里教）：每轮跑板、寄存卡、笔记文件、窗口上限、钩子和权限、子代理框、队列和工作区、预算和网关。
- **学习者造的元件**（封装件）：agent、完成闸、压缩器、spec 写手、技能（每个技能都是学习者收起来的一块板）、评审、合并 agent、路由器。每个都在后面的参考解里用到（审计 `unused`）；第 5 章专题和第 8 章终极谜题专门用来检查前面的东西还在抽象链里。

要守住「基础元件保持最少」：压缩器是「模型 + 截断 + 寄存卡」，评审是「新上下文里的模型 + 规则文件」，技能是「封装的板 + 按需加载」，都不能做成原始元件。

## 6. 引擎：复用什么，补什么

**复用 kit 里已有的：**

- `domains/unix/kernel.js`：仓库的文件系统和跑测试的进程。
- `engine/machine.js`：每轮跑一遍板，寄存卡。
- `circuit/frames.js`：子代理。
- `engine/tests.js` 的 `score`：token 数和轮数。
- `shell/usePlayback.jsx`：逐轮回放。

**要新做的（新领域 `domains/agent/`）：**

1. **模拟模型**：第 2.2 节的每条规则一个单元测试；同一个上下文永远给同一个动作。
2. **抽象仓库**：段、所需修改、陷阱标记、测试程序；从一份 JSON 世界生成。
3. **上下文条和回放视图**。
4. **校准脚本**（第 2.3 节）：把世界导出成真实的小仓库，用真模型跑参考解和 naive 解。不进 CI。
5. 第 7 章起：多个 agent 的调度、工作区、合并。

**诚实的限制：**

- 游戏里的「代码」是抽象的段，模型的「写对」是规则判定的。学习者学到的是 agent 外面那一层（上下文、循环、工具、闸门、分工），不是模型本身写代码的能力，引入里要明说。
- 模拟模型的每条能力规则都是对真模型的一个简化。有的规则（「看不出自己的错」「中间看不清」）在真模型上程度不一，而且会随模型进步而变弱；校准不再支持它时，就要改关或删关。
- 提示词写作的手感、行业经验、团队推广、开源贡献，没法用确定的规格判定，不进关卡。第 4-2 关的「写描述」只判结构，不判文笔。
- 题材变化快。关卡只教机制，不出现产品名；点题里的「真实写法」会过时，要定期更新。

## 7. 建议的第一步

1. 先只做模拟模型和第 0–2 章：模型的规则能不能撑起「会编、陷阱修改、完成闸」这几面墙，要在写后面几章的逐关规格之前试出来。
2. 同时做一次校准：第 2 章专题的参考解和 naive 解，在真模型上的差距是否和游戏里一致。不一致就先改规则。
3. 第 3 章的上下文条是这个游戏和其他几款最不一样的视图，紧接着做它的原型。
