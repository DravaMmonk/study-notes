# 平台化评审（2026-11-12）

对 `games/kit`、领域层、内容层和工具链的一次评审：骨架决策是否站得住，离「开放给更多人制作和体验的平台」还差什么。每条写明依据（在 `6bdc712` 上读代码或实测），方便逐条核对；采纳的条目写进 `DIRECTION.md` 的实施顺序，本文随之删掉对应条目。

## 结论

三层分层、封闭词汇表、操作集作为唯一写入口、契约测试，这四个决策都站得住，并且已有实证，不建议动。差距集中在三处：内核改动没有针对真实内容的回归；测试强度靠事后逐条补洞；平台化需要的存储、权限、版本三样还停留在单人单机的形状。

## 已有实证的部分

- **新领域的成本已经降下来了。** 建在电路底座上的领域（不含测试）：`calculus` 269 行、`linear` 387 行、`can` 486 行、`net` 798 行，其中 JSX 各 38–56 行。原型领域是 `image` 9739 行、`logic` 8499 行、`table` 6136 行。差一个数量级，说明 `circuit-domain.js` 和 `CircuitScreen` 这层抽象是成立的。
- **同一领域上的第二款游戏已经存在。** `comp90086` 和 `vision-complete` 都写 `domain: image`。
- **分层边界在代码里是干净的。** 领域之间没有互相导入；内核对领域只有 `content-node.js` 里按名字的动态加载。
- **检查很快。** `npm test` 414 条 34 秒；`npm run check` 全部十款游戏 35 秒。单款 5–15 秒，其中约 4 秒是经 vite 载入 `game.jsx` 的固定开销。

## 改进空间，按优先级

### 1. 内核改动没有真实内容的回归

`test-kit.yml` 只跑 `npm test`，它按设计不读任何真实游戏；`deploy-games.yml` 只构建和发布。内核或领域的一次重构弄坏某款游戏的参考解时，没有任何自动环节会发现，线上页面会直接带着它发布。

「内容检查不进 CI」防的是改关卡牵动测试，这个理由对内容编辑成立，对 kit 代码变更不成立。建议区分两件事：

- 内容变更：照旧，只过操作集的门。
- `games/kit/**` 变更：把全部游戏当回归语料跑 `npm run check`，35 秒。可以先只报告、不拦发布。

这不违反「单元测试不认识关卡」：测试文件一行不改，只是 kit 变更时多跑一个已有的命令。

### 2. 测试强度：用变异代替逐条补洞

「空板必须不过」「一根线直通必须不过」（`net`）都是盲玩抓到以后加的单条检查。盲玩现在暂停，这类漏洞没有别的来源。

建议做成一条通用审计：对每个任务的参考板做机械变异（删一个元件并短接、换一个设置的取值、交换两个输入、换一个同口型的元件），跑这一关的测试，统计杀掉的比例；活下来的变异体就是测试没有区分的错误解法，按 `元件@关卡` 报出。纠错关已经在用「参考解各改错一处」出题，变异算子可以共用。再加一条有界搜索：用托盘里的元件穷举不超过 3–4 个元件的板，报出能通过的、比参考解明显短的解。

这是目前唯一能在没有玩家数据时给出的经验性质量信号，也直接服务「提高 AI 关卡设计质量」。

### 3. 引擎资源缺类型签名

`expr.js` 的检查只有参数个数和「要纯数的参数不是输入」（第 164 行附近）。口只有名字，接线能不能接由各领域的 `parts.refuse` 用代码回答。

给引擎资源声明输入输出的值形状（`scalar`、`grid`、`bits`、`ticks`、`list`，`kit/engine/views.js` 已有这组形状），之后三件事从同一份签名推出：式子的检查（`round(image)` 这类错误不必单独列规则）、接线拒绝、一个值能用哪些显示方式。有状态的资源（寄存、跨拍保存）也需要在这里定下形状，逐拍领域的元件才能搬进 `parts.json`（阶段 6.6 剩下的那一半）。

### 4. 平台化的三个前置

**存储。** `ops/workspace.js` 直接用 `node:fs` 读写，并发靠 `changes.lock` 文件；游戏的关卡数还要用正则改 `games/games.js` 的源码（`hubEntry`）。多人、多机时都撑不住。建议现在就把 workspace 收成一个存储接口（读一款游戏的文件、原子地写一个变更集、追加日志、取 head），文件系统是它的第一个实现；`games.js` 里随内容变的字段挪进数据。接口定了，换成 git 后端或数据库是局部改动。

**权限。** 决策三的两级权限在操作集里没有对应物（`ops/` 里没有任何级别或角色的概念）。建议每个操作声明它需要的级别：`level.*`、`task.*`、`text.set`、`glossary.*` 是创作级；`part.*`、`parts.set`、`game.set` 里改课程形状和词汇表版本的是内核级。`modify` 按调用方的级别拒绝。开发服务器上的 HTTP 桥没有认证，只能留在本机。

**版本。** 词汇表有只增不改的版本和快照，这很好。但内核自己的格式没有版本号：蓝图文本语法、元件式子语法、`parts.json` 和 `blueprint.json` 的 schema、`changes.jsonl` 的行格式。内容和代码已经可以分开发布（`publish:content`），内容需要能声明它对的内核格式版本。另外，存档的 stamp 是整款游戏一个哈希（`stamp.js`），改任何一个元件或任何一关的谜题就清空全部进度；开发阶段没问题，上线前要细到任务，并沿 `requires`、`carry` 和封装件依赖传到下游。

### 5. kit 还不是一个独立的包

- 所有命令在 `trace-viewer/package.json` 里，依赖装在 `trace-viewer/node_modules`；`engine/games.mjs`、`pipeline/pipeline.mjs` 写死了 `../trace-viewer` 的路径。
- `image` 领域导入 `trace-viewer/src/index.css` 和笔记站的插图注册表。
- ESLint 的配置在 `trace-viewer/`，覆盖不到 `games/kit`（实测：对 kit 的文件报「在 base path 之外」），CI 里也没有 lint。
- 没有任何类型检查（`@ts-check` 零处）。领域契约是运行时检查的，但 `CircuitLevel` 的适配面（`card.body`、`thumb`、`tileExtra`、`sinkBody` 等二十来个钩子）只有文档。

建议：`games/kit` 有自己的 `package.json`（npm workspaces），笔记站是它的使用者之一；lint 覆盖 kit 并进 `test-kit.yml`，加一条导入边界规则（领域不引用别的领域，内核不静态引用领域），把现在靠自觉保持的干净状态固定下来；适配面写成 JSDoc 类型并对 `shell/` 和 `engine/` 开 `checkJs`。

### 6. 确定性

`domains/image/engine/parts/generative.js` 的 `dg_sample` 用 `Math.random()` 取种子。封装件跑玩家的电路、运行要能回放和留在板上，检查要可复现，所以元件求值里不应有未播种的随机源。建议由求值上下文给种子（测试的序号加节点路径），并加一条契约检查：领域的求值代码里不出现 `Math.random` 和 `Date.now`。

### 7. 检查的增量化

单款 5–15 秒对 studio 的「改完 0.7 秒后整款检查」偏慢（`network` 15 秒，`qed` 12 秒）。两处可以省：

- 约 4 秒的 vite 启动是每次命令付一遍，studio 的常驻进程已经免掉，命令行和 MCP 也可以用常驻进程。
- 领域检查按任务缓存：键是任务的谜题哈希（`stamp.js` 已经在算）加它依赖的封装件的板的哈希，没变的任务不重跑参考解。§7.0 现在靠人判断的影响范围就变成了机械的。

### 8. 流水线绑定在一个执行器上

`pipeline.mjs` 直接 `spawnSync('claude', ['-p', …])`，默认模型写死。建议把「跑一步」抽成接口（输入 brief 和工具白名单，输出报告和用量），`claude -p` 是一个实现；这样才能比较不同模型在同一专题上的闸门通过率和评审发现数，流水线本身的质量才有数可看。

### 9. 文档

`DESIGN.md` 一千多行，同时承担规范、现状清单、走查记录（Playwright 的实测数字）和实例，中英文段落混排。对面向 agent 的平台，文档就是接口，漂移就是缺陷。本次已修的三处失效引用：地图小节丢了标题（现为 §2.6）、「第 7 节第 5 步」、SKILL 里的「§7 steps 9–11」。

建议拆成三份：规范（契约、schema、界面约定，尽量从代码生成：`describe` 已能打印词汇表，操作表和契约表同理）、现状与工作单（「现状和待做」「还没有的」这些段落）、实例。再加一条文档 lint：章节引用解析得到、提到的文件路径存在。

### 10. 适用范围要写明

九种机制里只有数据流电路和逐拍总线有脚手架；框、参数台、纠错与修正、词序条各只有一个领域用过，是从单一用例抽出的抽象，第二个使用者出现前接口还会变。《句法之图》不走电路编辑器。平台对外说「几乎任何主题」之前，`DIRECTION.md` 第 5 节值得加一条：适合的是有组合结构、能由少量原始能力逐层搭起来的主题；以记忆、语感、判断为主的主题需要另一种玩法，不在当前内核的承诺之内。

### 11. 面向玩家的平台功能

进度只在浏览器的 localStorage 里，没有导出、导入和跨设备。文字固定为 `{ zh, en }` 两面（`stamp.js` 的 `isText` 等处写死了这两个键），加第三种语言要改内核。两者都不急，但都是越晚改越贵的数据形状，建议在阶段 7 之前定下：存档能导出成一个文件；文字是「语言 → 字符串」的映射，必填的基准语言由游戏声明。

## 建议的顺序

1. 第 1 条（kit 变更时跑全部游戏的检查）和第 6 条（确定性）：各半天，立刻堵住两类静默错误。
2. 第 2 条（变异审计）：一到两周，替代暂停的盲玩。
3. 第 3 条（资源签名）：和阶段 6.6 的有状态资源一起做。
4. 第 5 条（独立包、lint、类型）：阶段 6.5 重做游戏之前做，重做时就在新边界里。
5. 第 4 条（存储接口、操作级别、格式版本）：阶段 7 的前置。
