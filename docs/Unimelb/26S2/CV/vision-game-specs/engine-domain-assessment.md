# Chapter 0–1 Implementation Gap Assessment

Status: design inspection only. No engine, domain, game content or existing design file was changed. A proposed capability below is not evidence that it exists or that the existing framework has been executed against these specifications.

## What can be reused

- Shared course layout, prerequisite graph, branch and challenge conventions, circuit editor, saved player-built boards, generic parameter bench and numeric image comparison provide useful foundations. Actual compatibility depends on the chosen domain and content schema.
- `games/kit/domains/image/engine/image.js` represents a single floating-point plane as `{w,h,data}`, supports rectangular dimensions, indexing, shifts and dimension/value comparison. Its numeric values can extend outside [0,1]. `ui/ImageView.jsx` renders a grayscale display, so display and underlying values are already conceptually separable.
- The current image domain has multiple input/output ports and several colour-related examples using separate planes. It does not follow that one first-class RGB value, channel-aware comparison and general-purpose channel assembly are supported.
- `image/benches/obscura.js` provides a physical pinhole camera-obscura model with height, blur and brightness, and shared parameter-bench infrastructure has controls, stages, numeric goals and domain-specific displays. It is a useful starting point, not the complete camera and lens model specified here.
- The general shell supplies row-table controls and case playback components. Their existence does not by itself provide chapter 0's particular classification, evidence and scene-comparison exercises.

## Shared engine: likely changes versus domain-specific changes

1. **Stable task IDs:** `games/DESIGN.md` describes task IDs and `taskLevel`/`taskLevels` for the newer contract while identifying image as a prototype with positional tasks. For these chapters, migrate the image domain to the current task contract if needed, including save migration via the supported operations. This is primarily domain/content integration; the shared task machinery already exists. Do not reuse the proposal IDs over existing saves without an explicit migration.
2. **Choice/structured answer UX:** first try existing table, forms and bench components. If several domains genuinely need a generic accessible selection or multi-case interaction that cannot be expressed through those components, extend the shared shell with a domain-independent interface. This inspection does not prove such a kernel change is necessary.
3. **Per-pixel execution:** determine whether the existing shared circuit or machine abstractions can represent coordinate iteration and dynamic output shapes cleanly. Add shared execution support only if a domain-neutral abstraction is warranted; otherwise keep image sampling, values and evaluators in the image domain. This is an architectural decision, not an established engine defect.
4. **No mandatory kernel rewrite:** the current generic bench, course graph and test mechanisms are useful starting points. Capability must be proven with the first representative vertical slice before concluding that further kernel work is required.

## Design gates before executable authoring

- Chapter 0 currently has several structured selection exercises. Prototype and blind-test them: retain them only if they teach a meaningful action and do not become a vocabulary quiz. Several exercises may need to become tasks in a smaller number of levels. The authored reference interactions and numeric examples must be executable and tested, not assumed correct.
- The current proposal groups multiple primitive capabilities at 1D1 and 1D3. The handbook permits at most one new idea per level. Split lead-ins or demonstrate that the additional operations are already acquired before production authoring; do not relax the audit to make the proposal pass.
- The point-lookup and RGB assembly examples are explicitly primitive demonstrations, not player-built composites. Confirm they warrant a separate level under the handbook's showcase rule; otherwise fold each into the first substantive use.
- For 1G, formalise the focus/defocus model and numeric targets before implementing. Until then, the three lens levels are pedagogical specifications, not executable test cases.
- Resolve whether crop and resize operate on scalar planes only or RGB bundles, and verify all built-part interfaces and later usage. Pin down invalid inputs instead of relying on implicit broadcasting or clipping.
- Follow the repository's docs-first content process and the applicable operation/pipeline gates when implementing. This proposal is an independent design artefact and does not itself modify or replace the current game's design or curriculum.
