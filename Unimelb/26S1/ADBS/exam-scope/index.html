    COMP90050 Final Exam Scope¶

    Exam Format¶

    • The final is a two-hour, on-campus written examination worth 50% of the subject.
    • It is open book: unlimited printed or handwritten resources are permitted, but digital resources are not permitted.
    • A non-programmable calculator is permitted, although the announcement states that the exam will not contain much calculation.
    • The actual paper will contain more questions than the four-page sample paper.
    • Marks differ by question, and answers must be written in the designated answer areas.

    The subject hurdle requires at least 30/60 across the final examination and five quizzes combined. The group project has a separate 20/40 hurdle.

    Scope Boundary¶

    The examinable body of material is:

    1. The topics identified on the Canvas weekly-content page.
    2. Both prerecorded and live lecture material.
    3. The corresponding tutorial exercises and practical labs.
    4. Only the portions of reference-book chapters actually covered in lectures or tutorials.

    Explicit Exclusions¶

    • Week 2: the linked Oracle query-optimisation reading.
    • Week 3: the linked article about whether clustered indexes physically store rows in key order.
    • Week 4: the external MySQL and Microsoft SQL Server savepoint/nested-transaction readings.
    • Week 5: comparisons among alternative versions of Dekker's algorithm and Peterson's algorithm; the MySQL deadlock demonstration video.
    • Week 9: detailed bit-by-bit CRC operations. The purpose and use of CRC remain examinable.
    • Week 9: linked industry readings about Dell storage, RAID and CRC.
    • Week 10: buffer-management content from the linked external reading that was not covered in lectures or tutorials.

    [!warning] An external reading being excluded does not exclude the lecture concept attached to it. For example, CRC as a reliability technique is in scope even though detailed bitwise CRC calculation is not.

    Week-by-Week Knowledge Outline¶

    Week 1: DBMS Foundations, Hardware and Architectures¶

    Core concepts¶

    • Database and DBMS purpose: efficient access, effectiveness under concurrent use, security and reliability.
    • Performance factors: storage devices, I/O bandwidth, memory, database architecture, database type, indexing and query optimisation.
    • HDD components: platters, tracks, sectors, heads, seek time, rotational delay and transfer time.
    • SSD comparison: no seek or rotational delay under the model used in the course.
    • Memory hierarchy, cache hit ratio, effective memory access time and disk-buffer access time.
    • Database types: simple files, relational, object-oriented and NoSQL.
    • NoSQL categories: key-value, document, column and graph databases.
    • Architectures: centralised, client-server, distributed, web, grid, peer-to-peer and cloud.
    • Cloud service examples and the distinction among compute, block storage and object storage.

    Required skills¶

    • Calculate HDD access time and effective memory/cache access time.
    • Compare storage technologies under stated assumptions.
    • Select a database type or architecture for an application and justify the trade-off.
    • Match NoSQL models to access patterns.

    Week 2: Query Processing and Optimisation¶

    Core concepts¶

    • Database engine components and the query-processing pipeline.
    • Translation from SQL to relational algebra.
    • Selection, projection, product, theta join and natural join.
    • Pages/blocks as the main I/O cost unit.
    • Cost-based optimisation: equivalent expressions, physical plans and cheapest-plan selection.
    • Reduction factors and intermediate-result size estimation.
    • Heap scans versus index scans.
    • Nested-loop and page-oriented nested-loop joins, including outer-relation choice.
    • Merge join and hash join at the conceptual comparison level presented in class.
    • Exhaustive enumeration, heuristics and adaptive plans.
    • Practical tuning: refresh statistics, force a plan, add an index, parameterise/rewrite a query, store derived data, use pre-joined tables and use memory appropriately.

    Required skills¶

    • Estimate selection and join result sizes.
    • Calculate simple and page-oriented nested-loop join costs and seek counts.
    • Choose an optimisation strategy for a simple or complex query.
    • Explain how stale statistics can produce a poor plan.
    • Apply the course convention that optimiser cost calculation does not change merely because the relevant tables are currently in main memory.

    Week 3: Indexing¶

    Core concepts¶

    • Search keys, ordered indexes and the relationship between selectivity and index usefulness.
    • Primary/secondary and clustered/non-clustered indexing concepts as presented in the lecture.
    • B+ trees for equality and range search.
    • Hash indexes for equality lookup.
    • Bitmap indexes for low-cardinality attributes and set-style filtering.
    • Quadtrees and R-trees for spatial search.
    • Creating and using indexes in SQL.
    • Cases where a full scan is more appropriate than an index.

    Required skills¶

    • Select an index type and search key from a query's predicate and data characteristics.
    • Explain why an index helps or does not help.
    • Recognise that an aggregate over all records may have no useful filtering index.
    • Read a MySQL EXPLAIN plan and connect plan changes to index creation.

    Week 4: Transactions and Transaction Processing¶

    Core concepts¶

    • A transaction as a unit of work.
    • ACID: atomicity, consistency, isolation and durability.
    • Unprotected, protected and real actions.
    • Flat transactions, flat transactions with savepoints, chained transactions and nested transactions.
    • Nested-transaction commit, rollback and visibility rules.
    • Why long-running work should not always be modelled as one flat transaction.
    • Singleton selection, cursors and SQL transaction boundaries at the level used in tutorials.
    • Transaction-processing monitors and their services: heterogeneity, communication, terminal/presentation, context and restart support.

    Required skills¶

    • Determine which nested transactions commit or roll back after parent/child failures.
    • Trace savepoint and rollback behaviour.
    • Explain why a TP monitor is needed and why one process should not provide every monitor service.

    Week 5: Concurrency Primitives and Deadlocks¶

    Core concepts¶

    • Why concurrent access requires exclusive-access mechanisms.
    • OS locks, spin locks and their cost/waiting trade-offs.
    • Atomic test-and-set and compare-and-swap.
    • Semaphores, wait queues and lock release.
    • Convoys and convoy-avoidance behaviour.
    • Deadlocks and resource-dependency graphs.
    • Deadlock prevention, avoidance, detection and timeout/rollback handling.

    Required skills¶

    • Trace whether a lock implementation preserves exclusive access.
    • Identify a deadlock cycle.
    • Compare practical deadlock-handling strategies.
    • Explain the factors affecting deadlock probability.

    Week 6: Isolation, Dependencies and Two-Phase Locking¶

    Core concepts¶

    • Isolation as equivalence to a serial execution, without requiring literal sequential execution.
    • Transaction inputs and outputs.
    • Write-write, write-read and read-write dependencies.
    • Dirty read, unrepeatable read and lost update.
    • Histories and dependency graphs.
    • Before/after sets, cycles and wormhole transactions.
    • Well-formed transactions, legal histories and two-phase locking.
    • Growing and shrinking phases.
    • Locking, converse-locking and rollback theorems at the level covered in class.

    Required skills¶

    • Derive dependencies from a history.
    • Draw a dependency graph and determine serialisability/isolation.
    • Detect a wormhole using a cycle or intersecting before/after sets.
    • Identify operations that violate two-phase locking.
    • Correctly recognise dirty reads, unrepeatable reads and lost updates in an interleaving.

    Week 7: Advanced Locking and Concurrency Control¶

    Core concepts¶

    • Lock granularity and hierarchical database objects.
    • Shared, exclusive, update and intention locks.
    • IS, IX and SIX compatibility across hierarchy levels.
    • Lock escalation and the concurrency/overhead trade-off.
    • Optimistic concurrency control.
    • Snapshot isolation and version-based reads.
    • Timestamp ordering.
    • Isolation degrees and when locks are retained or released.

    Required skills¶

    • Use a compatibility matrix to determine which transactions can run concurrently.
    • Check both ancestor intention locks and fine-grained locks.
    • Convert a locking sequence to a stronger isolation degree.
    • Compare pessimistic locking, optimistic locking, snapshot isolation and timestamping.

    Week 8: Fault Tolerance and Reliable Communication¶

    Core concepts¶

    • Fault-tolerance goals and failure assumptions.
    • RAID organisations covered in class, including striping, mirroring and parity.
    • Reliability, mean-time-to-failure reasoning and disk-space utilisation.
    • Fail-fast and fail-vote approaches.
    • Reliable communication using stable storage, sequence numbers, acknowledgements and retransmission state.

    Required skills¶

    • Compare RAID reliability and usable capacity.
    • Determine how many disk failures a configuration tolerates.
    • Update stable-storage Out, Ack and In records after a message and acknowledgement.

    Week 9: Reliable Writes, Logging and WAL¶

    Core concepts¶

    • Disk-write failure and consistency problems.
    • Duplex write and logged write.
    • CRC as an error-detection concept, excluding detailed bitwise execution.
    • Buffer pools, page transfer, fix/unfix, dirty pages and eviction.
    • Logging for recovery.
    • Write-ahead logging rules.
    • Log sequence numbers, pageLSN, flushedLSN and per-transaction log chains.
    • Steal/no-force motivation at the level presented with WAL.
    • Checkpointing, simple transaction abort and transaction commit.

    Required skills¶

    • Explain why the log must reach stable storage before the corresponding data page.
    • Decide whether a page/log write is permitted from LSN relationships.
    • Trace commit and abort effects through the log.

    Week 10: ARIES Crash Recovery¶

    Core concepts¶

    • Recovery goals: preserve committed transactions and remove incomplete transactions.
    • Transaction table and dirty-page table reconstruction.
    • recLSN, lastLSN, prevLSN and compensation log records.
    • Analysis phase: reconstruct state and identify winners/losers.
    • Redo phase: start from the oldest required recLSN and repeat history conditionally using pageLSN.
    • Undo phase: traverse loser transactions backwards and write CLRs.
    • Recovery from a crash during restart.
    • Checkpoint frequency as a recovery-time versus transaction-overhead trade-off.

    Required skills¶

    • Execute all three ARIES phases on a supplied log.
    • Build/update the transaction table and dirty-page table.
    • State the redo starting point and decide which updates are actually redone.
    • Follow undoNextLSN and generate the required CLR.

    Week 11: Distributed Databases, CAP and NoSQL¶

    Core concepts¶

    • Atomicity in distributed transactions.
    • Two-phase commit: prepare/vote and global commit/abort phases.
    • Coordinator and participant failure/timeout behaviour.
    • Distributed concurrency control using lock release, timestamps and optimistic methods.
    • Replicated data and one-copy serialisability.
    • CAP: consistency, availability and partition tolerance.
    • Strong, weak and eventual consistency.
    • Causal, read-your-write, session, monotonic-read and monotonic-write consistency.
    • Dynamic consistency/availability trade-offs and partitioning a system by requirement.
    • BASE: basically available, soft state and eventual consistency.
    • PACELC at the conceptual level presented in the lecture.
    • NoSQL document, graph, key-value and column stores.

    Required skills¶

    • Trace commit or abort outcomes in 2PC failure scenarios.
    • Explain why eventual consistency can be preferable in a highly available partition-prone service.
    • Choose a consistency guarantee for an application.
    • Relate NoSQL/BASE design choices to CAP trade-offs.

    Week 12: Backup, Shadow Paging and Data Warehousing¶

    Core concepts¶

    • Remote backup, heartbeat failure detection and transfer of control.
    • Redo processing at the backup and hot-spare behaviour.
    • One-safe, two-very-safe and two-safe commit policies.
    • Shadow paging: current/shadow page tables, copy-on-write, commit pointer switch, recovery, advantages and disadvantages.
    • Backup-strategy design: full versus partial/differential backup, update frequency, space, retention and recovery objectives.
    • Data warehouses as unified historical repositories for analytics.
    • Source-driven versus destination-driven loading.
    • Why exact synchronisation with operational systems is often too expensive.
    • Schema integration, data cleansing, update propagation and summarisation.
    • Practical document-store concepts: database/collection/document terminology, flexible schema and MongoDB filtering.

    Required skills¶

    • Compare remote-backup durability/availability policies.
    • Trace shadow-page updates and commit/recovery behaviour.
    • Choose backup frequency and type from workload and recovery requirements.
    • Explain data-warehouse design trade-offs.
    • Reason about distributed timestamping, available-copies replication and 2PC failures.

    Sample-Exam Signal¶

    The sample paper is evidence about question style, not a complete prediction of topic weighting. Its five tasks require:

    1. Updating reliable-message stable-storage state.
    2. Applying CAP to justify eventual consistency.
    3. Selecting B+ tree, R-tree/quadtree or no index for different queries.
    4. Applying the course's optimiser cost convention.
    5. Evaluating hierarchical lock compatibility and transaction arrival order.

    The expected response style is concise but justified: identify the concept, apply it to the given scenario, and state the reason. Several questions explicitly award marks for rationale, not only the final choice.

    Revision Priorities¶

    Priority 1: Procedure-heavy¶

    • Query result-size and join-cost calculation.
    • Index selection.
    • Dependency graph, wormhole and two-phase-locking analysis.
    • Granular/intention-lock compatibility.
    • RAID reliability/capacity reasoning.
    • WAL/LSN reasoning and complete ARIES recovery.
    • Two-phase-commit failure scenarios.

    Priority 2: Comparison-heavy¶

    • Database types and architectures.
    • Optimisation strategies.
    • Transaction models.
    • Concurrency-control methods.
    • CAP/consistency/BASE choices.
    • Backup and recovery strategies.

    Priority 3: Definition-heavy¶

    • Hardware and memory hierarchy terminology.
    • TP-monitor services.
    • Fail-fast/fail-vote and reliable communication.
    • Data-warehouse design concepts.

    Final Checklist¶

    • [ ] Can solve every tutorial exercise without reading its solution.
    • [ ] Can complete the sample exam under a two-hour limit.
    • [ ] Can explain every choice, not merely name an algorithm or index.
    • [ ] Can work through ARIES and lock-compatibility tables accurately.
    • [ ] Can distinguish explicit exclusions from examinable lecture concepts.
    • [ ] Has printed the required notes because digital resources are prohibited.
